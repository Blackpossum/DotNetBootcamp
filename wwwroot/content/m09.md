## What EF Core is (and isn't)

**Entity Framework Core** is .NET's flagship ORM (object-relational mapper): it maps C# classes to database tables and translates LINQ queries into SQL. Current version: **EF Core 10** (ships alongside .NET 10, LTS).

What it buys you: no hand-written SQL for routine operations, compile-checked queries, database-agnostic code (SQLite today, PostgreSQL/SQL Server tomorrow), migrations as versioned schema history. What it does *not* do: absolve you from understanding SQL — the best EF users read the generated SQL fluently (lesson 3).

We use **SQLite**: a full SQL engine in a single file, zero installation — ideal for learning and genuinely used in production for local/embedded scenarios (this app's course data could live in one).

## The three building blocks

```bash
dotnet add package Microsoft.EntityFrameworkCore.Sqlite
```

### 1. Entities — plain classes

```csharp
public class Author
{
    public int Id { get; set; }                      // convention: 'Id' = primary key, auto-increment
    public required string Name { get; set; }
    public List<Book> Books { get; } = [];           // navigation property (next lesson)
}

public class Book
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public decimal Price { get; set; }
    public int AuthorId { get; set; }                // foreign key by convention
    public Author Author { get; set; } = null!;      // reference navigation
}
```

### 2. The DbContext — your unit of work

```csharp
using Microsoft.EntityFrameworkCore;

public class BookstoreContext : DbContext
{
    public DbSet<Author> Authors => Set<Author>();
    public DbSet<Book> Books => Set<Book>();

    protected override void OnConfiguring(DbContextOptionsBuilder options)
        => options.UseSqlite("Data Source=bookstore.db");
}
```

A `DbSet<T>` represents a table; the context tracks changes and coordinates saves. **Contexts are units of work**: create, use briefly, dispose — never share one across long lifetimes or threads (in ASP.NET Core, DI hands you one per request — Module 10).

### 3. Creating the database

```csharp
using var db = new BookstoreContext();
db.Database.EnsureCreated();          // dev-only shortcut: create schema from the model NOW
```

`EnsureCreated` is for experiments; real projects use **migrations** (next lesson) — know both and their tradeoff: EnsureCreated can't evolve schema, migrations can.

## CRUD — the daily verbs

```csharp
// CREATE
var author = new Author { Name = "Martin Fowler" };
db.Authors.Add(author);                              // tracked as Added
db.Books.Add(new Book { Title = "Refactoring", Price = 47.99m, Author = author });
await db.SaveChangesAsync();                         // ONE transaction, INSERTs happen HERE
Console.WriteLine(author.Id);                        // DB-generated key populated automatically!

// READ
var cheap = await db.Books
    .Where(b => b.Price < 50)
    .OrderBy(b => b.Title)
    .ToListAsync();                                  // async LINQ → SQL (needs using Microsoft.EntityFrameworkCore)

var one = await db.Books.FirstOrDefaultAsync(b => b.Title == "Refactoring");
var byKey = await db.Books.FindAsync(1);             // checks the tracker FIRST, then the DB

// UPDATE — load, mutate, save; the tracker diffs for you
var book = await db.Books.FirstAsync(b => b.Id == 1);
book.Price = 39.99m;
await db.SaveChangesAsync();                         // UPDATE Books SET Price=… WHERE Id=1 (only changed columns!)

// DELETE
db.Books.Remove(book);
await db.SaveChangesAsync();

// Bulk operations WITHOUT loading (EF7+) — set-based, immediate, no tracking:
await db.Books.Where(b => b.Price < 5m).ExecuteDeleteAsync();
await db.Books.Where(b => b.AuthorId == 2)
              .ExecuteUpdateAsync(s => s.SetProperty(b => b.Price, b => b.Price * 0.9m));
```

## Change tracking — the engine under everything

When a query materializes entities, the context **snapshots** them. `SaveChangesAsync` compares current values to snapshots and emits exactly the needed SQL. States: `Added`, `Unchanged`, `Modified`, `Deleted`, `Detached`. This is why "load → mutate → save" needs no explicit UPDATE statement — and why long-lived contexts leak memory (the tracker never forgets).

:::tip See the SQL from day one
`options.UseSqlite(…).LogTo(Console.WriteLine, LogLevel.Information)` prints every SQL statement. Leave it on for this whole module — the habit of *reading what EF sends* is the single best predictor of EF competence.
:::

### Step 2 — create + seed

```csharp
using Microsoft.EntityFrameworkCore;

using (var db = new BookstoreContext())
{
    await db.Database.EnsureDeletedAsync();          // fresh start each run while learning
    await db.Database.EnsureCreatedAsync();

    var fowler = new Author { Name = "Martin Fowler" };
    var evans = new Author { Name = "Eric Evans" };

    db.AddRange(
        new Book { Title = "Refactoring", Price = 47.99m, Author = fowler },
        new Book { Title = "Patterns of EAA", Price = 54.99m, Author = fowler },
        new Book { Title = "Domain-Driven Design", Price = 59.99m, Author = evans });

    int rows = await db.SaveChangesAsync();
    Console.WriteLine($"seeded {rows} rows");
}
```

Read the logged SQL: two INSERTs into Authors, three into Books, all in one transaction, foreign keys wired automatically because the *object graph* connected them. Open `bookstore.db` with any SQLite browser (or the `sqlite3` CLI) and look at the real tables — EF is not magic, it's SQL generation.

### Step 3 — query and watch the translation

```csharp
using (var db = new BookstoreContext())
{
    var expensive = await db.Books
        .Where(b => b.Price > 50)
        .Select(b => new { b.Title, b.Price, AuthorName = b.Author.Name })
        .ToListAsync();

    foreach (var b in expensive)
        Console.WriteLine($"{b.Title} by {b.AuthorName}: {b.Price:C}");
}
```

Find in the log: one SELECT with a JOIN — `b.Author.Name` inside Select became SQL, no second query. Projections (`Select` to an anonymous type) fetch *only the named columns* — remember the shape of this log line; lesson 3 builds a whole discipline on it.

### Step 4 — update & delete, tracker visible

```csharp
using (var db = new BookstoreContext())
{
    var book = await db.Books.FirstAsync(b => b.Title == "Refactoring");
    book.Price = 41.99m;

    Console.WriteLine(db.Entry(book).State);         // Modified — the tracker noticed
    await db.SaveChangesAsync();                     // log: UPDATE … SET Price = @p0 WHERE Id = @p1 — ONLY Price!

    await db.Books.Where(b => b.Price > 55m).ExecuteDeleteAsync();   // log: one DELETE, no SELECT first
}
```

### Step 5 — prove FindAsync's cache behavior

```csharp
using (var db = new BookstoreContext())
{
    var a = await db.Books.FindAsync(1);             // SQL logged: SELECT …
    var b = await db.Books.FindAsync(1);             // NO SQL — served from the tracker
    Console.WriteLine(ReferenceEquals(a, b));        // True — identity map: one instance per key per context
}
```

Two lessons in one experiment: Find's tracker-first lookup, and the **identity map** — a context never gives you two objects for one row.

## Challenge: `ExpenseTracker` — a persistent CLI

Build the classic: expenses stored in SQLite, commands to add/list/summarize.

### Requirements

1. Entity `Expense`: Id, required `Description`, `decimal Amount`, `DateOnly Date` (SQLite stores it fine), required `string Category`. Context `ExpenseContext` with SQL logging on, db file under your AppData folder (Module 6 skill — not the working directory!).
2. Commands (your REPL pattern): `add <amount> <category> <description…>` (date = today), `list [category]` (newest first), `month` (current month's expenses grouped by category with totals + grand total, computed **in the database** — GroupBy in the LINQ query, verify in the SQL log), `raise <category> <percent>` (ExecuteUpdateAsync — no loading), `prune <days>` (ExecuteDeleteAsync for entries older than N days), `quit`.
3. Every DB op async; context created per command (unit of work), not one for the whole REPL.
4. After `month`, paste the logged GROUP BY SQL as a comment in your code — evidence you read it.
5. Prove persistence: quit, rerun, `list` still shows data.

:::solution Show solution (core)
```csharp
using Microsoft.EntityFrameworkCore;

public class Expense
{
    public int Id { get; set; }
    public required string Description { get; set; }
    public decimal Amount { get; set; }
    public DateOnly Date { get; set; }
    public required string Category { get; set; }
}

public class ExpenseContext : DbContext
{
    public DbSet<Expense> Expenses => Set<Expense>();

    public static string DbPath => Path.Combine(
        Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData),
        "ExpenseTracker", "expenses.db");

    protected override void OnConfiguring(DbContextOptionsBuilder options)
        => options.UseSqlite($"Data Source={DbPath}")
                  .LogTo(Console.WriteLine, Microsoft.Extensions.Logging.LogLevel.Information);
}

Directory.CreateDirectory(Path.GetDirectoryName(ExpenseContext.DbPath)!);
using (var setup = new ExpenseContext())
    await setup.Database.EnsureCreatedAsync();

while (true)
{
    Console.Write("> ");
    string[] p = (Console.ReadLine() ?? "quit").Split(' ', StringSplitOptions.RemoveEmptyEntries);
    if (p is [] or ["quit"]) break;

    using var db = new ExpenseContext();             // unit of work per command

    switch (p)
    {
        case ["add", var amt, var cat, .. var desc] when decimal.TryParse(amt, out decimal amount):
            db.Add(new Expense
            {
                Amount = amount,
                Category = cat,
                Description = string.Join(' ', desc),
                Date = DateOnly.FromDateTime(DateTime.Today),
            });
            await db.SaveChangesAsync();
            Console.WriteLine("saved");
            break;

        case ["list", .. var maybeCat]:
        {
            var query = db.Expenses.AsQueryable();
            if (maybeCat is [var cat2])
                query = query.Where(e => e.Category == cat2);

            foreach (var e in await query.OrderByDescending(e => e.Date).ThenByDescending(e => e.Id).ToListAsync())
                Console.WriteLine($"{e.Date}  {e.Category,-10} {e.Amount,8:C}  {e.Description}");
            break;
        }

        case ["month"]:
        {
            var start = new DateOnly(DateTime.Today.Year, DateTime.Today.Month, 1);
            var groups = await db.Expenses
                .Where(e => e.Date >= start)
                .GroupBy(e => e.Category)
                .Select(g => new { Category = g.Key, Total = g.Sum(e => e.Amount), Count = g.Count() })
                .OrderByDescending(x => x.Total)
                .ToListAsync();
            // Logged SQL (evidence):
            // SELECT "e"."Category", COALESCE(SUM("e"."Amount"), 0.0) AS "Total", COUNT(*) AS "Count"
            // FROM "Expenses" AS "e" WHERE "e"."Date" >= @start GROUP BY "e"."Category" ORDER BY "Total" DESC

            foreach (var g in groups)
                Console.WriteLine($"{g.Category,-10} {g.Total,8:C}  ({g.Count})");
            Console.WriteLine($"{"TOTAL",-10} {groups.Sum(g => g.Total),8:C}");
            break;
        }

        case ["raise", var cat3, var pct] when decimal.TryParse(pct, out decimal percent):
            int updated = await db.Expenses
                .Where(e => e.Category == cat3)
                .ExecuteUpdateAsync(s => s.SetProperty(e => e.Amount, e => e.Amount * (1 + percent / 100)));
            Console.WriteLine($"{updated} rows updated in-database");
            break;

        case ["prune", var daysArg] when int.TryParse(daysArg, out int days):
            var cutoff = DateOnly.FromDateTime(DateTime.Today.AddDays(-days));
            int deleted = await db.Expenses.Where(e => e.Date < cutoff).ExecuteDeleteAsync();
            Console.WriteLine($"{deleted} old expenses pruned");
            break;

        default:
            Console.WriteLine("add <amt> <cat> <desc> | list [cat] | month | raise <cat> <pct> | prune <days> | quit");
            break;
    }
}
```

Note the aggregation happening *in SQL* — for a million expenses, `month` transfers a handful of group rows, not a million entities. `ExecuteUpdate/Delete` similarly never load. The rule crystallizing here: **push work to the database, pull only results** — lesson 3 makes it doctrine. (List patterns dispatching the command array — Module 5 paying rent again.)
:::

@QUIZ
? What does SaveChangesAsync actually do?
- Saves the context's configuration to disk
* Diffs tracked entities against their snapshots and emits the needed INSERT/UPDATE/DELETE statements in one transaction
- Re-runs all queries
- Flushes SQLite's cache
> The change tracker computes the delta; SaveChanges is the single point where your object mutations become SQL — atomically.

? After `db.Authors.Add(author); await db.SaveChangesAsync();`, author.Id is…
- 0 until you query it back
* Populated with the database-generated key automatically
- A Guid
- Whatever you set it to
> EF fetches store-generated values (identity keys, defaults) back into your objects as part of SaveChanges. The object graph and DB stay in sync.

? FindAsync(1) twice in one context executes…
- Two SELECTs
* One SELECT; the second call is served by the change tracker (identity map)
- Zero SELECTs
- A JOIN
> Find checks tracked entities first. Corollary: one row = one instance per context — mutations via either reference are the same mutation.

? ExecuteDeleteAsync differs from Remove + SaveChanges by…
- Being transactional
* Running one set-based SQL DELETE immediately, without loading or tracking entities
- Also deleting related entities always
- Being SQLite-only
> Load-then-remove is fine for single entities already in hand; bulk conditions should delete WHERE-style in the database. Same logic for ExecuteUpdateAsync.

? A DbContext should live…
- As an application-wide singleton
* Briefly — one unit of work (a command, a web request), then disposed
- One per entity type
- Inside each entity
> Long-lived contexts accumulate tracked entities (memory), serve stale identity-mapped data, and aren't thread-safe. Short and scoped is the law.

## Migrations: schema as versioned code

Databases evolve. **Migrations** capture each model change as generated C# you check into git:

```bash
dotnet tool install --global dotnet-ef          # once per machine
dotnet add package Microsoft.EntityFrameworkCore.Design

dotnet ef migrations add InitialCreate          # generates Migrations/xxxx_InitialCreate.cs
dotnet ef database update                       # applies pending migrations
dotnet ef migrations add AddBookRating          # after model changes: the DIFF becomes a migration
dotnet ef migrations script                     # SQL preview — what DBAs review
```

Each migration has `Up` (apply) and `Down` (revert). The database tracks applied migrations in `__EFMigrationsHistory`. Team workflow: model change → `migrations add` → review generated code (it's code! read it!) → commit → teammates/CI run `database update`. In app startup for simple deployments: `db.Database.Migrate()` applies pending ones programmatically.

:::warn EnsureCreated and migrations don't mix
EnsureCreated builds schema without recording migration history — a database created that way can't take migrations later. Pick migrations for anything that will live longer than an experiment.
:::

## Relationships — the three shapes

### One-to-many (the workhorse)

```csharp
public class Blog
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public List<Post> Posts { get; } = [];           // collection navigation
}

public class Post
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public int BlogId { get; set; }                  // FK — convention: <Nav>Id
    public Blog Blog { get; set; } = null!;          // reference navigation
}
```

Convention wires it automatically: `Post.BlogId` → FK to `Blog.Id`, cascade delete on by default for required relationships (delete a Blog, its Posts go too — configurable).

### Many-to-many

```csharp
public class Post { …; public List<Tag> Tags { get; } = []; }
public class Tag  { public int Id { get; set; } public required string Name { get; set; } public List<Post> Posts { get; } = []; }
```

Two collection navigations = EF creates the hidden join table (`PostTag`). When the join needs payload (e.g., `AddedOn`), model the join entity explicitly.

### One-to-one

```csharp
public class User    { …; public UserProfile? Profile { get; set; } }
public class UserProfile { public int Id { get; set; } public int UserId { get; set; } public User User { get; set; } = null!; }
```

## Configuration: conventions → attributes → Fluent API

Three layers, later wins:

```csharp
// Attributes — quick constraints on the entity:
public class Book
{
    [MaxLength(200)] public required string Title { get; set; }
    [Precision(10, 2)] public decimal Price { get; set; }
}

// Fluent API — the full power, in the context:
protected override void OnModelCreating(ModelBuilder b)
{
    b.Entity<Book>(e =>
    {
        e.HasIndex(x => x.Title);
        e.Property(x => x.Title).HasMaxLength(200);
        e.HasOne(x => x.Author)
         .WithMany(a => a.Books)
         .OnDelete(DeleteBehavior.Restrict);         // forbid deleting authors with books
    });

    b.Entity<Author>().HasQueryFilter(a => !a.IsDeleted);   // GLOBAL filter: soft delete pattern
}
```

Prefer conventions; add attributes for simple facts (lengths, precision); use Fluent for relationships, indexes, filters, and anything conditional. EF Core 10 adds **named query filters** — multiple filters per entity, selectively disabled with `IgnoreQueryFilters(["SoftDelete"])`.

## Loading related data — the choice that defines performance

```csharp
// 1. Eager — JOIN it in up front:
var blogs = await db.Blogs
    .Include(b => b.Posts)
    .ThenInclude(p => p.Tags)
    .ToListAsync();

// 2. Projection — load exactly the SHAPE you need (usually best):
var summaries = await db.Blogs
    .Select(b => new { b.Name, PostCount = b.Posts.Count })
    .ToListAsync();

// 3. Explicit — load later, on demand:
await db.Entry(blog).Collection(b => b.Posts).LoadAsync();

// 4. Lazy loading exists (proxy packages) — and is the classic N+1 footgun. Avoid until expert.
```

Un-Included navigations are simply **empty/null** — EF never secretly fetches (without lazy proxies). Forgetting `Include` is the #1 beginner surprise; overusing `Include` (cartesian explosions) is the #2 — `AsSplitQuery()` splits a multi-collection Include into separate SQL queries when the JOIN multiplies rows.

```csharp
using (var db = new BlogContext())
{
    var blog = await db.Blogs.FirstAsync();
    Console.WriteLine($"{blog.Name}: {blog.Posts.Count} posts");   // 0 !! — nothing was Included
}

using (var db = new BlogContext())
{
    var blog = await db.Blogs.Include(b => b.Posts).FirstAsync();

```

### Step 5 — projection beats Include for read models

```csharp
var dashboard = await db.Blogs
    .Select(b => new
    {
        b.Name,
        PostCount = b.Posts.Count,
        Latest = b.Posts.OrderByDescending(p => p.Id).Select(p => p.Title).FirstOrDefault(),
        TopTags = b.Posts.SelectMany(p => p.Tags).GroupBy(t => t.Name)
                   .OrderByDescending(g => g.Count()).Take(3).Select(g => g.Key).ToList()
    })
    .ToListAsync();
```

One SQL round-trip computing counts, latest titles, and tag rankings server-side. Compare the log with an equivalent `Include everything and compute in C#` version: less data, less memory, less code. Projection-first is the professional default for read paths.

### Step 6 — cascade behavior, felt

```csharp
db.Blogs.Remove(techBlog);
await db.SaveChangesAsync();                          // Posts go too (cascade), PostTag rows go too
```

Then reconfigure `OnDelete(DeleteBehavior.Restrict)` in OnModelCreating, add a migration, and watch the same Remove throw instead. Deletion policy is a *modeling decision*, and migrations carry it.

## Challenge: `CourseCatalog` — a realistic schema with history

Model a training platform: Courses have Modules (one-to-many, ordered); Students enroll in Courses (many-to-many **with payload**: EnrolledOn date + Progress percent — explicit join entity); Courses have an optional `CourseDetail` (one-to-one: description, hours).

### Requirements

1. Build the model with: explicit join entity `Enrollment` (StudentId + CourseId composite key via Fluent `HasKey`), Restrict delete on Course when enrollments exist, an index on `Course.Title`, MaxLength on all strings, decimal precision on `CourseDetail.PriceUsd`.
2. Three migrations telling a story: `InitialCreate` (Course+Module), `AddStudentsAndEnrollments`, `AddCourseDetails`. Apply each; keep all three in the project (history matters).
3. Seed: 2 courses (one with detail), 4 modules, 3 students, 4 enrollments with varied progress.
4. Queries (each a single LINQ expression, projection-first):
   - catalog page: title, module count, enrolled count, price (null-safe from the optional detail)
   - a student's transcript: course titles + progress, ordered by EnrolledOn
   - "at risk": enrollments with progress < 30 older than 30 days — student name, course, days enrolled
5. Prove Restrict: attempt to delete an enrolled course, catch the exception, print a friendly message.

:::solution Show solution (model + key queries)
```csharp
public class Course
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public List<Module> Modules { get; } = [];
    public List<Enrollment> Enrollments { get; } = [];
    public CourseDetail? Detail { get; set; }
}

public class Module
{
    public int Id { get; set; }
    public required string Title { get; set; }
    public int Order { get; set; }
    public int CourseId { get; set; }
    public Course Course { get; set; } = null!;
}

public class Student
{
    public int Id { get; set; }
    public required string Name { get; set; }
    public List<Enrollment> Enrollments { get; } = [];
}

public class Enrollment                                   // join entity WITH payload
{
    public int StudentId { get; set; }
    public Student Student { get; set; } = null!;
    public int CourseId { get; set; }
    public Course Course { get; set; } = null!;
    public DateOnly EnrolledOn { get; set; }
    public int Progress { get; set; }
}

public class CourseDetail
{
    public int Id { get; set; }
    public required string Description { get; set; }
    public int Hours { get; set; }
    public decimal PriceUsd { get; set; }
    public int CourseId { get; set; }
    public Course Course { get; set; } = null!;
}

public class CatalogContext : DbContext
{
    public DbSet<Course> Courses => Set<Course>();
    public DbSet<Student> Students => Set<Student>();
    public DbSet<Enrollment> Enrollments => Set<Enrollment>();

    protected override void OnConfiguring(DbContextOptionsBuilder o)
        => o.UseSqlite("Data Source=catalog.db").LogTo(Console.WriteLine, LogLevel.Information);

    protected override void OnModelCreating(ModelBuilder b)
    {
        b.Entity<Enrollment>().HasKey(e => new { e.StudentId, e.CourseId });   // composite key

        b.Entity<Enrollment>()
            .HasOne(e => e.Course).WithMany(c => c.Enrollments)
            .OnDelete(DeleteBehavior.Restrict);

        b.Entity<Course>(e =>
        {
            e.HasIndex(x => x.Title);
            e.Property(x => x.Title).HasMaxLength(150);
        });
        b.Entity<CourseDetail>().Property(x => x.PriceUsd).HasPrecision(8, 2);
        b.Entity<Student>().Property(x => x.Name).HasMaxLength(100);
        b.Entity<Module>().Property(x => x.Title).HasMaxLength(150);
    }
}
```

```csharp
// catalog page — null-safe optional detail via projection
var catalog = await db.Courses.Select(c => new
{
    c.Title,
    Modules = c.Modules.Count,
    Enrolled = c.Enrollments.Count,
    Price = c.Detail != null ? c.Detail.PriceUsd : (decimal?)null
```

## The two-world model

An EF LINQ query lives in two worlds: **expression trees** translated to SQL (server), and **objects in memory** (client). The boundary is where performance lives or dies:

```csharp
var query = db.Books.Where(b => b.Price > 20);       // IQueryable — a SQL description, nothing ran
var list = await query.ToListAsync();                 // NOW it's SQL → rows → entities

var oops = db.Books.AsEnumerable()                    // ← boundary crossed: everything after runs in C#
    .Where(b => SomeCSharpMethod(b.Title));           // fetched ALL books, filtered in memory!
```

`IQueryable` = composable SQL builder (deferred, like Module 5's LINQ but translated, not executed, per element). Calling `AsEnumerable/ToList` mid-chain drags every row across the wire. EF Core refuses silent client evaluation in Where — you get a runtime `InvalidOperationException: could not be translated` instead of a hidden table scan. When you see it: reshape the query (translatable constructs: comparisons, string.Contains/StartsWith, EF.Functions.Like, date parts, aggregate functions), or split explicitly and *knowingly*.

## Tracking vs no-tracking

```csharp
var report = await db.Books.AsNoTracking()            // read-only: skip snapshots entirely
    .Where(b => b.Price > 20)
    .ToListAsync();
```

Tracking costs memory + time per entity. **Rule: reads that won't be saved → `AsNoTracking()`** (or projections, which are naturally untracked — anonymous types/DTOs aren't entities). Mutating flows keep tracking. Context-wide default: `db.ChangeTracker.QueryTrackingBehavior = QueryTrackingBehavior.NoTracking`.

## The N+1 catastrophe (and its cures)

```csharp
// ❌ 1 query for blogs + N queries for posts = N+1 round trips
var blogs = await db.Blogs.ToListAsync();
foreach (var blog in blogs)
{
    await db.Entry(blog).Collection(b => b.Posts).LoadAsync();     // one query PER BLOG
    Console.WriteLine($"{blog.Name}: {blog.Posts.Count}");
}

// ✅ cure 1: Include (one query, JOINed)
// ✅ cure 2: projection (one query, minimal columns)
var counts = await db.Blogs.Select(b => new { b.Name, Count = b.Posts.Count }).ToListAsync();
```

N+1 is the most common ORM performance bug in existence — 10 ms locally, 30 s in production with 3,000 rows. Defense: **read your SQL logs**; count round trips per operation.

## The performance toolbox

```csharp
// Pagination — never unbounded lists:
var page = await db.Books.OrderBy(b => b.Title)
    .Skip(pageIndex * 20).Take(20)
    .ToListAsync();

// Streaming — process without materializing everything:
await foreach (var book in db.Books.AsAsyncEnumerable())
    Process(book);

// EF.Functions — provider-specific SQL:
db.Books.Where(b => EF.Functions.Like(b.Title, "%pattern%"));

// Split queries — when multi-Include JOINs explode row counts:
db.Blogs.Include(b => b.Posts).Include(b => b.Tags).AsSplitQuery();

// Raw SQL escape hatch — composable with LINQ:
db.Books.FromSql($"SELECT * FROM Books WHERE Price > {min}")        // parameterized! (interpolation is safe here)
        .Where(b => b.Title.Contains("EF"))
        .ToListAsync();
```

Indexes matter more than any of it: a `WHERE Category = X` over a million rows without an index on Category is a table scan no C# can save. `HasIndex` in the model; verify with `EXPLAIN QUERY PLAN` (SQLite).

## Compiled queries & second-level knowledge

Frequently-run hot queries can skip repeated translation with `EF.CompileAsyncQuery` — file under "when the profiler says so". Also know these exist: query tags (`.TagWith("dashboard")` labels SQL logs), `DbContext` pooling (Module 10 wires it), and interceptors (cross-cutting SQL auditing).

:::tip The three-question ritual
For every EF query you write, answer: (1) how many round trips? (2) how many rows/columns cross the wire? (3) is it tracked, and should it be? The log answers all three in ten seconds. This ritual IS senior-level EF.

## Transactions: all or nothing

`SaveChangesAsync` is already atomic — every statement in one call commits or rolls back together. Explicit transactions span *multiple* saves or mixed operations:

```csharp
await using var tx = await db.Database.BeginTransactionAsync();
try
{
    from.Balance -= amount;
    await db.SaveChangesAsync();

    to.Balance += amount;
    await db.SaveChangesAsync();

    await tx.CommitAsync();
}
catch
{
    await tx.RollbackAsync();       // both saves undone — money neither vanished nor duplicated
    throw;
}
```

(Module 6's Bank compensation logic — now done properly by the database.) Savepoints (`tx.CreateSavepointAsync`) allow partial rollback inside long transactions.

## Concurrency: when two users edit the same row

Default EF behavior is **last writer wins** — user B silently overwrites user A. For data where that's unacceptable, use **optimistic concurrency**:

```csharp
public class Product
{
    …
    [Timestamp] public byte[] Version { get; set; } = null!;      // SQL Server rowversion
}

// SQLite/PostgreSQL style — a concurrency token you bump:
b.Entity<Product>().Property(p => p.Version).IsConcurrencyToken();
```

EF appends `WHERE Id = @id AND Version = @original` to UPDATEs. If another writer got there first, zero rows match → `DbUpdateConcurrencyException`:

```csharp
try
{
    await db.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var current = await entry.GetDatabaseValuesAsync();           // what's in the DB now
    // strategies: retry with fresh data / merge fields / surface a conflict UI
}
```

Optimistic = no locks held, conflicts detected at write. The right default for web apps (pessimistic locking — `SELECT … FOR UPDATE` — exists via raw SQL for queue-worker patterns).

## Testing data access — the honest hierarchy

| Approach | Speed | Fidelity | Use |
|----------|-------|----------|-----|
| **SQLite in-memory** | fast | high for common SQL | The workhorse for repository/query tests |
| **Testcontainers** (real PostgreSQL/SQL Server in Docker) | slower | perfect | CI integration suites, provider-specific SQL |
| EF InMemory provider | fast | **low — not a database** (no SQL, no constraints, no transactions) | Avoid except trivial cases |

```csharp
static async Task SafeTransfer(BankContext db, int fromId, int toId, decimal amount, bool failMidway = false)
{

    var from = await db.Accounts.FirstAsync(a => a.Id == fromId);
    if (from.Balance < amount) throw new InvalidOperationException("insufficient funds");
    from.Balance -= amount;
    await db.SaveChangesAsync();

    if (failMidway) throw new IOException("power cut!");

    var to = await db.Accounts.FirstAsync(a => a.Id == toId);
    to.Balance += amount;
    await db.SaveChangesAsync();
    await tx.CommitAsync();
}   // no explicit Rollback needed: disposing an uncommitted transaction rolls back
```

```csharp
    public async Task<BuyResult> BuyAsync(int eventId, string buyer)
    {
        for (int attempt = 1; attempt <= 3; attempt++)
        {
            using var db = contextFactory();                       // fresh context per attempt
            await using var tx = await db.Database.BeginTransactionAsync();

            var evt = await db.Events.FirstAsync(e => e.Id == eventId);
            if (evt.Sold >= evt.Capacity) return new BuyResult.SoldOut();

            evt.Sold++;
            evt.Version = Guid.NewGuid().ToString();               // bump token
            var ticket = new Ticket { EventId = eventId, Buyer = buyer, PurchasedAt = DateTimeOffset.UtcNow };
            db.Tickets.Add(ticket);

            try
            {
                await db.SaveChangesAsync();                       // WHERE Version = original → 0 rows if raced
                await tx.CommitAsync();
                return new BuyResult.Purchased(ticket.Id);
            }
            catch (DbUpdateConcurrencyException)
            {
                // lost the race — loop retries with a FRESH read (maybe now sold out)
            }
        }
        return new BuyResult.Conflicted();
    }
}
```

```csharp
// WHY the token prevents oversells:
// Every buyer's UPDATE carries "WHERE Version = <the version I read>". Two buyers who both
// read Sold=9 both try to write; the database serializes writes, the first bumps Version,
// the second's WHERE matches ZERO rows → DbUpdateConcurrencyException → retry re-READS
// (now Sold=10) → SoldOut. The check-then-act race is closed because the ACT verifies
// the CHECK's premise atomically. No C# lock could do this across processes — the
// database is the only shared ground truth.
```

* Wraps all 5 statements in one transaction automatically — all or nothing
- Requires BeginTransaction first
- Saves only the first change
> SaveChanges is implicitly transactional. Explicit transactions exist for spanning MULTIPLE SaveChanges calls or mixing raw SQL.

? Optimistic concurrency detects conflicts by…
- Locking rows during reads
* Appending the original token/version to the UPDATE's WHERE; zero affected rows means someone else wrote first
- Comparing timestamps in C#
- Serializing all requests
> No locks held during think-time. The write itself verifies the read's premise; failure surfaces as DbUpdateConcurrencyException to handle (retry/merge/surface).

? After DbUpdateConcurrencyException, a sound retry must…
- Save again immediately
* Re-read current database state and re-apply the intent against fresh values
- Increase the timeout
- Switch to a new thread
> Saving again would just re-lose the race with stale data. Refresh (GetDatabaseValues / fresh context), recheck business rules, reapply, save.
