## C# is statically and strongly typed

Every expression has a type **known at compile time**, and the compiler refuses operations that don't make sense for that type. This is the opposite trade-off from Python/JavaScript: more red squiggles while writing, dramatically fewer surprises while running.

```csharp
int age = 25;        // declare + initialize
age = "old";         // ❌ compile error CS0029: cannot convert string to int
```

### The built-in value types

| C# keyword | .NET type | Size | Range / purpose |
|-----------|-----------|------|-----------------|
| `int` | `System.Int32` | 4 B | ±2.1 billion — the default integer |
| `long` | `System.Int64` | 8 B | ±9.2 quintillion — big counts, ticks, IDs |
| `short`, `byte` | `Int16`, `Byte` | 2 B, 1 B | Compact/interop scenarios |
| `double` | `System.Double` | 8 B | Default floating point (~15–16 significant digits, base-2) |
| `float` | `System.Single` | 4 B | Graphics/ML; suffix `f`: `3.14f` |
| `decimal` | `System.Decimal` | 16 B | Base-10, 28–29 digits — **money**; suffix `m`: `19.99m` |
| `bool` | `System.Boolean` | 1 B | `true` / `false` only — no truthy/falsy in C# |
| `char` | `System.Char` | 2 B | One UTF-16 code unit: `'A'` |

The keyword and the .NET type are the *same thing*: `int` is an alias for `System.Int32`. That's why `42.ToString()` works — even literals are full objects with methods.

:::warn Floating point vs money
`0.1 + 0.2 == 0.3` is **false** for `double` (binary fractions can't represent 0.1 exactly). For money and anything requiring exact decimal arithmetic, use `decimal`. This single fact prevents a famous class of production bugs.
:::

## The big divide: value types vs reference types

This is the most important concept in this module. Every type is one of two kinds, and they behave differently on **assignment** and **comparison**.

### Value types (`int`, `double`, `bool`, `char`, `struct`, `enum`)

The variable *contains the data itself*. Assignment **copies** the data.

```csharp
int a = 10;
int b = a;      // b gets a COPY of the value
b = 99;
Console.WriteLine(a);   // 10 — unaffected
```

### Reference types (`string`, arrays, `class` instances, delegates)

The variable contains a *reference* (essentially a pointer) to an object on the **managed heap**. Assignment copies **the reference** — both variables now point at the *same* object.

```csharp
int[] x = { 1, 2, 3 };
int[] y = x;          // y points to the SAME array
y[0] = 99;
Console.WriteLine(x[0]);   // 99 — x sees the change!
```

```
value type:                reference type:
┌─────┐  ┌─────┐           ┌───┐     ┌───┐
│a: 10│  │b: 99│           │ x │──┐  │ y │──┐
└─────┘  └─────┘           └───┘  │  └───┘  │
                                  ▼         │
                              [99, 2, 3] ◄──┘   (one object on the heap)
```

Where things live: value-type *locals* typically live on the stack (or in registers); reference-type *objects* live on the heap and are the GC's responsibility; a value type *inside* an object lives inline within that object on the heap. Don't memorize "stack vs heap" as a law — memorize the **copy vs share** semantics, which is what actually bites.

:::note Strings are special
`string` is a reference type but **immutable** — no method ever changes a string; they all return new ones. So it *feels* like a value type (`==` compares content too). More in Module 3.
:::

## Default values, `var`, and constants

```csharp
int count;                 // locals must be assigned before use (compile error otherwise)
Console.WriteLine(count);  // ❌ CS0165 use of unassigned local

var total = 42;            // 'var' = compiler INFERS int. Still statically typed!
var name = "Ada";          // string
// var z;                  // ❌ needs an initializer to infer from

const double Pi = 3.14159;      // compile-time constant, baked into IL
```

`var` changes nothing at runtime — it is purely "you figure out the type, compiler." Team conventions vary; the common rule: use `var` when the type is obvious from the right side.

Fields (variables inside a class) *do* get automatic defaults: `0`, `false`, `null`.

## Conversions

```csharp
int small = 100;
long big = small;            // ✅ implicit — no data can be lost (widening)

long huge = 5_000_000_000;
int oops = (int)huge;        // explicit CAST — may lose data! oops == 705032704
double d = 3.99;
int truncated = (int)d;      // 3 — cast truncates, never rounds

// string → number: NEVER cast; PARSE.
string input = "42";
int parsed = int.Parse(input);            // throws FormatException on bad input
bool ok = int.TryParse(input, out int n); // returns false instead of throwing — prefer this for user input

// number → string
string s = parsed.ToString();
string s2 = $"{parsed}";
```

Also meet `checked { }` blocks: inside them, integer overflow throws `OverflowException` instead of silently wrapping.

## Arithmetic and its traps

```csharp
int q  = 17 / 5;    // 3   — integer division truncates
int r  = 17 % 5;    // 2   — remainder (modulo)
double x = 17.0 / 5;  // 3.4 — one double operand promotes the whole expression
```

`%` is more useful than beginners expect: `n % 2 == 0` (even), `i % 3 == 0` (every third), wrapping indexes `(i + 1) % length`.

Compound assignment and increment:

```csharp
int n = 10;
n += 5;      // 15     also -=, *=, /=, %=
n++;         // 16     postfix: use value, THEN increment
int m = n++; // m=16, n=17
int k = ++n; // k=18, n=18 — prefix increments first (avoid mixing into expressions; keep ++ on its own line)
```

## Comparison & logic

```csharp
bool inRange = age >= 18 && age < 65;    // && and: short-circuits
bool weird   = x < 0 || x > 100;         // || or: short-circuits
bool flip    = !isOpen;
```

**Short-circuiting matters**: in `a != null && a.Length > 0`, the right side never runs when `a` is null — this ordering is a null-safety idiom, not a style choice.

### Null-related operators — the everyday four

```csharp
string? nickname = null;               // '?' marks the type as nullable

int len = nickname?.Length ?? 0;       // ?. null-conditional: null propagates instead of crashing
                                       // ?? null-coalescing: fallback when left side is null

nickname ??= "anon";                   // ??= assign only if currently null

customer?.Order = GetOrder();          // C# 14: ?. now legal on the LEFT of assignment —
                                       // assigns only if customer is not null (RHS not even evaluated otherwise)
```

### Ternary conditional

```csharp
string label = count == 1 ? "item" : "items";
```

One condition → ternary is clean. Nested ternaries → use a `switch` expression (next lesson) instead.

## Strings and interpolation

```csharp
string name = "Yosaphat";
int score = 92;

// Interpolation ($"...") — the modern default
string msg = $"{name} scored {score}!";

// Format specifiers after ':'
Console.WriteLine($"{Math.PI:F2}");        // 3.14        fixed 2 decimals
Console.WriteLine($"{1234567.891:N1}");    // 1,234,567.9 thousands separators
Console.WriteLine($"{0.847:P0}");          // 85 %        percent
Console.WriteLine($"{19.99m:C}");          // currency in your locale, e.g. $19.99
Console.WriteLine($"{255:X}");             // FF          hex
Console.WriteLine($"{7:D3}");              // 007         zero-pad
Console.WriteLine($"{"left",-10}|{"right",10}|");  // alignment: negative = left-pad

// Verbatim @"..." — backslashes are literal (paths, regex)
string path = @"C:\dev\bootcamp";

// Raw strings """...""" (C# 11+) — no escaping at all, great for JSON/XML snippets
string json = """
    { "name": "Ada", "role": "pioneer" }
    """;
```

:::tip
Interpolation calls `.ToString()` on each hole, honoring format specifiers — the same specifiers work in `string.Format`, `ToString("F2")`, and logging. Learn them once, use them everywhere.
:::

## Operator precedence — one rule to keep

Full precedence tables exist, but professionals rely on one habit: **when mixing `&&`/`||` or arithmetic with comparisons in nontrivial ways, add parentheses.** `a || b && c` means `a || (b && c)` — if you had to think about it, the parentheses were worth writing.

Write a program (project `GradeCalc`) that takes scores from the command line and prints a formatted report line per score plus a summary.

### Requirements

1. Each command-line arg is a score out of 100 (parse with `TryParse`; skip invalid args but count them).
2. Per score print: the score right-aligned in 5 chars with 1 decimal, the fraction as a percent (`P1`), and a letter grade computed with ternary/logic operators: A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 60, else F.

:::solution Show solution
```csharp
double sum = 0;
int valid = 0, skipped = 0;
double? best = null;                       // nullable: "no best yet"

foreach (string arg in args)
{
    if (!double.TryParse(arg, out double score) || score < 0 || score > 100)
    {
        skipped++;
        continue;
    }

    valid++;
    sum += score;
    best = best is null || score > best ? score : best;   // ?? alternative: best = Math.Max(best ?? score, score);

                  : score >= 80 ? "B"
                  : score >= 70 ? "C"
                  : score >= 60 ? "D" : "F";

    Console.WriteLine($"{score,5:F1}  ({score / 100:P1})  → {letter}");

double? avg = valid > 0 ? sum / valid : null;
Console.WriteLine($"Valid: {valid}, avg: {avg?.ToString("F1") ?? "n/a"}, best: {best?.ToString("F1") ?? "n/a"}, skipped: {skipped}");
```

Notes: chained ternaries formatted one-per-line stay readable (a switch expression would be better still — next lesson). `avg?.ToString("F1") ?? "n/a"` is the classic null-display idiom.

## Before the syntax: what control flow actually is

Strip away everything and a program is a **numbered list of instructions**. The computer keeps one finger on the current line, executes it, and moves the finger down to the next line. That's the default: top to bottom, one line at a time, no exceptions.

**Control flow is the small set of statements that move the finger somewhere other than "the next line."** There are only three kinds of movement, and this lesson is simply their catalog:

| Movement | Statements | What the finger does |
|----------|-----------|----------------------|
| **Choose a path** | `if`, `switch` | Skips over the lines that don't apply |
| **Repeat lines** | `while`, `for`, `foreach`, `do` | Jumps *back up* to run lines again |
| **Leave early** | `break`, `continue`, `return` | Jumps *out* of a loop or method |

That table is the complete list. Every program you will ever read — including this app's own source code — is straight-line code plus those three movements, nested and combined.

### Why branching has to exist

When you *write* a program, you don't know the data yet. You don't know what the user will type, what the file contains, what the sensor reads. So a program can't be a fixed script — it must be a **map of possible paths**, and the actual data chooses the route at runtime:

```
                 ┌─────────────┐
     ────────►   │ temp > 30 ? │
                 └──────┬──────┘
              true ◄────┴────► false
                │               │
          "Hot today"     "Not too bad"
                │               │
                └───────┬───────┘
                        ▼
              (paths rejoin, program continues)
```

An `if` statement is exactly this diagram, written as text. When you're confused by nested conditions later, draw the diagram — it's never wrong to fall back to the picture.

### Why loops have to exist

Computers earn their keep by repeating things a million times without complaining. But *you* only want to write the instruction once. A loop is the deal you strike: "here's the work, here's the rule for when to keep going."

**Every loop, in any language, answers three questions:**

1. **Where do I start?** (the initial state — `int i = 0`)
2. **When do I keep going?** (the condition — `i < 10`)
3. **What changes each lap?** (the progress — `i++`)

Miss question 3 and the condition never becomes false — that's what an *infinite loop* is: not a mystery, just missing progress. When any loop misbehaves, check the three questions in order; one of them has a wrong answer.

:::note What the machine really does
There's no `if` or `while` inside your CPU. There are only two primitive moves: *compare two values* and *jump to a line*. Every control-flow statement compiles down to compare-and-jump — you can see it in the IL from Module 1 (`brtrue` = "branch if true"). `if`/`while`/`for` exist purely so humans can read the jumps as intentions. That's worth knowing once: high-level syntax is packaging, and the packaging is for *you*.
:::

## Branching

### `if` / `else if` / `else`

```csharp
if (temp > 30)      Console.WriteLine("Hot");
else if (temp > 15) Console.WriteLine("Mild");
else                Console.WriteLine("Cold");
```

Conditions must be `bool` — `if (count)` does not compile in C#; write `if (count != 0)`. There is no truthiness, by design.

### The `switch` statement (classic)

```csharp
switch (day)
{
    case DayOfWeek.Saturday:
    case DayOfWeek.Sunday:          // fall-through by stacking labels only
        Console.WriteLine("Weekend");
        break;                      // break is mandatory
    default:
        Console.WriteLine("Weekday");
        break;
}
```

### The `switch` expression (modern default)

An *expression* that returns a value — terser, exhaustive-checked, and pattern-powered:

```csharp
string label = day switch
{
    DayOfWeek.Saturday or DayOfWeek.Sunday => "Weekend",
    DayOfWeek.Friday => "Almost!",
    _ => "Weekday"                            // _ = discard: matches anything
};
```

**Patterns** make switches powerful. The ones to know now:

```csharp
string Describe(object thing) => thing switch
{
    0 => "zero",                              // constant pattern
    int n when n < 0 => $"negative {n}",      // type pattern + when guard
    int n => $"positive {n}",
    string s => $"text of length {s.Length}", // type pattern binds a variable
    null => "nothing",
    _ => "something else"
};

string Bucket(double score) => score switch
{
    >= 90 => "A",                             // relational patterns
    >= 80 => "B",
    >= 70 and >= 65 => "C+",                  // combinators: and / or / not
    < 0 or > 100 => "invalid",
    _ => "F"
};
```

The compiler warns when a switch expression doesn't cover all inputs — exhaustiveness checking catches real bugs when you add a new enum value and forget a branch. Much more on patterns in Module 5.

## Loops

```csharp
for (int i = 0; i < 5; i++) { }        // counted; you control index math

foreach (var item in collection) { }   // iterate anything enumerable — the default choice
                                       // (you cannot reassign 'item' or mutate the collection while iterating)

while (queue.Count > 0) { }            // condition checked BEFORE each pass (0+ times)

do { input = Console.ReadLine(); }
while (input != "quit");               // checked AFTER — body runs at least once: perfect for menus
```

### `break`, `continue`, and loop design

```csharp
foreach (var line in lines)
{
    if (string.IsNullOrWhiteSpace(line)) continue;  // skip to next iteration
    if (line == "END") break;                        // exit the loop entirely
    Process(line);
}
```

:::tip Choosing a loop
`foreach` when touching every element; `for` when you need the index or a stride; `while` for "until some condition changes"; `do-while` for "at least once" (menus, retry prompts). If you find yourself writing `for (int i = 0; ...)` just to read elements, you wanted `foreach`.
:::

### Common pitfalls

```csharp
for (int i = 0; i <= arr.Length; i++)   // ❌ off-by-one: <= visits arr[Length]
while (true) { }                        // fine WITH a break/return inside; infinite otherwise
for (int i = 0; i < n; i--)             // ❌ wrong direction → infinite
```

### Part A — FizzBuzz three ways

The classic: numbers 1–30; multiples of 3 print "Fizz", of 5 "Buzz", of both "FizzBuzz". First the if/else version:

```csharp
for (int i = 1; i <= 30; i++)
{
    if (i % 15 == 0)      Console.WriteLine("FizzBuzz");   // why 15? and why must this check go FIRST?
    else if (i % 3 == 0)  Console.WriteLine("Fizz");
    else if (i % 5 == 0)  Console.WriteLine("Buzz");
    else                  Console.WriteLine(i);
}
```

Now the switch-expression version — tuple pattern flavor:

```csharp
for (int i = 1; i <= 30; i++)
{
    string output = (i % 3, i % 5) switch
    {
        (0, 0) => "FizzBuzz",
        (0, _) => "Fizz",
        (_, 0) => "Buzz",
        _ => i.ToString()
    };
    Console.WriteLine(output);
}
```

Read `(i % 3, i % 5)` as "make a pair of both remainders, then pattern-match the pair." No ordering trap — each case states its shape explicitly. This style scales beautifully to real business rules.

### Part B — a menu-driven number game

```csharp
{
    int secret = rng.Next(1, 101);     // 1..100 inclusive-exclusive upper bound!

    rounds++;
    Console.WriteLine("\nI picked a number 1–100. Guess it!");

}

```

## Main challenge: `RockPaperScissors` with a scoreboard

Build the full game loop: best-of-N rock-paper-scissors against the computer.

### Requirements

1. Ask for the player's name and how many rounds to play (odd number; re-prompt with a do-while until valid).
2. Each round: read `r`/`p`/`s` (reject anything else without consuming the round), computer picks randomly, decide the winner **with one switch expression over a tuple** `(player, computer)` — no if-chains.
3. Track wins/losses/draws; after each round print the running score like `You 2 — 1 CPU (1 draw)`.
4. Stop early when one side mathematically clinches the match (e.g. 2 wins in best-of-3). Announce the final result with a switch expression over the comparison of scores.

:::solution Show solution
```csharp
var rng = new Random();
string[] moves = { "rock", "paper", "scissors" };

Console.Write("Your name: ");
string name = Console.ReadLine() is { Length: > 0 } n ? n : "Player";

int rounds;
do
{
    Console.Write("Best of how many rounds (odd)? ");
} while (!int.TryParse(Console.ReadLine(), out rounds) || rounds < 1 || rounds % 2 == 0);

int toWin = rounds / 2 + 1;
int wins = 0, losses = 0, draws = 0;

while (wins < toWin && losses < toWin)
{
    Console.Write("[r]ock, [p]aper, [s]cissors: ");
    string? key = Console.ReadLine()?.Trim().ToLowerInvariant();
    int player = key switch { "r" => 0, "p" => 1, "s" => 2, _ => -1 };
    if (player == -1) { Console.WriteLine("r, p, or s only."); continue; }

    int cpu = rng.Next(3);
    Console.WriteLine($"You: {moves[player]}  CPU: {moves[cpu]}");

    string outcome = (player, cpu) switch
    {
        var (a, b) when a == b => "draw",
        (0, 2) or (1, 0) or (2, 1) => "win",   // rock>scissors, paper>rock, scissors>paper
        _ => "loss"
    };

    switch (outcome)
    {
        case "win": wins++; Console.WriteLine("You take the round!"); break;
        case "loss": losses++; Console.WriteLine("CPU takes it."); break;
        default: draws++; Console.WriteLine("Draw."); break;
    }
    Console.WriteLine($"{name} {wins} — {losses} CPU ({draws} draw{(draws == 1 ? "" : "s")})\n");
}

string final = wins.CompareTo(losses) switch
{
    > 0 => $"🏆 {name} wins the match!",
    < 0 => "🤖 CPU wins the match!",
    0 => "Somehow a tie?!"
};
Console.WriteLine(final);
```

Highlights: property pattern `is { Length: > 0 } n` gives a non-empty name with binding; the tuple switch encodes the *entire* game rules in three lines; the clinch condition lives in the while condition, not scattered breaks.

## Before the syntax: why methods exist

Imagine you need the same five lines of tax math in eight places in your program. Copy-paste works — until the tax rule changes and you must find and fix all eight copies (and you'll miss one; everyone misses one). A **method** is the cure: write the block *once*, give it a *name*, and call it by name everywhere. One home for the rule, one place to fix it.

But naming reusable code is only half the idea. The deeper half is the **contract**:

> A method's signature is a promise: *"give me these inputs, and I'll give you back this output."*

```
                    ┌───────────────────┐
   inputs go in ──► │     ApplyTax      │ ──► one result comes out
  (parameters)      │  (how? not your   │      (return value)
                    │     problem)      │
                    └───────────────────┘
```

This is the same idea as a math function — f(x) = x². You give x, you get x². You don't ask *how* the squaring happens. You've been using this contract all module: you call `Console.WriteLine(...)` and `int.TryParse(...)` daily without ever reading their insides. That is **abstraction** — the caller thinks about *what*, the method body handles *how* — and writing your own methods means building your own vocabulary that the rest of your program speaks in.

### What actually happens during a call

When the running program hits `ApplyTax(100m)`, five things occur, in order:

1. Execution **pauses** at the call site — the finger remembers where it was.
2. The arguments are **delivered** into the parameters (as *copies* — a big deal, section below).
3. The method body runs in its own **private workspace** — its parameters and local variables live in a fresh "stack frame" that no other code can see.
4. `return` hands back the result and the workspace is **thrown away** — every local in it dies.
5. The finger **comes back** to the call site and continues, with the returned value in hand.

This little lifecycle quietly explains three things that otherwise feel like arbitrary rules:

- **Why locals die at the end of a method** — their workspace is destroyed (the scope rule, later in this lesson).
- **Why parameters are copies by default** — each call gets a fresh workspace; nothing inside it *is* your variable.
- **Why a method can even call itself** (recursion) — each call gets its *own* workspace, so they don't collide.

### Doors in, one door out

Think of the workspace as a room with strict doors:

- **Parameters** are the only doors *in* — a method sees exactly what you hand it, nothing else.
- **The return value** is the one door *out* — one result, back to the caller.
- `ref` and `out` (below) are special service hatches you can install when one door out isn't enough — and because they're unusual, C# makes both sides write the keyword so the hatch is visible in the code.

Hold onto that picture: the entire rest of this lesson — anatomy, overloading, ref/out, tuples, `params` — is just the catalog of door designs.

## Anatomy of a method

```csharp
//  modifiers  return   name       parameters
    static     decimal  ApplyTax(decimal amount, decimal rate = 0.11m)
    {
        return amount * (1 + rate);
    }

// expression-bodied form — same thing, for one-liners:
static decimal ApplyTax2(decimal amount, decimal rate = 0.11m) => amount * (1 + rate);
```

- **Return type** `void` = returns nothing.
- **`static`** = belongs to the type, not an instance (all we need until Module 4).
- **Optional parameters** (`rate = 0.11m`) must come after required ones.
- **Named arguments** at the call site: `ApplyTax(100m, rate: 0.2m)` — great for readability with booleans: `Search(query, ignoreCase: true)`.

### Overloading — same name, matched by shape

Several methods may share one name as long as their **parameter lists differ**. The compiler picks the winner at *compile time* by matching what you pass along **two axes: argument count, then argument types**:

```csharp
static int    Max(int a, int b)        => a > b ? a : b;      // ①
static double Max(double a, double b)  => a > b ? a : b;      // ②
static int    Max(int a, int b, int c) => Max(Max(a, b), c);  // ③
```

| Call | Runs | Matched by |
|------|------|------------|
| `Max(7, 3)` | ① | two arguments, both `int` |
| `Max(1.5, 9.2)` | ② | two arguments, both `double` |
| `Max(4, 8, 2)` | ③ | three arguments — count decides alone |

`Console.WriteLine` has ~18 overloads; that's why it swallows anything. No runtime magic — just shape-matching.

## How arguments travel — predict this before reading on

Don't skim this section. First, commit to an answer:

```csharp
static void Bump(int x)
{
    x = x + 1;
}

int n = 5;
Bump(n);
Console.WriteLine(n);      // ❓ does this print 5 or 6?
```

Most people predict **6**. The answer is **5** — and if that surprises you, you've just found the single most important rule in this lesson:

**Passing a variable hands the method a *copy* of its value. The parameter `x` is a brand-new box.** `Bump` increments its own copy; your `n` never hears about it. Nothing flows back.

:::note The Google Docs analogy
A **normal parameter** is *File → Make a copy*: the method gets its own duplicate document and can scribble anything on it — your original never changes.
A **`ref` parameter** is *Share with edit access*: there is only **one** document; the method edits the very same one you're looking at.
:::

### `ref` — share the original

If you predicted 6 above, your instinct was describing `ref`. Three extra characters on each side make it true:

```csharp
static void Bump(ref int x) { x = x + 1; }

int n = 5;
Bump(ref n);                 // caller must repeat 'ref' — visible mutation is opt-in
Console.WriteLine(n);        // 6 — ONE box, two names (n and x)
```

| Call | How many boxes | Prints |
|------|----------------|--------|
| `Bump(n)` | 2 — `x` is a copy | 5 |
| `Bump(ref n)` | 1 — `x` is another name for `n` | 6 |

Everything about parameter passing is that table. The classic `ref` use case:

```csharp
static void Swap(ref int a, ref int b) => (a, b) = (b, a);
```

### `out` — share a *blank* box the method must fill

`out` is `ref`'s cousin with one twist: the caller hands over an **empty** box, and the method is *required* to fill it before returning — the compiler enforces it:

```csharp
static bool TryDivide(int a, int b, out double result)
{
    if (b == 0) { result = 0; return false; }    // even on failure, the box MUST be filled
    result = (double)a / b;                       // → convention: fill with the type's default
    return true;
}
```

That's why a *failed* `int.TryParse("abc", out int n)` leaves `n == 0`: the box can't stay empty, so it gets the default value (`0` for int, `false` for bool, `null` for reference types — lesson 1's defaults again).

### The TryXxx pattern: two results through two doors

`TryParse` wants to answer two questions at once — *did it work?* and *what's the value?* It delivers them through two separate doors:

```
                     ┌───────────┐
     "42"  ────────► │  TryParse │
                     └─────┬─────┘
     front door: RETURNS bool ────► the if checks THIS
     side door:  fills the out box ────► your variable gets THIS
```

```csharp
if (int.TryParse(input, out int age))     // the if checks the RETURNED bool — never the box
{
    Console.WriteLine($"You are {age}");  // box is trustworthy only inside this branch
}
else
{
    Console.WriteLine("Not a number!");   // box holds junk (0) — we never touch it
}
```

Read it aloud as: *"if parsing succeeded, use the filled box; otherwise ignore it."* Every `TryXxx` method in .NET follows this exact shape.

:::warn Reference types add one twist (deeper point — fine to revisit later)
Arrays and objects are also passed as copies — but what gets copied is the *reference* (the sticker pointing at the object), not the object itself. So a method **can mutate the shared object** you both see, yet still cannot re-point *your variable*:

```csharp
static void Fill(int[] arr) { arr[0] = 99; }         // affects caller's array (shared object)
static void Replace(int[] arr) { arr = new int[5]; } // does NOT affect caller (only the local copy re-pointed)
```
:::

There's also `in` — read-only pass-by-reference, a performance tool for big structs (`static double Distance(in BigStruct p1, in BigStruct p2)`); file it as recognition knowledge for now.

## Returning multiple values: tuples

```csharp
static (int Min, int Max, double Avg) Analyze(int[] data)
{
    int min = data.Min(), max = data.Max();
    return (min, max, data.Average());
}

var stats = Analyze(scores);
Console.WriteLine($"{stats.Min}–{stats.Max}, avg {stats.Avg:F1}");

var (min, max, avg) = Analyze(scores);   // or deconstruct into locals
```

Tuples are the modern answer for "a method with 2–3 results"; `out` remains idiomatic mainly for the `TryXxx` pattern.

```csharp
static int SumAll(params int[] numbers) => numbers.Sum();
SumAll(1, 2, 3);           // caller passes any count
SumAll();                  // even zero
```

## Local functions & scope

Functions can nest inside methods (or below top-level statements) — perfect for helpers that make no sense elsewhere:

```csharp
int[] data = LoadData();
Console.WriteLine(Trimmed().Average());

double[] Trimmed()
{
    // local function: sees enclosing variables ('data'), keeps Program tidy
    return data.OrderBy(x => x).Skip(1).SkipLast(1).Select(x => (double)x).ToArray();
}
```

**Scope rule**: a variable lives from its declaration to the end of its enclosing block `{ }`. Loop variables die with the loop; method parameters die with the call.

:::tip Design guidance (from the .NET design guidelines)
Methods should do one thing; if you struggle to name it without "And", split it. Prefer returning results over mutating parameters. Keep parameter lists ≤ 4 where possible — more usually means a type is hiding in there (Module 4 fixes that).
:::

### Step 4 — a TryXxx of your own

```csharp
static bool TryMedian(int[] values, out double median)

    median = 0;
    if (values.Length == 0) return false;

    int[] sorted = (int[])values.Clone();   // don't mutate the caller's array! (why? lesson 1)
    Array.Sort(sorted);
    int mid = sorted.Length / 2;
    median = sorted.Length % 2 == 1
        ? sorted[mid]
        : (sorted[mid - 1] + sorted[mid]) / 2.0;
    return true;
}
```

```csharp

```

Every piece of this method is a callback to earlier lessons: Clone for reference semantics, `% 2` for parity, `/ 2.0` to defeat integer division.

### Required signatures

```csharp
static double Mean(params double[] values)                       // params: callable as Mean(1, 2, 3)
static (double Min, double Max, double Range) Spread(double[] values)
static bool TryStdDev(double[] values, out double stdDev)        // false when values.Length < 2

static double Percentile(double[] values, double p = 50)         // default = median; p in 0..100
```

### Rules

1. `TryStdDev` uses the sample formula: sqrt of (Σ(x−mean)² / (n−1)). Return false rather than dividing by zero.
2. `Normalize` must demonstrate `ref` semantics for real: it assigns a **new** array to the parameter, and the caller must observe the replacement (prove it by printing the array before/after and also keeping a second variable pointing at the old array to show it unchanged).
3. `Percentile` sorts a **copy** (never mutate input), then uses nearest-rank: index = ceil(p/100 × n) − 1, clamped.
4. Exercise all five from top-level statements with the dataset `{ 4, 8, 15, 16, 23, 42 }` and print results labeled.

:::tip Stuck on Normalize? Map each signature to the box model first
Before writing any code, say out loud for each method: *copy, shared original, or blank box?* — `Mean`/`Spread`/`Percentile` get **copies** of the reference (they may read the array, must not mutate it), `TryStdDev` fills a **blank box** (`out`, so it must assign even on failure), and `Normalize` holds **your actual variable** (`ref`) — which is the only reason it can point it at a brand-new array. If any of those three words feels shaky, reread "How arguments travel" in the Material tab — the challenge is just that table wearing work clothes.
:::

:::solution Show solution
```csharp

Console.WriteLine($"mean       {Mean(data):F2}");
Console.WriteLine($"mean(params) {Mean(1, 2, 3):F2}");

Console.WriteLine($"spread     {min}–{max} (range {range})");

Console.WriteLine($"median     {Percentile(data):F2}");
Console.WriteLine($"p90        {Percentile(data, 90):F2}");

Normalize(ref data);

static double Mean(params double[] values) => values.Sum() / values.Length;

static (double Min, double Max, double Range) Spread(double[] values)
{
    double min = values.Min(), max = values.Max();
    return (min, max, max - min);
}

static bool TryStdDev(double[] values, out double stdDev)
{
    stdDev = 0;
    if (values.Length < 2) return false;
    double mean = Mean(values);
    double sumSq = values.Sum(v => (v - mean) * (v - mean));
    stdDev = Math.Sqrt(sumSq / (values.Length - 1));
    return true;
}

static void Normalize(ref double[] values)
{
    double max = values.Max();
    var scaled = new double[values.Length];
    for (int i = 0; i < values.Length; i++) scaled[i] = values[i] / max;
    values = scaled;                 // re-points the CALLER's variable — only possible via ref
}

static double Percentile(double[] values, double p = 50)
{
    double[] sorted = (double[])values.Clone();
    Array.Sort(sorted);
    int index = (int)Math.Ceiling(p / 100 * sorted.Length) - 1;
    return sorted[Math.Clamp(index, 0, sorted.Length - 1)];
}
```

The Normalize proof is the key insight: `data` now points at a new normalized array, while `before` still sees the untouched original. Without `ref`, the reassignment inside the method would be invisible to the caller.

@QUIZ
? A method reassigns its `int[] arr` parameter to a new array (no ref). What does the caller observe?
- Their variable now points to the new array
* Nothing — only the method's local copy of the reference changed
- A compile error
- The old array is garbage collected immediately
> Parameters are passed by value; for reference types that value is the reference. Re-pointing the copy doesn't touch the caller's variable — that's exactly what `ref` changes.

? What must a method do with an `out` parameter?
- Read it before writing it
* Assign it on every path before returning
- Declare it nullable
- Return it as well
> `out` means "this is an output": definite assignment before return is enforced by the compiler. This powers the TryParse pattern.

? Which call is legal for `static int SumAll(params int[] xs)`?
- SumAll(1, 2, 3) only
- SumAll(new[] {1, 2, 3}) only
* Both of those, and SumAll() with no arguments too
- Neither
> params accepts a comma list, an actual array, or nothing (empty array). C# 13 extended params to spans and other collection types.

? Why prefer returning a tuple over using two out parameters?
- Tuples are faster
* Tuples make the call site cleaner (deconstruction) and compose with var, LINQ, and async, where out cannot
- out is deprecated
- Tuples can hold more than two values but out cannot
> `(min, max) = MinMax(a)` reads better than two out args, and out parameters don't work in async methods or lambdas-as-expressions. TryXxx + out remains the idiom specifically for parse/lookup success flags.

### Error philosophy

A calculator must never crash on user input. Every failure becomes a friendly message: unknown operator, malformed numbers, division by zero. We use `TryXxx` + `out` so the main loop reads as a clean decision tree. (Exceptions exist too — Module 6 — but for *expected* invalid input, Try-methods are the idiomatic tool.)

```csharp
static bool TryEvaluate(string input, out decimal result, out string error)
{
    result = 0; error = "";

    if (!TryTokenize(input, out var t))
    { error = "Expected: <number> <op> <number> (spaces required)"; return false; }

    if (!decimal.TryParse(t.Left, out decimal a) || !decimal.TryParse(t.Right, out decimal b))
    { error = "Both operands must be numbers."; return false; }

    if (t.Op is "/" or "%" && b == 0)
    { error = "Division by zero."; return false; }

    decimal? value = t.Op switch
    {
        "+" => a + b,
        "-" => a - b,
        "*" => a * b,
        "/" => a / b,
        "%" => a % b,
        "^" => (decimal)Math.Pow((double)a, (double)b),
        _ => null
    };

    if (value is null) { error = $"Unknown operator '{t.Op}'."; return false; }
    result = value.Value;
    return true;
}
```

@QUIZ
? Why use TryEvaluate with out parameters instead of throwing exceptions for bad calculator input?
- Exceptions cannot cross method boundaries
* Invalid user input is expected, not exceptional — Try-methods make the failure path a normal, cheap branch
- out is required for decimals
- Exceptions don't carry messages
> Reserve exceptions for unexpected states; for input you *know* will often be wrong, TryXxx keeps control flow clear and avoids exception overhead. (Module 6 goes deep.)

? What does `input is null or "quit"` do?
* Pattern-matches: true when input is null OR equals "quit"
- Compares references only
- Throws if input is null
- Assigns "quit" to input when null
> `is` with constant patterns and `or` combinators reads as English and handles the null case without a separate check.

? In the calculator, why is `decimal` the right operand type?
- It's the fastest numeric type
* Users type base-10 numbers and expect exact base-10 answers like 0.1 + 0.2 = 0.3
- double can't be parsed from strings
- decimal supports more operators
> A calculator's inputs and outputs are decimal text; binary floating point would produce 0.30000000000000004-style surprises. decimal matches user expectations exactly.

? The history list holds "12 + 3 = 15" entries. Which statement is true?
- Strings in the list can be modified in place later
* Each entry is an immutable string; replacing an entry means storing a new string
- The list must be sized in advance
- Strings can't be stored in List
> Strings are immutable reference types: contents never change after creation. Lists grow dynamically — no pre-sizing needed (details next module).
