## Principles are heuristics, not laws

You've been *doing* good design for ten modules. This lesson names the principles, shows their C# faces, and — the part most courses skip — shows what happens when you over-apply them.

## S — Single Responsibility

*A class should have one reason to change.* Your Module 8 `ReportMailer` refactor was SRP in action: fetching, logging, mailing, and scheduling are four reasons to change, so they became four collaborators.

**The C# smell**: a class name containing "Manager"/"Processor"/"Handler" that grows a new method every sprint; constructors with 7 dependencies (Module 8's test-pain signal).
**Over-application**: forty two-line classes where four cohesive ones would do. Responsibility is about *reasons to change*, not line count.

## O — Open/Closed

*Open for extension, closed for modification.* Your Module 4 payroll: adding `Contractor` touched zero existing classes. The C# machinery: abstract members, interfaces, strategy delegates, DI registration.

```csharp
// violates OCP — every new format edits this method:
public decimal Export(string format) => format switch { "csv" => …, "json" => …, };   // grows forever

// honors it — new formats are new classes (your Module 4 exporters):
public string Export(IExporter exporter) => exporter.Export(rows);
```

**Judgment**: a switch over a *closed*, rarely-changing set (weekdays, order states) is fine — patterns with exhaustiveness checking are often *better* than a class explosion. OCP earns its cost when the variation axis is genuinely open (formats, channels, payment providers).

## L — Liskov Substitution

*Subtypes must honor the base's contract.* If code holding a `Shape` breaks when handed your subclass, the hierarchy lies. Classic violation: `Square : Rectangle` where setting Width mutates Height — callers' assumptions shatter.

**The C# face**: overrides must not throw where the base didn't, tighten preconditions, or weaken postconditions. `NotSupportedException` inside an override is LSP screaming — the capability belonged in a separate interface (your Module 4 `IReservable` split was exactly this cure).

## I — Interface Segregation

*Many focused interfaces beat one fat one.* Module 4's payment methods: `IRefundable` separate from `IPaymentMethod` so crypto never lies. **Smell**: implementing an interface with half the methods throwing.

## D — Dependency Inversion

*High-level policy depends on abstractions; details depend on abstractions too.* Modules 8 and 10 were built on this: `CheckoutService` knows `IPaymentGateway`, not Stripe. The direction of the arrow is the point — *business logic imports nothing concrete*.

```
OrderService ──► IPaymentGateway ◄── StripeGateway
   (policy)        (abstraction)        (detail)
```

**Judgment**: inverting *everything* (interfaces for DTOs, for classes with one implementation ever) produces navigational misery — "go to implementation" archaeology. Invert at *volatile seams*: I/O, external services, things you'll fake in tests, things that genuinely vary.

## The quieter principles that do daily work

- **DRY** — but its real name is "don't duplicate *knowledge*". Two identical-looking snippets encoding *different* decisions should stay separate; merging them couples unrelated changes. Duplication is cheaper than the wrong abstraction.
- **YAGNI** — build for today's requirements; speculative flexibility is debt. (TDD's "minimum to pass" is YAGNI operationalized.)
- **Composition over inheritance** — Module 4's warning, now a principle: prefer has-a + interfaces; inherit for true is-a with polymorphism.
- **Law of Demeter** — `order.Customer.Address.City.Length` chains couple you to four shapes. Ask, don't dig: `order.ShippingCity()`. (Records/DTOs are exempt — they're data, not collaborators.)
- **High cohesion, low coupling** — the meta-principle all the above serve: things that change together live together; things that don't, don't touch.

:::tip The review question that beats all acronyms
"When requirement X changes, how many files change, and are they next to each other?" Good architecture makes the common changes local. Every principle above is a tactic for that one outcome.
:::

## Tutorial: refactor a God class, principle by principle

Project `SolidLab`. The patient — a believable mess:

```csharp
public class OrderManager
{
    public string ProcessOrder(List<(string Sku, int Qty, decimal Price)> items,
                               string customerEmail, string paymentType, string cardNumber)
    {
        // validation
        if (items.Count == 0) throw new ArgumentException("empty order");
        if (!customerEmail.Contains('@')) throw new ArgumentException("bad email");

        // pricing w/ discount rules
        decimal total = items.Sum(i => i.Price * i.Qty);
        if (total > 100) total *= 0.95m;
        if (items.Count > 10) total -= 5;

        // payment — grows a case per provider (OCP violation)
        string receipt;
        if (paymentType == "card")
            receipt = $"card-{cardNumber[^4..]}-{Guid.NewGuid():N}";
        else if (paymentType == "transfer")
            receipt = $"tf-{Guid.NewGuid():N}";
        else throw new NotSupportedException(paymentType);

        // persistence + notification, hardwired (DIP violations)
        File.AppendAllText("orders.log", $"{DateTime.Now}: {receipt} {total}\n");
        Console.WriteLine($"EMAIL to {customerEmail}: receipt {receipt}");

        return receipt;
    }
}
```

Write them as comments: SRP (validation+pricing+payment+persistence+notification = five reasons to change), OCP (payment if-chain), DIP (File/Console/DateTime hardwired), and primitive obsession (that tuple + loose strings — a missing `Order` type).

### Step 2 — carve along the responsibilities

```csharp
public record OrderLine(string Sku, int Qty, decimal UnitPrice) { public decimal Total => Qty * UnitPrice; }
public record Order(List<OrderLine> Lines, string CustomerEmail)
{
    public decimal Subtotal => Lines.Sum(l => l.Total);
}

public class OrderValidator
{
    public List<string> Validate(Order order)
    {
        List<string> errors = [];
        if (order.Lines.Count == 0) errors.Add("empty order");
        if (!order.CustomerEmail.Contains('@')) errors.Add("bad email");
        return errors;
    }
}

public class PricingEngine                       // discount rules = ONE home
{
    public decimal FinalTotal(Order order)
    {
        decimal total = order.Subtotal;
        if (total > 100) total *= 0.95m;
        if (order.Lines.Count > 10) total -= 5;
        return total;
    }
}
```


### Step 5 — the coordinator that remains

```csharp
public class OrderProcessor(
    OrderValidator validator,             // concrete: stable, no IO, no need to invert (judgment!)
    PricingEngine pricing,                //         "
    IOrderStore store,                    // inverted: IO
    ICustomerNotifier notifier)           // inverted: IO
{
    public string Process(Order order, IPaymentProvider payment)
    {
        var errors = validator.Validate(order);
        if (errors.Count > 0)
            throw new ArgumentException(string.Join("; ", errors));

        decimal total = pricing.FinalTotal(order);
        string receipt = payment.Charge(total);
        store.Record(receipt, total);
        notifier.Receipt(order.CustomerEmail, receipt);
        return receipt;
    }
}
```

Read the constructor's deliberate asymmetry: validator and pricing are *concrete* — they're pure, stable, and testing them needs no fakes. Only the I/O edges got interfaces. That's DIP with judgment, not religion.

## Why architecture exists

Architecture answers one question: **where does code go, so that change stays cheap?** Two dominant answers in .NET services:

## Answer 1: Clean/Onion layering (dependency rule)

```
┌─────────────────────────────────────┐
│  Api        (endpoints, DTOs)       │ ──┐
├─────────────────────────────────────┤   │ dependencies
│  Application (use cases, interfaces)│ ◄─┤ point INWARD
├─────────────────────────────────────┤   │ only
│  Domain     (entities, rules)       │ ◄─┘
├─────────────────────────────────────┤
│  Infrastructure (EF, SMTP, HTTP)    │ ─── implements Application's interfaces
└─────────────────────────────────────┘
```

- **Domain**: entities, value objects, domain rules. References *nothing*. Your Module 4 Library, Module 9 aggregates.
- **Application**: use cases ("PlaceOrder", "EnrollStudent") orchestrating domain objects; *defines* `IOrderRepository`, `IMailer` — the ports.
- **Infrastructure**: EF DbContext, SMTP, HttpClients — *implements* the ports (the adapters). Depends on Application, never vice versa.
- **Api**: thin HTTP translation (your Module 10 endpoint discipline).

The invariant: **Domain and Application compile without EF, ASP.NET, or any I/O package**. Physically enforced with project references — Architecture you can't violate accidentally beats architecture in a wiki.

```bash
dotnet new classlib -n Shop.Domain
dotnet new classlib -n Shop.Application   # references Domain
dotnet new classlib -n Shop.Infrastructure # references Application
dotnet new web -n Shop.Api                 # references Application + Infrastructure (for DI wiring only)
```

## Answer 2: Vertical slices (feature folders)

Layering groups by *technical role*; slices group by **feature**:

```
Features/
  Products/
    ListProducts.cs      (endpoint + query + DTO in one file)
    CreateProduct.cs
    ProductsMapper.cs
  Enrollments/
    EnrollStudent.cs
    CancelEnrollment.cs
```

Each slice owns its request→handling→response path end to end. The claim: most changes are *feature-shaped* ("add a field to enrollment"), so locality-of-change favors slices — one folder, not four projects. Slices tolerate different rigor per feature: a trivial read can be an inline EF projection; a complex write can grow a full domain model *inside its slice*.

### Choosing (the honest table)

| Force | Favors |
|-------|--------|
| Large team, strict domain, long life | Layers (+ domain modeling) |
| CRUD-heavy service, small team, speed | Slices |
| Complex core + simple edges | Slices outside, clean core inside the complex slices |
| "Where does X go?" debates dominating PRs | You need EITHER, decided and written down |

Both share the non-negotiables: domain logic doesn't import infrastructure; endpoints stay thin; tests target behavior. The rest is layout taste — hold it loosely.

## The patterns that show up at this scale

- **Mediator/handler style** (often via the MediatR library, or plain handler classes + DI): each use case is a class `EnrollStudentHandler.Handle(command)` — uniform shape, easy cross-cutting (logging/validation pipelines around every handler).
- **Domain events** — "EnrollmentCompleted" raised by the domain, handled elsewhere (send email, update stats): decouples side effects from the deciding code. Your Module 5 events, promoted to architecture.
- **Value objects** — small immutable types replacing primitives: `Email`, `Money`, `CourseId` (records/record structs!). They pull validation *into the type system*: an `Email` that exists is valid — no re-checking downstream.
- **Aggregates** (from Module 4/9): one guardian object per consistency boundary; repositories load/save whole aggregates.

:::warn Architecture theater
Five projects, IRepository over IUnitOfWork over DbContext (which already is both), AutoMapper mapping identical shapes, MediatR for a 3-endpoint API — ceremony without forces to justify it. Start simpler than you think you need; add structure when pain, not fashion, demands it. The skill isn't building cathedrals — it's matching structure to forces.
:::

**Domain** (no packages at all):

```csharp
namespace Enroll.Domain;

public record StudentId(Guid Value) { public static StudentId New() => new(Guid.CreateVersion7()); }

public class Course
{
    public Guid Id { get; init; } = Guid.CreateVersion7();
    public required string Title { get; init; }
    public int Capacity { get; init; }
    private readonly List<StudentId> _enrolled = [];
    public IReadOnlyList<StudentId> Enrolled => _enrolled;

    public EnrollmentResult Enroll(StudentId student)
    {
        if (_enrolled.Contains(student)) return EnrollmentResult.AlreadyEnrolled;
        if (_enrolled.Count >= Capacity) return EnrollmentResult.Full;
        _enrolled.Add(student);
        return EnrollmentResult.Enrolled;
    }
}

public enum EnrollmentResult { Enrolled, AlreadyEnrolled, Full }
```

**Application** (defines its port, orchestrates):

```csharp
namespace Enroll.Application;

public interface ICourseRepository
{
    Task<Course?> GetAsync(Guid id, CancellationToken ct);
    Task SaveAsync(Course course, CancellationToken ct);
}

public class EnrollStudentHandler(ICourseRepository courses)
{
    public async Task<EnrollmentResult?> HandleAsync(Guid courseId, StudentId student, CancellationToken ct)
    {
        var course = await courses.GetAsync(courseId, ct);
        if (course is null) return null;

        var result = course.Enroll(student);
        if (result == EnrollmentResult.Enrolled)
            await courses.SaveAsync(course, ct);
        return result;
    }
}
```

**Infrastructure**: an EF (or even in-memory) `CourseRepository : ICourseRepository`. **Api**: one endpoint translating `EnrollmentResult?` to 200/404/409. Wire DI in Program.cs.

Now the payoff experiment: **unit-test the domain rule and the handler** from a test project referencing only Domain+Application — no EF, no ASP.NET, no fakes for the domain test at all. Capacity rules tested in microseconds. *This* is what the layering bought.

```csharp
namespace EnrollSliced.Features.Enrollment;

public static class EnrollStudent
{
    public record Request(Guid StudentId);

    public static void Map(IEndpointRouteBuilder app)
        => app.MapPost("/courses/{courseId:guid}/enrollments",
            async (Guid courseId, Request req, AppDb db, CancellationToken ct) =>
        {
            var course = await db.Courses.Include(c => c.Enrollments)
                .FirstOrDefaultAsync(c => c.Id == courseId, ct);
            if (course is null) return Results.NotFound();

            if (course.Enrollments.Any(e => e.StudentId == req.StudentId))
                return Results.Conflict(new { Error = "already enrolled" });
            if (course.Enrollments.Count >= course.Capacity)
                return Results.Conflict(new { Error = "course full" });

            course.Enrollments.Add(new Enrollment { StudentId = req.StudentId });
            await db.SaveChangesAsync(ct);
            return Results.Created($"/courses/{courseId}/enrollments/{req.StudentId}", null);
        });
}
```

Program.cs just calls `EnrollStudent.Map(app);` per slice. Test it with WebApplicationFactory (Module 10) — the slice is tested *through HTTP*, which is its public contract.

```csharp
// Library.Core — the heart, dependency-free:
public record LoanRequest(bool ItemAvailable, bool ItemReservedByOther,
                          int MemberActiveLoans, int MemberLoanLimit);

public abstract record LoanDecision
{
    public sealed record Approved(int LoanDays) : LoanDecision;
    public sealed record Refused(string Reason) : LoanDecision;
}

public static class LoanPolicy
{
    public static LoanDecision Decide(LoanRequest req, int loanDays) => req switch
    {
        { ItemAvailable: false } => new LoanDecision.Refused("item is on loan"),
        { ItemReservedByOther: true } => new LoanDecision.Refused("item is reserved by another member"),
        { MemberActiveLoans: var n, MemberLoanLimit: var max } when n >= max
            => new LoanDecision.Refused($"member at loan limit ({max})"),
        _ => new LoanDecision.Approved(loanDays)
    };
}
```

```csharp
// Library.Api/Features/Loans/CheckoutLoan.cs — the slice orchestrates:
app.MapPost("/loans", async (CheckoutRequest req, LibraryDb db, TimeProvider clock, CancellationToken ct) =>
{
    var item = await db.Items.FindAsync([req.ItemId], ct);
    if (item is null) return Results.NotFound();

    var facts = new LoanRequest(
        ItemAvailable: item.Status == ItemStatus.Available,
        ItemReservedByOther: item.ReservedFor is not null && item.ReservedFor != req.MemberId,
        MemberActiveLoans: await db.Loans.CountAsync(l => l.MemberId == req.MemberId, ct),
        MemberLoanLimit: await db.Members.Where(m => m.Id == req.MemberId)
                             .Select(m => m.Tier == Tier.Premium ? 7 : 3).FirstAsync(ct));

    switch (LoanPolicy.Decide(facts, item.LoanDays))
    {
        case LoanDecision.Refused r:
            return Results.Conflict(new { Error = r.Reason });
        case LoanDecision.Approved a:
            var due = DateOnly.FromDateTime(clock.GetUtcNow().UtcDateTime).AddDays(a.LoanDays);
            item.Status = ItemStatus.OnLoan;
            item.ReservedFor = null;
            db.Loans.Add(new Loan { ItemId = item.Id, MemberId = req.MemberId, Due = due });
            await db.SaveChangesAsync(ct);
            return Results.Created($"/loans/{item.Id}", new { item.Id, Due = due });
        default: throw new UnreachableException();
    }
});
```

The pattern to study: the slice *gathers facts* (queries), the core *decides* (pure function over a facts record), the slice *applies* the decision (mutations). LoanPolicy tests are trivial theories over LoanRequest — every rule combination in milliseconds, no database, no fakes. The stress question's answer in this structure: a `ReservationAvailable` domain event record raised in the return-item slice, handled by `Features/Notifications/ReservationAvailableHandler.cs` holding the email port — one new file plus one raise-site line, which is exactly the locality the ADR promised.
:::

## Patterns, priced honestly

Design patterns are *named solutions to recurring shapes*. In modern C#, many classics are one lambda long — knowing the *name and when* matters more than UML. Here are the ones .NET code actually uses, with their native C# spellings.

### Strategy — behavior as a parameter

The pattern you've used since Module 5: `Func<T, bool>` predicates, `IComparer<T>`, your exporters. Classic form = interface + implementations chosen at runtime; lambda form = just pass the function. **Use**: swappable algorithms. **C# native**: often just a delegate.

### Factory — creation with a name

```csharp
public static class Notification
{
    public static INotification For(string channel, string to) => channel switch
    {
        "email" => new EmailNotification(to),
        "sms" => new SmsNotification(to),
        _ => throw new ArgumentException($"unknown channel {channel}")
    };
}
```

**Use**: construction needs logic/validation, or callers shouldn't know concrete types. DI containers are industrial-strength factories — `IServiceProvider` + registrations replaced most hand-rolled ones. `Func<T>` injections and `IHttpClientFactory` are factories you already consume.

### Builder — assembling complex objects fluently

```csharp
var host = Host.CreateApplicationBuilder(args);       // you've used builders all along
var request = new OrderBuilder().For("ada").WithLine("kb-1", 2).Express().Build();
```

Each method returns `this` (or a new immutable copy); `Build()` validates completeness. **Use**: many optional parts, readable construction, test-data builders (Module 8 mention). With records + `with`, small builders are often unnecessary — judgment.

### Decorator — wrapping to add behavior

```csharp
public class CachingCatalog(ICatalog inner, IMemoryCache cache) : ICatalog
{
    public async Task<Product?> GetAsync(int id, CancellationToken ct)
        => await cache.GetOrCreateAsync($"product:{id}", _ => inner.GetAsync(id, ct));
}
// registration: services.AddScoped<Catalog>();
//               services.AddScoped<ICatalog>(sp => new CachingCatalog(sp.GetRequiredService<Catalog>(), …));
```

Same interface, wrapped instance, added concern (caching/logging/retry) — callers can't tell. **This is the architecture of ASP.NET middleware and HttpClient handlers** — decorators all the way down. Stream wrapping (Module 6's GZipStream) too.

### Observer — you know it as events

C# events, `IProgress<T>`, domain events, `INotifyPropertyChanged` (XAML binding's engine). **Use**: one-to-many notification without coupling.

### Adapter — translating interfaces

Your Module 8 `ISalesApi` wrapping HttpClient; any wrapper making a third-party API fit *your* port. Infrastructure layers are made of adapters (the clean-architecture name for them).

### Singleton — the lifetime, not the GoF class

The classic double-checked-locking Singleton class is dead in .NET; **DI singleton lifetime** replaced it (testable, no hidden global). `Lazy<T>` covers "expensive, once, on demand".

### Repository & Unit of Work — mostly already inside EF

DbContext *is* a unit of work; DbSet *is* a repository. Wrap them only for: a genuinely swappable persistence boundary (clean core), or repeated query logic wanting a home (query classes). Wrapping "because pattern" duplicates EF's API worse — Module 9's verdict, now with pattern vocabulary.

### Null Object & Result — absence without surprises

`NullLogger.Instance` (a logger that does nothing) beats null checks everywhere. Your `Result<T>`/`LoanDecision` closed hierarchies are the modern Result pattern — failures as data, exhaustively matched.

:::warn Anti-pattern radar
**Service Locator** (`provider.GetService` sprinkled through logic — hides dependencies; constructor injection instead). **God object** (Module 11 opened with one). **Anemic domain + fat services** *when the domain has real rules* (rules belong on the objects that own the data — Module 4's whole thesis). And pattern-fever itself: a pattern unrequested by forces is complexity, not design.
:::

## Tutorial: build a resilient, observable API client — with four patterns

Project `PatternsLab`. We compose Strategy, Decorator, Factory, and Observer into something you'd actually ship: a catalog client with caching, retry, and metrics.

### Step 1 — the port and the real adapter

```csharp
public interface ICatalog
{
    Task<string?> GetProductJsonAsync(int id, CancellationToken ct);
}

public class SlowFlakyCatalog : ICatalog                      // stands in for a real HTTP adapter
{
    public async Task<string?> GetProductJsonAsync(int id, CancellationToken ct)
    {
        await Task.Delay(300, ct);                            // "network"
        if (Random.Shared.Next(4) == 0) throw new HttpRequestException("upstream hiccup");
        return id <= 100 ? $"{{\"id\":{id},\"name\":\"product-{id}\"}}" : null;
    }
}
```

### Step 2 — Decorator #1: retry with pluggable Strategy

```csharp
public delegate TimeSpan BackoffStrategy(int attempt);        // Strategy as a delegate

public static class Backoff
{
    public static BackoffStrategy Fixed(TimeSpan delay) => _ => delay;
    public static BackoffStrategy Exponential(TimeSpan initial)
        => attempt => initial * Math.Pow(2, attempt - 1);
}

public class RetryingCatalog(ICatalog inner, BackoffStrategy backoff, int maxAttempts = 3) : ICatalog
{
    public async Task<string?> GetProductJsonAsync(int id, CancellationToken ct)
    {
        for (int attempt = 1; ; attempt++)
        {
            try { return await inner.GetProductJsonAsync(id, ct); }
            catch (HttpRequestException) when (attempt < maxAttempts)
            {
                await Task.Delay(backoff(attempt), ct);
            }
        }
    }
}
```

### Step 3 — Decorator #2: caching

```csharp
public class CachingCatalog(ICatalog inner) : ICatalog
{
    private readonly Dictionary<int, (string? Json, DateTimeOffset At)> _cache = [];

    public async Task<string?> GetProductJsonAsync(int id, CancellationToken ct)
    {
        if (_cache.TryGetValue(id, out var hit) && DateTimeOffset.UtcNow - hit.At < TimeSpan.FromSeconds(30))
            return hit.Json;

        var json = await inner.GetProductJsonAsync(id, ct);
        _cache[id] = (json, DateTimeOffset.UtcNow);
        return json;
    }
}
```

### Step 4 — Decorator #3: metrics via Observer

```csharp
public class MeteredCatalog(ICatalog inner) : ICatalog
{
    public event Action<int, TimeSpan, bool>? Fetched;         // Observer

    public async Task<string?> GetProductJsonAsync(int id, CancellationToken ct)
    {
        var sw = Stopwatch.StartNew();
        try
        {
            var result = await inner.GetProductJsonAsync(id, ct);
            Fetched?.Invoke(id, sw.Elapsed, true);
            return result;
        }
        catch
        {
            Fetched?.Invoke(id, sw.Elapsed, false);
            throw;
        }
    }
}
```

### Step 5 — Factory assembles the stack

```csharp
public static class CatalogFactory
{
    public static (ICatalog Catalog, MeteredCatalog Meter) CreateProduction()
    {
        var meter = new MeteredCatalog(
            new CachingCatalog(
                new RetryingCatalog(
                    new SlowFlakyCatalog(),
                    Backoff.Exponential(TimeSpan.FromMilliseconds(100)))));
        return (meter, meter);
    }
}
```

Read the nesting inside-out: raw client → retried → cached → metered. **Order is semantics**: cache *outside* retry means hits skip retries entirely; metrics *outside* cache means hits get timed too. Swap the nesting and you get different (also defensible) behavior — say which you want, on purpose.

### Step 6 — drive it and watch the layers work

```csharp
var (catalog, meter) = CatalogFactory.CreateProduction();
var times = new List<(TimeSpan, bool)>();
meter.Fetched += (id, elapsed, ok) => times.Add((elapsed, ok));
meter.Fetched += (id, elapsed, ok) =>
    Console.WriteLine($"  fetch #{id}: {elapsed.TotalMilliseconds,6:F0} ms {(ok ? "✔" : "✘")}");

foreach (int id in (int[])[1, 1, 1, 2, 999, 2])
    Console.WriteLine($"product {id}: {(await catalog.GetProductJsonAsync(id, default))?[..30] ?? "not found"}");

Console.WriteLine($"avg: {times.Average(t => t.Item1.TotalMilliseconds):F0} ms over {times.Count} fetches");
```

Observe: the second and third `1` return in ~0 ms (cache); occasional hiccups never surface (retry absorbed them — visible as slower fetches); every fetch emitted an event consumed by two independent observers. Four patterns, ~100 lines, production shape. This IS how `AddStandardResilienceHandler` and `IMemoryCache` are architected inside.

## Challenge: `PipelineKit` — patterns serving a mini-framework

Build a tiny request-processing framework (a micro-MediatR) — the exercise is choosing and combining patterns *as a framework author*.

### Requirements

1. Core abstraction: `public interface IHandler<TRequest, TResponse> { Task<TResponse> HandleAsync(TRequest request, CancellationToken ct); }`
2. **Decorator chain as middleware**: `LoggingDecorator<TReq,TRes>` (structured line per request with timing), `ValidatingDecorator<TReq,TRes>` (accepts `IEnumerable<Rule<TReq>>` — your Module 5 delegate! — throws `ValidationException` listing failures), `CachingDecorator<TReq,TRes>` (only when TReq is marked with an `ICacheableRequest` interface — key from `request.ToString()`, records make that meaningful).
3. **Builder** to assemble: `Pipeline.For<TReq,TRes>(handler).WithValidation(rules).WithCaching().WithLogging().Build()` — order of calls = order of wrapping; document what order you make outermost and why.
4. **Factory + registry**: `PipelineRegistry` mapping request types to built pipelines; `SendAsync<TRes>(object request)` dispatches (a dictionary of `Type → object` and one cast — this is how mediators actually work).
5. Demo with two request types: `GetProductQuery(int Id) : ICacheableRequest` (handler returns a fake product; prove cache hits skip the handler via a call counter) and `CreateOrderCommand(...)` (validation rules: qty > 0, sku non-empty; prove a bad command throws with both failures listed).
6. Tests: one per decorator, decorators tested in isolation with a stub handler (they're just classes — that's the payoff of the design).

:::solution Show solution (core)
```csharp
public interface IHandler<TReq, TRes> { Task<TRes> HandleAsync(TReq request, CancellationToken ct); }
public interface ICacheableRequest;

public class LoggingDecorator<TReq, TRes>(IHandler<TReq, TRes> inner) : IHandler<TReq, TRes>
{
    public async Task<TRes> HandleAsync(TReq request, CancellationToken ct)
    {
        var sw = Stopwatch.StartNew();
        try
        {
            var result = await inner.HandleAsync(request, ct);
            Console.WriteLine($"[pipe] {typeof(TReq).Name} ok in {sw.ElapsedMilliseconds} ms");
            return result;
        }
        catch (Exception ex)
        {
            Console.WriteLine($"[pipe] {typeof(TReq).Name} FAILED ({ex.GetType().Name}) in {sw.ElapsedMilliseconds} ms");
            throw;
        }
    }
}

public class ValidatingDecorator<TReq, TRes>(IHandler<TReq, TRes> inner, IEnumerable<Rule<TReq>> rules)
    : IHandler<TReq, TRes>
{
    public Task<TRes> HandleAsync(TReq request, CancellationToken ct)
    {
        var failures = rules.Select(r => r(request)).Where(r => !r.Ok).Select(r => r.Error!).ToList();
        return failures.Count > 0
            ? throw new ValidationException(string.Join("; ", failures))
            : inner.HandleAsync(request, ct);
    }
}

public class CachingDecorator<TReq, TRes>(IHandler<TReq, TRes> inner) : IHandler<TReq, TRes>
{
    private readonly Dictionary<string, TRes> _cache = [];

    public async Task<TRes> HandleAsync(TReq request, CancellationToken ct)
    {
        if (request is not ICacheableRequest) return await inner.HandleAsync(request, ct);

        string key = request!.ToString()!;                    // records give value-based ToString
        if (_cache.TryGetValue(key, out var hit)) return hit;
        return _cache[key] = await inner.HandleAsync(request, ct);
    }
}

public class PipelineBuilder<TReq, TRes>(IHandler<TReq, TRes> handler)
{
    private IHandler<TReq, TRes> _current = handler;

    public PipelineBuilder<TReq, TRes> WithValidation(params Rule<TReq>[] rules)
    { _current = new ValidatingDecorator<TReq, TRes>(_current, rules); return this; }

    public PipelineBuilder<TReq, TRes> WithCaching()
    { _current = new CachingDecorator<TReq, TRes>(_current); return this; }

    public PipelineBuilder<TReq, TRes> WithLogging()
    { _current = new LoggingDecorator<TReq, TRes>(_current); return this; }

    public IHandler<TReq, TRes> Build() => _current;
}
// Order note: we call WithValidation FIRST so it wraps CLOSEST to the handler
// (cache must not store unvalidated junk; logging outermost times everything incl. cache hits).

public class PipelineRegistry
{
    private readonly Dictionary<Type, object> _pipelines = [];

    public void Register<TReq, TRes>(IHandler<TReq, TRes> pipeline)
        => _pipelines[typeof(TReq)] = pipeline;

    public Task<TRes> SendAsync<TReq, TRes>(TReq request, CancellationToken ct = default)
        => ((IHandler<TReq, TRes>)_pipelines[typeof(TReq)]).HandleAsync(request, ct);
}
```

```csharp
public record GetProductQuery(int Id) : ICacheableRequest;
public record Product(int Id, string Name);

public class GetProductHandler : IHandler<GetProductQuery, Product>
{
    public int Calls { get; private set; }
    public Task<Product> HandleAsync(GetProductQuery q, CancellationToken ct)
    { Calls++; return Task.FromResult(new Product(q.Id, $"product-{q.Id}")); }
}

var handler = new GetProductHandler();
var registry = new PipelineRegistry();
registry.Register(Pipeline.For<GetProductQuery, Product>(handler).WithCaching().WithLogging().Build());

await registry.SendAsync<GetProductQuery, Product>(new(7));
await registry.SendAsync<GetProductQuery, Product>(new(7));    // cache hit
Console.WriteLine($"handler executed {handler.Calls} time(s)"); // 1 — proven
```

What you just built is structurally MediatR + its pipeline behaviors: uniform handlers, cross-cutting concerns as generic decorators, a registry dispatching by request type. The record-as-cache-key trick (value-based ToString) is why requests-as-records is the ecosystem convention. Framework authorship is pattern fluency — and now the libraries you use are legible from the inside.
:::

@QUIZ
? Decorators and inheritance both add behavior. Decorators win when…
- The class is sealed
* You want to stack concerns at runtime (retry+cache+log in any order) around ANY implementation of the interface
- Performance matters
- The base has virtual methods
> Inheritance fixes the combination at compile time to one base. Decorators compose freely — the design behind middleware, HttpClient handlers, and stream wrapping.

? In a cache+retry decorator stack, putting cache OUTSIDE retry means…
* Cache hits return immediately without ever consulting retry or the source
- Retries are cached
- The cache is retried on failure
- Order doesn't matter
> Nesting order is behavior: outermost runs first. Cache-outside = hits skip everything; retry-outside would retry even cache misses' failures differently. Choose consciously and write it down.

? The GoF Singleton class died in .NET because…
- Static classes replaced it
* DI singleton lifetime gives one-instance semantics without hidden globals, with testability and disposal handled by the container
- It was too slow
- C# forbids private constructors
> Container-managed singletons are injectable (fakeable in tests) and explicit in the composition root. Hand-rolled Instance properties hide the dependency and resist testing.

? Service Locator (calling provider.GetService inside business logic) is an anti-pattern because…
- It's slower than injection
* Dependencies become invisible — constructors lie, tests can't see requirements, and failures move to runtime
- It only works in ASP.NET
- It creates memory leaks
> Constructor injection makes needs explicit and compile-checkable. A locator turns every class into "depends on anything, discover at runtime".

? Wrapping DbContext in IRepository/IUnitOfWork "because pattern" is usually…
- Required by clean architecture
* Redundant ceremony — DbContext already IS both patterns; wrap only for a real swap boundary or shared query homes
- A performance win
- Needed for testing
> Module 9's verdict with pattern vocabulary: EF implements the patterns internally, and SQLite-in-memory makes direct testing cheap. Add layers for forces, not fashion.

## BackgroundService — the long-running loop done right

```csharp
public class QueueWorker(ILogger<QueueWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        logger.LogInformation("worker starting");
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                await ProcessNextBatchAsync(stoppingToken);
                await Task.Delay(TimeSpan.FromSeconds(5), stoppingToken);
            }
            catch (OperationCanceledException) { }                       // shutdown — expected
            catch (Exception ex)
            {
                logger.LogError(ex, "batch failed; continuing");         // one bad batch ≠ dead worker
                await Task.Delay(TimeSpan.FromSeconds(30), stoppingToken);
            }
        }
        logger.LogInformation("worker stopping cleanly");
    }
}
```

The host wires **graceful shutdown**: Ctrl+C / SIGTERM / service-stop cancels `stoppingToken`; your loop drains and exits; the host waits (default 30 s) before force-killing. Every pattern from Module 7 — cooperative cancellation, per-iteration error containment — is exactly what this loop needs.

### Scoped services inside a singleton worker

Hosted services are **singletons** — injecting a scoped DbContext is the Module 10 captive-dependency bug. The pattern:

```csharp
public class CleanupWorker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        while (!ct.IsCancellationRequested)
        {
            using (var scope = scopeFactory.CreateScope())               // one scope per iteration
            {
                var db = scope.ServiceProvider.GetRequiredService<AppDb>();
                int n = await db.Sessions.Where(s => s.Expires < DateTimeOffset.UtcNow)
                                         .ExecuteDeleteAsync(ct);
                if (n > 0) logger.LogInformation("pruned {Count} sessions", n);
            }
            await Task.Delay(TimeSpan.FromMinutes(10), ct);
        }
    }
}
```

One scope per unit of work = fresh context, correct lifetimes, memory bounded. This exact shape runs in every production .NET system you'll touch.

```csharp
public record CheckResult(string Url, bool Up, long Ms, DateTimeOffset At);

public class StatsCollector                                   // singleton — thread-safe by lock
{
    private readonly Lock _lock = new();
```

```csharp
public class ProbeWorker(IHttpClientFactory httpFactory, IOptions<MonitorOptions> options,
                         StatsCollector stats, ILogger<ProbeWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        var client = httpFactory.CreateClient("probe");
        while (!ct.IsCancellationRequested)
        {
            foreach (var url in options.Value.Urls)
            {
                var sw = Stopwatch.StartNew();
                bool up;
                try
                {
                    var response = await client.GetAsync(url, HttpCompletionOption.ResponseHeadersRead, ct);
                    up = response.IsSuccessStatusCode;
                }
                catch (OperationCanceledException) when (ct.IsCancellationRequested) { return; }
                catch (Exception) { up = false; }

                stats.Record(new CheckResult(url, up, sw.ElapsedMilliseconds, DateTimeOffset.UtcNow));
                logger.LogInformation("{Url} {Status} in {Ms} ms", url, up ? "UP" : "DOWN", sw.ElapsedMilliseconds);
            }
            await Task.Delay(TimeSpan.FromSeconds(options.Value.IntervalSeconds), ct);
        }
    }
}
```

## Challenge: `JobRunner` — a queued background job system

The capstone of the module: a web API that accepts jobs and a worker fleet that processes them — the "accept fast, process async" architecture, complete.

### Requirements

1. **Shared core**: `record Job(Guid Id, string Kind, string Payload, DateTimeOffset EnqueuedAt)`; a bounded `Channel<Job>` (capacity 100) via DI; a `JobTracker` singleton (thread-safe) tracking each job's state: Queued → Running → Done/Failed (+ timings, + error message).
2. **API**: `POST /jobs` (kind + payload; 202 Accepted + job id + `Location: /jobs/{id}` — 202 is the semantically correct "accepted for async processing"); `GET /jobs/{id}` (state + timings); `GET /jobs?state=failed` (filtered list); when the channel is full, return 503 + Retry-After (use `Writer.TryWrite` — don't block the endpoint!).
3. **Workers**: TWO instances of `JobWorker` hosted (register AddHostedService twice via distinct classes or a factory); each drains the channel; job kinds: `"sleep"` (payload = ms), `"hash"` (payload = text to SHA256 1000 rounds — CPU-ish), `"flaky"` (30% throw). Failures mark Failed with the message; workers never die.
4. **Scoped correctness**: workers persist finished jobs to SQLite via a scope-per-job (`IServiceScopeFactory`) — the lesson's pattern, applied.
5. **Graceful drain**: on Ctrl+C, workers finish their in-flight job, remaining queued jobs stay Queued (report the count in the shutdown log).
6. Verify with a curl session: enqueue 10 mixed jobs, watch states move, kill mid-run, restart, confirm the persisted Done jobs and the shutdown log.

```csharp
// the worker base
public abstract class JobWorker(Channel<Job> channel, JobTracker tracker,
    IServiceScopeFactory scopes, ILogger logger, string name) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        try
        {
            await foreach (var job in channel.Reader.ReadAllAsync(ct))
            {
                tracker.SetState(job.Id, JobState.Running);
                var sw = Stopwatch.StartNew();
                try
                {
                    await RunJobAsync(job, ct);
                    tracker.Complete(job.Id, sw.Elapsed);

                    using var scope = scopes.CreateScope();                       // scope per job
                    var db = scope.ServiceProvider.GetRequiredService<JobsDb>();
                    db.Add(new CompletedJob(job.Id, job.Kind, sw.ElapsedMilliseconds, DateTimeOffset.UtcNow));
                    await db.SaveChangesAsync(CancellationToken.None);            // finish the write even during shutdown
                }
                catch (OperationCanceledException) when (ct.IsCancellationRequested)
                {
                    tracker.SetState(job.Id, JobState.Queued);                    // hand it back conceptually
                    throw;
                }
                catch (Exception ex)
                {
                    tracker.Fail(job.Id, sw.Elapsed, ex.Message);                 // job fails, worker lives
                }
            }
        }
        catch (OperationCanceledException)
        {
            logger.LogInformation("{Worker} stopping; {Count} jobs remain queued",
                name, tracker.CountIn(JobState.Queued));
        }
    }

    private static async Task RunJobAsync(Job job, CancellationToken ct)
    {
        switch (job.Kind)
        {
            case "sleep":
                await Task.Delay(int.Parse(job.Payload), ct);
                break;
            case "hash":
                await Task.Run(() =>
                {
                    byte[] data = Encoding.UTF8.GetBytes(job.Payload);
                    for (int i = 0; i < 1000; i++) data = SHA256.HashData(data);
                }, ct);
                break;
            case "flaky":
                await Task.Delay(200, ct);
                if (Random.Shared.Next(10) < 3) throw new InvalidOperationException("flaky job flaked");
                break;
            default:
                throw new NotSupportedException($"unknown kind '{job.Kind}'");
        }
    }
}
```

@QUIZ
? The Generic Host gives non-web apps…
- Kestrel and routing
* The same DI, configuration, logging, and lifetime management that ASP.NET Core uses — minus the HTTP parts
- Faster startup
- Automatic containerization
> One application model: WebApplication = Generic Host + Kestrel + middleware. Workers, tools, and services share everything else.

? BackgroundService.ExecuteAsync receives a stoppingToken that fires when…
- An exception occurs
* The host begins shutdown (Ctrl+C, SIGTERM, service stop) — your loop should drain and exit within the grace period
- The service is idle
- Configuration changes
> Graceful shutdown is cooperative (Module 7's model at app scale): the host signals, waits (default 30 s), then force-terminates. Honor the token.

? A hosted service needing a DbContext must…
- Inject it directly; the container allows it
* Create a scope per unit of work via IServiceScopeFactory and resolve the context inside
- Use a singleton context
- Avoid EF entirely
> Hosted services are singletons; DbContext is scoped. Direct injection is the captive-dependency bug. Scope-per-iteration gives fresh, correctly-disposed contexts.

? POST /jobs returning 202 Accepted communicates…
- The job completed successfully
* The request was accepted for asynchronous processing — check the Location URL for progress
- A validation error
- The job was cached
> 202 is the async-work status: accepted, not done. Pair with a status endpoint. Returning 200/201 would promise completion the system hasn't made.

? ValidateOnStart for options moves configuration failures to…
- The first request that uses them
* Application boot — a broken config fails loudly at deploy time instead of at 3 AM under traffic
- Compile time
- The logging pipeline
> Fail-fast beats fail-eventually: a worker that can't have valid options shouldn't start. Startup validation turns config drift into an instantly-visible deploy failure.
