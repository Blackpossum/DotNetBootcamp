## What .NET actually is

**.NET is a free, cross-platform, open-source developer platform** maintained by Microsoft and the .NET Foundation. It is not one thing but a stack of cooperating parts:

| Layer | Name | What it does |
|-------|------|--------------|
| Languages | C#, F#, VB | High-level languages that compile to a common intermediate form |
| Compiler | Roslyn (C#/VB), F# compiler | Compiles source code to **IL** (Intermediate Language) inside assemblies (`.dll`) |
| Runtime | **CLR** (Common Language Runtime) | Loads IL, **JIT-compiles** it to native machine code, manages memory (GC), enforces type safety |
| Base libraries | **BCL** (Base Class Library) | Thousands of built-in types: collections, IO, networking, JSON, LINQ… |
| App frameworks | ASP.NET Core, MAUI, WPF, WinForms | Web APIs, websites, mobile, desktop |
| Tooling | .NET SDK, `dotnet` CLI, NuGet | Build, run, test, package, and share code |

As of 2026 the current release is **.NET 10**, a Long-Term Support (LTS) release shipped in November 2025 and supported until November 2028. It ships with **C# 14**. A new major version ships every November; even-numbered versions are LTS (3 years), odd-numbered are STS (18 months).

:::note One ".NET", many pasts
You will see confusing older names in the wild. **.NET Framework** (4.8) is the legacy Windows-only runtime — maintenance mode only, don't start new projects on it. **.NET Core** (1–3.1) was the cross-platform rewrite; since version 5 it is simply called **.NET**. **Mono/Xamarin** merged into the platform too. When a tutorial says ".NET Core" it usually still applies to modern .NET.
:::

## How your code actually runs

When you build a C# program, this pipeline executes:

1. **Compile time** — Roslyn compiles `.cs` files into an **assembly** (a `.dll` file) containing **IL** (also called MSIL/CIL) plus **metadata** describing every type and member. IL is CPU-independent bytecode.
2. **Startup** — the host (your `.exe` or the `dotnet` command) boots the **CLR**.
3. **JIT compilation** — the first time each method is called, the **RyuJIT** compiler translates its IL into native machine code for your exact CPU. .NET uses **tiered compilation**: methods are first compiled quickly with few optimizations (Tier 0), and hot methods are recompiled with heavy optimizations (Tier 1). **Dynamic PGO** (profile-guided optimization) observes real behavior — which branches are taken, which concrete types show up — and optimizes for it, e.g. devirtualizing interface calls.
4. **Execution with services** — while running, the CLR provides:
   - **Garbage collection (GC)** — automatic memory management. Objects are allocated on a managed heap; the GC frees unreachable ones. It is *generational*: new objects go to Gen 0 (collected cheaply and often); survivors get promoted to Gen 1, then Gen 2; large objects (≥ 85 KB) live in the Large Object Heap.
   - **Type safety & verification** — you cannot read arbitrary memory or misinterpret one type as another (outside `unsafe` code).
   - **Exception handling, threading, reflection, interop** with native code.

```csharp
// This one line of C#...
Console.WriteLine("Hello, .NET 10!");

// ...compiles to IL roughly like this:
// ldstr      "Hello, .NET 10!"
// call       void [System.Console]System.Console::WriteLine(string)
// ret
```

An alternative to JIT is **Native AOT** (ahead-of-time compilation): `dotnet publish` can compile the whole app to a self-contained native executable with no JIT at all — instant startup, small memory, at the cost of no runtime code generation. You'll meet it in the Expert module.

## The SDK vs. the Runtime

- **.NET Runtime** — just enough to *run* apps. What end users need.
- **.NET SDK** — everything to *build* apps: the runtime + compilers + `dotnet` CLI + MSBuild + NuGet. What *you* need.

## Why this matters to you as a learner

Understanding the compilation pipeline is not trivia — it explains real behaviors you'll hit later:

- The first request to a web API is slow (JIT warm-up, tiered compilation).
- A `struct` behaves differently from a `class` (stack/inline storage vs. managed heap + GC).
- `Span<T>` exists to avoid heap allocations the GC would otherwise have to clean up.
- Reflection breaks under Native AOT (there's no JIT to generate code at runtime).

### Step 2 — what the build produces

When this is built (`dotnet build`), the `bin/Debug/net10.0/` folder contains:

| File | Purpose |
|------|---------|
| `MyApp.dll` | Your assembly — IL + metadata. This is your actual program. |
| `MyApp.exe` | A tiny native *host* that boots the CLR and loads the dll (Windows) |
| `MyApp.deps.json` | Dependency graph — which assemblies/NuGet packages are needed |
| `MyApp.runtimeconfig.json` | Which runtime version to use, GC settings, etc. |
| `MyApp.pdb` | Debug symbols mapping IL back to your source lines |

:::tip
Open a `runtimeconfig.json` some day — knobs like `System.GC.Server` (server GC) live there. Everything about how your app runs is inspectable.
:::

### Step 3 — reading IL (conceptually)

Given this method:

```csharp
static int Add(int a, int b) => a + b;
```

the compiler emits this IL:

```
.method private hidebysig static int32 Add(int32 a, int32 b) cil managed
{
    ldarg.0      // push argument 0 onto the evaluation stack
    ldarg.1      // push argument 1
    add          // pop two values, push their sum
    ret          // return top of stack
}
```

IL is a **stack machine**: instructions push and pop an evaluation stack. The JIT maps this to registers on your real CPU. Tools that let you explore this yourself: **ILSpy** (free decompiler), **ildasm** (ships with SDK workloads), and [sharplab.io](https://sharplab.io) in the browser — paste C#, see IL and JIT asm live.

### Step 4 — watch the versions

Every .NET release has three version numbers moving together — know how to read them:

```bash
dotnet --info
```

- **SDK version** e.g. `10.0.301` — the tooling.
- **Runtime version** e.g. `10.0.10` — monthly-patched runtime (second segment ≈ patch month).
- **Language version** — C# 14 is the default for `net10.0` projects; you rarely set it manually.

## The .NET SDK

Everything in modern .NET flows through one installer and one command. The **SDK** gives you:

- `dotnet` CLI — build/run/test/publish from any terminal
- Roslyn compiler + MSBuild build engine
- NuGet client (package manager)
- Project templates (`console`, `web`, `classlib`, `xunit`, …)

|--------|-----------------|-------|
| Winget (Windows) | `winget install Microsoft.DotNet.SDK.10` | Recommended on Windows |

## The `dotnet` CLI — your daily driver

The CLI follows a `dotnet <verb>` grammar. The verbs you will use constantly:

| Command | What it does |
|---------|--------------|
| `dotnet new console -n MyApp` | Scaffold a new console project in folder `MyApp` |
| `dotnet new list` | Show all installed templates |
| `dotnet run` | Build (if needed) and run the project in the current folder |
| `dotnet build` | Compile to `bin/` without running |
| `dotnet test` | Run unit tests |
| `dotnet add package Spectre.Console` | Add a NuGet package reference |
| `dotnet publish -c Release` | Produce deployable output |
| `dotnet clean` | Delete build outputs |

:::tip Debug vs Release
By default everything builds in **Debug** configuration: no optimizations, full debug info. Add `-c Release` for optimized builds — always benchmark and publish in Release.
:::

### File-based apps (new in .NET 10)

.NET 10 lets you run a **single `.cs` file with no project at all**:

```bash
dotnet run app.cs
```

Inside the file you can declare packages and settings with *file-level directives*:

```csharp
#:package Humanizer@2.*

using Humanizer;
Console.WriteLine(DateTime.UtcNow.AddDays(-3).Humanize()); // "3 days ago"
```

This makes C# usable for scripts and tiny experiments — and when the script grows up, `dotnet project convert app.cs` turns it into a full project. There is even `#!/usr/bin/env dotnet` shebang support on Unix.

## NuGet in 60 seconds

**NuGet** is .NET's package registry ([nuget.org](https://www.nuget.org)) — the equivalent of npm/PyPI/crates.io. A package is a `.nupkg` (zip) of assemblies + metadata. Packages are cached globally per user (`~/.nuget/packages`), so 50 projects using the same package share one copy on disk. Dependencies are recorded in your `.csproj` as `<PackageReference>` entries — human-readable, git-friendly XML you'll dissect next lesson.

## The two files that define a project

A minimal console project is just two files. Everything else (`bin/`, `obj/`) is generated.

### 1. The project file — `MyApp.csproj`

```xml
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net10.0</TargetFramework>
    <ImplicitUsings>enable</ImplicitUsings>
    <Nullable>enable</Nullable>
  </PropertyGroup>

</Project>
```

This is **MSBuild** XML, and each piece matters:

- `Sdk="Microsoft.NET.Sdk"` — imports hundreds of build targets so *you* don't write build logic. Web apps use `Microsoft.NET.Sdk.Web`.
- `OutputType` — `Exe` (runnable) vs `Library` (a `.dll` for others to reference).
- `TargetFramework` — the **TFM**. `net10.0` = cross-platform .NET 10. `net10.0-windows` adds Windows-only APIs (WPF/WinForms). You can *multi-target*: `<TargetFrameworks>net8.0;net10.0</TargetFrameworks>`.
- `ImplicitUsings` — auto-imports common namespaces (`System`, `System.Linq`, `System.Collections.Generic`, …) into every file, which is why `Console.WriteLine` works without `using System;`.
- `Nullable` — enables **nullable reference types**, the compiler's null-safety analysis (deep dive in Module 6). Keep it on; every template enables it.

Packages and project references also live here:

```xml
<ItemGroup>
  <PackageReference Include="Spectre.Console" Version="0.49.1" />
  <ProjectReference Include="..\MyLibrary\MyLibrary.csproj" />
</ItemGroup>
```

:::tip The csproj is code
Treat the project file as first-class code you read and edit by hand. Modern csproj is small and clean — no GUIDs, no file lists (all `.cs` files in the folder are compiled automatically).
:::

### 2. The program — `Program.cs`

Since C# 9, **top-level statements** let the template be one line:

```csharp
Console.WriteLine("Hello, World!");
```

The compiler wraps this in a class and a `Main` method for you. The explicit equivalent — which you should recognize because tons of real code still uses it — is:

```csharp
namespace HelloBootcamp;

internal class Program
{
    static void Main(string[] args)
    {
        Console.WriteLine("Hello, World!");
    }
}
```

Rules for top-level statements: only **one file** per project may have them; they can use `args` directly; they can `return int;` for an exit code; methods declared below the statements become local functions.

## The build pipeline & output folders

```
dotnet build
   │  restore  → resolve NuGet packages (obj/project.assets.json)
   │  compile  → Roslyn: .cs → obj/Debug/net10.0/MyApp.dll
   │  copy     → bin/Debug/net10.0/  (dll + host exe + deps.json + runtimeconfig.json)
```

- `obj/` — intermediate scratch space. Never commit it.
- `bin/` — final outputs. Never commit it either. (A proper `.gitignore` for .NET: `dotnet new gitignore`.)

### Publishing — making deployable output

`dotnet publish -c Release` assembles a self-sufficient folder. Big choices:

| Mode | Flag | Result |
|------|------|--------|
| Framework-dependent | (default) | Small output; target machine needs the runtime installed |
| Self-contained | `--self-contained` | Bundles the whole runtime (~70 MB); target needs nothing |
| Single file | `-p:PublishSingleFile=true` | Everything in one exe |
| Trimmed | `-p:PublishTrimmed=true` | Removes unused code (needs care with reflection) |
| Native AOT | `-p:PublishAot=true` | Compiles to native code — fastest startup (Expert module) |

## Solutions: many projects together

Real systems split into multiple projects (app + class libraries + test projects) grouped in a **solution** file:

```bash
dotnet new sln -n Shop
dotnet new console -n Shop.Cli
dotnet new classlib -n Shop.Core
dotnet sln add Shop.Cli Shop.Core
dotnet add Shop.Cli reference Shop.Core
dotnet build          # builds everything in dependency order
```

.NET 10 supports the new **`.slnx`** XML solution format (`dotnet new sln --format slnx`) — cleaner than the legacy `.sln` text format, and `dotnet sln migrate` converts old ones.

public static class Temperature
{
    public static double CelsiusToFahrenheit(double c) => c * 9 / 5 + 32;

if (args.Length != 2 || !double.TryParse(args[1], out double value))

    return 1;
}

{

    _ => null

## Debugging: stop guessing, start looking

The debugger is the single biggest upgrade to your learning speed. Core vocabulary:

- **Breakpoint** (F9) — pause execution at a line.
- **Step over / into / out** (F10 / F11 / Shift+F11) — advance line by line; *into* descends into method calls.
- **Locals / Watch** — inspect any variable's current state; expand objects to see fields.
- **Call stack** — the chain of method calls that got you here. Reading stacks is a superpower — it's the same skill as reading exception stack traces.
- **Conditional breakpoints** — right-click a breakpoint → condition like `i == 47` to stop only when it matters.
- **Debug Console** — evaluate expressions against the paused program, e.g. type `name.Length`.

:::tip Debug your understanding
Whenever a lesson's code surprises you, don't reread it — *step through it*. Watching values change line by line converts theory into intuition faster than anything else in this course.
::: 

## Fast feedback loops

### `dotnet watch` + Hot Reload

```bash
dotnet watch
```

Watches your files; on save it applies **Hot Reload** — patching the *running* process without restart when possible (method bodies), falling back to rebuild+restart for structural changes (new types/members). Brilliant with web apps where restarts lose state.

### Code style & analyzers

The compiler ships with hundreds of **analyzers** — rules that flag issues as you type (`CAxxxx` design rules, `IDExxxx` style rules, `CSxxxx` compiler errors). Fix formatting for a whole repo with:

```bash
dotnet format
```

Team conventions live in an **`.editorconfig`** file (indentation, naming rules, which diagnostics are errors vs suggestions) — checked into git so every editor agrees.

## Challenge: the debugging kata

Below is a small program with **three** distinct bugs. Your job is to find them *with the debugger* — not by staring. Create a console project `BuggyStats`, paste the program, and hunt.

```csharp
// Computes min, max and average of scores — supposedly.
int[] scores = { 87, 42, 95, 61, 73, 58, 99, 34 };

int min = 0;                       
int max = 0;
int sum = 0;

for (int i = 1; i < scores.Length; i++)   
{
    if (scores[i] < min) min = scores[i];
    if (scores[i] > max) max = scores[i];
    sum += scores[i];
}

double average = sum / scores.Length;     

Console.WriteLine($"Min: {min}  Max: {max}  Avg: {average:F1}");
```

Expected output: `Min: 34  Max: 99  Avg: 68.6` — but it prints `Min: 0  Max: 99  Avg: 57.0`.

### Hints (use only if stuck)

- Put a breakpoint in the loop; watch `min` — why does it never change?
- Watch `i` on the first iteration. Which element is never visited?
- When the loop is fixed, `average` still ends in `.0` — inspect the *types* of `sum` and `scores.Length` at the division line.

:::solution Show the three bugs
1. **`min` starts at 0** — no score is below 0, so it never updates. Initialize `min` (and `max`) to `scores[0]`, or to `int.MaxValue`/`int.MinValue`.
2. **Loop starts at `i = 1`** — element `[0]` (87) is skipped, corrupting the sum. Start at 0 (fine when min/max start at `scores[0]` — the first comparisons are just no-ops).
3. **Integer division** — `sum / scores.Length` is `int / int`, which truncates *before* the assignment to double. Cast one side: `(double)sum / scores.Length`.

Fixed program:

```csharp
int[] scores = { 87, 42, 95, 61, 73, 58, 99, 34 };

int min = scores[0];
int max = scores[0];
int sum = 0;

for (int i = 0; i < scores.Length; i++)
{
    if (scores[i] < min) min = scores[i];
    if (scores[i] > max) max = scores[i];
    sum += scores[i];
}

double average = (double)sum / scores.Length;

Console.WriteLine($"Min: {min}  Max: {max}  Avg: {average:F1}");
```

Integer division truncation is one of the most common bugs in all of programming — you'll be quizzed on it again in Module 2.
:::
