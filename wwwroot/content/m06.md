## The mechanics

An exception is an object (deriving from `System.Exception`) that **unwinds the call stack** until a matching `catch` is found — or crashes the process:

```csharp
try
{
    var config = File.ReadAllText("config.json");
    var port = int.Parse(cfgValue);
}
catch (FileNotFoundException ex)                 // most specific first!
{
    Console.WriteLine($"No config at {ex.FileName}; using defaults.");
}
catch (FormatException)
{
    Console.WriteLine("Config port isn't a number.");
}
catch (Exception ex) when (ex.Message.Contains("weird"))   // exception FILTER
{
    // 'when' filters without catching-and-rethrowing
}
finally
{
    // ALWAYS runs — exception or not, return or not. Cleanup lives here.
}
```

Catch order matters: the first assignable catch wins, so specific types precede general ones (the compiler enforces it). The exception object carries `Message`, `StackTrace`, and often extras (`FileName`, `ParamName`, `InnerException` — the original cause when exceptions wrap exceptions).

## Throwing well

```csharp
public void Withdraw(decimal amount)
{
    // Guard clauses with modern helpers:
    ArgumentOutOfRangeException.ThrowIfNegativeOrZero(amount);
    if (amount > Balance)
        throw new InvalidOperationException($"Insufficient funds: balance {Balance:C}, requested {amount:C}");
    …
}
```

The BCL's standard vocabulary — use these before inventing your own:

| Exception | Means |
|-----------|-------|
| `ArgumentException` / `ArgumentNullException` / `ArgumentOutOfRangeException` | Caller passed garbage (all have `ThrowIf…` static helpers now) |
| `InvalidOperationException` | Object is in the wrong state for this call |
| `NotSupportedException` | This operation will never work here |
| `KeyNotFoundException`, `FileNotFoundException`, `TimeoutException` | Self-explanatory |

**Custom exceptions** when callers need to catch *your* failure distinctly:

```csharp
public class InsufficientFundsException(decimal balance, decimal requested)
    : Exception($"Insufficient funds: have {balance:C}, need {requested:C}")
{
    public decimal Balance { get; } = balance;
    public decimal Requested { get; } = requested;
}
```

Convention: name ends in `Exception`, derive from `Exception`, carry structured data as properties.

## Rethrowing — the rule that separates professionals

```csharp
catch (Exception ex)
{
    _logger.Log(ex);
    throw;                    // ✅ rethrow preserving the ORIGINAL stack trace
    // throw ex;              // ❌ RESETS the stack trace — evidence destroyed!
}
```

And wrapping with context:

```csharp
catch (SqlException ex)
{
    throw new OrderProcessingException($"Failed saving order {order.Id}", innerException: ex);
}
```

The inner exception keeps the root cause; the outer adds domain context. Log viewers show both.

## Strategy: when to catch, when to let fly

- **Catch only what you can handle.** "Handle" means: recover, retry, substitute a default, or translate to a user-facing outcome. Log-and-rethrow at boundaries; never swallow.
- **`catch (Exception) { }` (empty) is the cardinal sin** — failures vanish, corruption spreads silently.
- **Expected conditions aren't exceptions**: use `TryParse`/`TryGetValue` for input you *know* is often invalid (you've done this since Module 2). Exceptions cost ~microseconds *when thrown* (stack capture); fine for exceptional paths, wrong for control flow in loops.
- Central handling: top-level catch in `Main`, middleware in ASP.NET Core (Module 10) — one place where unexpected exceptions become logs + clean error responses.

:::note Where exceptions shine vs Result types
The Result&lt;T&gt; you built in Module 5 and exceptions are complementary. Result for *expected, local* failure (parse, lookup, validation); exceptions for *unexpected or cross-cutting* failure (IO died, invariant broken, bug detected). Codebases that pick one religion for everything fight the language.
:::

## Tutorial: harden a fragile importer

Project `Importer`. Start broken-by-design, harden step by step.

### Step 1 — the fragile version

```csharp
string[] rows =
[
    "Ada,ada@ex.com,1985",
    "Grace,grace@ex.com,not-a-year",
    "",
    "Linus,linus@ex.com,1969",
    "MalformedRowWithoutCommas",
];

foreach (var row in rows)
{
    var parts = row.Split(',');
    Console.WriteLine($"{parts[0]} born {int.Parse(parts[2])}");   // 💥 twice!
}
```

Run it: `FormatException` on row 2 kills the entire import — rows 3–5 never processed. Read the stack trace top to bottom: exception type, message, then frames from throw-site down to Main.

### Step 2 — quarantine per row

```csharp
var imported = new List<(string Name, string Email, int Year)>();
var rejects = new List<(string Row, string Reason)>();

foreach (var row in rows)
{
    try
    {
        if (string.IsNullOrWhiteSpace(row))
            throw new FormatException("blank row");

        var parts = row.Split(',');
        if (parts.Length != 3)
            throw new FormatException($"expected 3 fields, got {parts.Length}");

        imported.Add((parts[0], parts[1], int.Parse(parts[2])));
    }
    catch (FormatException ex)
    {
        rejects.Add((row, ex.Message));
    }
}

Console.WriteLine($"imported {imported.Count}, rejected {rejects.Count}:");
foreach (var (row, reason) in rejects)
    Console.WriteLine($"   \"{row[..Math.Min(20, row.Length)]}\" → {reason}");
```

One bad row no longer poisons the batch — the failure *boundary* is the row. Deciding where boundaries go is 80% of exception design.

### Step 3 — a custom exception carrying evidence

```csharp
public class ImportException(int rowNumber, string raw, string reason)
    : Exception($"Row {rowNumber}: {reason}")
{
    public int RowNumber { get; } = rowNumber;
    public string Raw { get; } = raw;
}
```

Refactor parsing into `static (string, string, int) ParseRow(string row, int number)` that throws `ImportException` with row context; the catch block now logs `ex.RowNumber` — structured data beats string-mangling the message.

### Step 4 — wrap-and-rethrow with InnerException

```csharp
static int ParseYear(string field, int rowNumber, string raw)
{
    try
    {
        return int.Parse(field);
    }
    catch (FormatException inner)
    {
        throw new ImportException(rowNumber, raw, $"'{field}' is not a year")
        { /* pass inner via a constructor overload in your version */ };
    }
}
```

Extend `ImportException` with an `Exception? inner` parameter chained to `base(message, inner)`. Print `ex.InnerException?.GetType().Name` in the handler — you see both layers: domain context outside, root cause inside.

### Step 5 — finally & the top-level net

```csharp
try
{
    RunImport(rows);
}
catch (Exception ex)                                   // last-resort net: log, exit non-zero
{
    Console.Error.WriteLine($"FATAL: {ex}");           // ex.ToString() = type + message + stack + inners
    Environment.Exit(1);
}
finally
{
    Console.WriteLine("import attempt finished (finally always runs)");
}
```

`Console.Error` for diagnostics, exit code for scripts/CI — good CLI citizenship.

## Challenge: a resilient banking core

Build `Bank` with correct exception design — the point is choosing failure *modes*, not just try/catch syntax.

### Requirements

1. `Account` (from Module 4 spirit): `Deposit` throws `ArgumentOutOfRangeException` on ≤ 0 (use `ThrowIfNegativeOrZero`); `Withdraw` throws custom `InsufficientFundsException(balance, requested)` carrying both values as properties.
2. `Bank.Transfer(from, to, amount)` must be **atomic**: withdraw then deposit, but if the deposit throws (simulate: a `FrozenAccountException` on a frozen target account), the withdrawal must be compensated (redeposit) before wrapping and rethrowing as `TransferFailedException` with the original as `InnerException`.
3. A processing loop over a batch of transfers: catches `InsufficientFundsException` (print shortfall from properties — no message parsing), `TransferFailedException` (print its inner exception's type), lets anything else propagate to a top-level handler that prints `ex.ToString()` and exits 1.
4. Prove with output: successful transfer, insufficient funds (balance intact after!), transfer to a frozen account (sender's balance restored — print before/after to prove the compensation ran).
5. Every custom exception ends in `Exception`, has structured properties, and at least one is thrown with `throw;` rethrow semantics somewhere in your code path (e.g. logging layer).

:::solution Show solution
```csharp
public class InsufficientFundsException(decimal balance, decimal requested)
    : Exception($"Insufficient funds: have {balance:C}, need {requested:C}")
{
    public decimal Balance { get; } = balance;
    public decimal Requested { get; } = requested;
    public decimal Shortfall => Requested - Balance;
}

public class FrozenAccountException(string accountId)
    : Exception($"Account {accountId} is frozen")
{
    public string AccountId { get; } = accountId;
}

public class TransferFailedException(string fromId, string toId, decimal amount, Exception inner)
    : Exception($"Transfer of {amount:C} from {fromId} to {toId} failed", inner);

public class Account(string id, decimal opening = 0)
{
    public string Id { get; } = id;
    public decimal Balance { get; private set; } = opening;
    public bool Frozen { get; set; }

    public void Deposit(decimal amount)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(amount);
        if (Frozen) throw new FrozenAccountException(Id);
        Balance += amount;
    }

    public void Withdraw(decimal amount)
    {
        ArgumentOutOfRangeException.ThrowIfNegativeOrZero(amount);
        if (amount > Balance) throw new InsufficientFundsException(Balance, amount);
        Balance -= amount;
    }
}

public class Bank
{
    public void Transfer(Account from, Account to, decimal amount)
    {
        from.Withdraw(amount);
        try
        {
            to.Deposit(amount);
        }
        catch (Exception ex)
        {
            from.Deposit(amount);                     // COMPENSATE before surfacing
            throw new TransferFailedException(from.Id, to.Id, amount, ex);
        }
    }
}
```

```csharp
var bank = new Bank();
var ada = new Account("ada", 100m);
var grace = new Account("grace", 50m);
var frozen = new Account("frozen", 0m) { Frozen = true };

var jobs = new (Account From, Account To, decimal Amount)[]
{
    (ada, grace, 30m),          // fine
    (grace, ada, 500m),         // insufficient
    (ada, frozen, 40m),         // frozen target → compensation
};

try
{
    foreach (var (from, to, amount) in jobs)
    {
        decimal before = from.Balance;
        try
        {
            bank.Transfer(from, to, amount);
            Console.WriteLine($"✔ {from.Id} → {to.Id} {amount:C}");
        }
        catch (InsufficientFundsException ex)
        {
            Console.WriteLine($"✘ {from.Id}: short by {ex.Shortfall:C} (balance intact: {from.Balance:C})");
        }
        catch (TransferFailedException ex)
        {
            Console.WriteLine($"✘ transfer failed ({ex.InnerException!.GetType().Name}); " +
                              $"{from.Id} balance {before:C} → {from.Balance:C} (compensated)");
        }
    }
}
catch (Exception ex)
{
    Console.Error.WriteLine($"FATAL:\n{ex}");
    Environment.Exit(1);
}
```

Output proves: grace still has 80 after the refused 500 (Withdraw threw before mutating), and ada's balance returns to its pre-transfer value after the frozen bounce. The compensation-in-catch pattern is a baby saga — the same shape used across microservices (Module 12).
:::

@CHECKS
- Insufficient withdrawal leaves the balance untouched (throw before mutate)
- Frozen-target transfer restores the sender's balance and wraps the cause as InnerException
- Handlers read structured properties (Shortfall), never parse messages
- Unknown exceptions reach the top-level net and exit non-zero

## The problem and the system

`NullReferenceException` (NRE) is historically .NET's most common crash. Since C# 8, projects enable **nullable reference types** (every template does):

```xml
<Nullable>enable</Nullable>
```

Under this regime the *type system* distinguishes:

```csharp
string name = null;      // ⚠ CS8600 warning — string promises "never null"
string? maybe = null;    // ✅ string? declares "null is a legal value here"
```

The compiler then **flow-analyzes** every use:

```csharp
string? input = Console.ReadLine();

int len = input.Length;              // ⚠ CS8602: possible null dereference

if (input is not null)
    len = input.Length;              // ✅ compiler tracked the check — no warning

len = (input ?? "").Length;          // ✅ null handled
len = input?.Length ?? 0;            // ✅ the ?. / ?? toolkit from Module 2
```

This is *static analysis*, not runtime enforcement: nullability annotations compile away (mostly to attributes). The value is in the warnings — treat them as errors in spirit (many teams literally do: `<WarningsAsErrors>nullable</WarningsAsErrors>`).

## The operators & their exact meanings

```csharp
x?.M()        // null-conditional: skip call, produce null, when x is null
x ?? y        // null-coalescing: x unless it's null, then y
x ??= y       // assign y only if x is null
x!            // null-forgiving: "compiler, trust me, it's not null here"
x?.P = v      // C# 14: assign only when x isn't null
```

`!` deserves respect: it silences the warning **without any runtime check**. Legitimate uses exist (after an `Any()` guard the compiler can't see; test setup), but every `!` is a place where a human overrode the analysis — audit them. If you're sprinkling `!` routinely, the design is fighting the type system.

## Designing APIs with nullability

Signatures become documentation the compiler enforces:

```csharp
public Customer? FindByEmail(string email);     // "may not find one" — callers MUST handle null
public Customer GetByEmail(string email);       // "always returns, throws if missing"

public void Send(string to, string? cc = null); // cc is genuinely optional
```

Patterns for fields and properties:

```csharp
public class Profile
{
    public required string Email { get; init; }       // 'required' kills the "uninitialized non-null" problem
    public string? Bio { get; set; }                  // honestly optional
    public List<string> Tags { get; init; } = [];     // prefer empty collections over null ones — ALWAYS
}
```

:::tip Null vs empty
Return empty strings/collections rather than null when "nothing" isn't distinct from "none". `foreach` over an empty list just works; over null it crashes. Reserve `?` for cases where absence *means something different* from empty.
:::

### Helpful analysis attributes (recognition level)

`[NotNullWhen(true)]` — "when I return true, the out param isn't null" (how `TryParse` patterns stay warning-free); `[MemberNotNull(nameof(_field))]` — "this method initializes that field". You'll mostly consume these from the BCL, occasionally write them in libraries.

## `Nullable<T>` for value types is different machinery

`int?` is `Nullable<int>` — a real struct with `HasValue`/`Value` (value types can't be null natively). Same operators work (`??`, `?.`, patterns), plus:

```csharp
int? maybe = TryComputeScore();
if (maybe is int score) { … }        // pattern unwraps HasValue+Value in one move
```

Reference nullability (`string?`) is annotations + analysis; value nullability (`int?`) is an actual wrapper struct. Syntax converges; mechanics differ.

Project `NullSafety`. Paste this deliberately warning-riddled program and drive warnings to zero *properly* (no `!` unless justified in a comment):

```csharp
#nullable enable

var db = new UserDb();

Console.Write("email: ");
string email = Console.ReadLine();                       // ⚠ ReadLine returns string?

var user = db.FindByEmail(email);
Console.WriteLine($"Hello {user.Name.ToUpper()}");        // ⚠ user may be null

public class UserDb
{
    private readonly List<User> _users =
    [
        new() { Name = "Ada", Email = "ada@ex.com", Address = new() { City = " London " } },
        new() { Name = "Linus", Email = "linus@ex.com" },

    public User FindByEmail(string email)
        => _users.FirstOrDefault(u => u.Email == email);  // ⚠ FirstOrDefault returns User?
}

public class User
{
    public string Name { get; set; }                      // ⚠ non-null without initializer
    public string Email { get; set; }
    public Address Address { get; set; }                  // ⚠ same — but is it REQUIRED or OPTIONAL?
}

public class Address
{
```

### Step 1 — read every warning first

`dotnet build` and list them. Each CS8xxx is a *design question*: is this thing optional, or guaranteed? Fixing warnings = answering questions, not silencing noise.

### Step 2 — fix the model with intent

```csharp
public class User
{
    public required string Name { get; set; }
    public required string Email { get; set; }
    public Address? Address { get; set; }          // decision: address IS optional in our domain
}

public class Address
{
    public required string City { get; set; }
}
```

`required` = "constructor-time guarantee, no null ever"; `?` = "legitimately absent sometimes". Every property got a *decision*, not a suppression.

### Step 3 — fix the API signature

```csharp
public User? FindByEmail(string? email)
    => string.IsNullOrWhiteSpace(email)
        ? null
        : _users.FirstOrDefault(u => u.Email.Equals(email, StringComparison.OrdinalIgnoreCase));
```

The signature now tells the truth: input might be null (ReadLine!), output might be absent.

### Step 4 — fix the consuming flow

```csharp
string? email = Console.ReadLine();

if (db.FindByEmail(email) is not { } user)
{
    Console.WriteLine("No such user.");
    return;
}

Console.WriteLine($"Hello {user.Name.ToUpper()}");        // no warning: flow knows user isn't null

string city = user.Address?.City ?? "(no address on file)";
Console.WriteLine($"City: {city.Trim()}");
```

Zero warnings, zero `!`, and — run it with a missing email — zero crashes. The type system just walked you through every absence case in the program.

### Step 5 — meet TryGet-style attributes

```csharp
using System.Diagnostics.CodeAnalysis;

public bool TryFind(string? email, [NotNullWhen(true)] out User? user)
{
    user = FindByEmail(email);
    return user is not null;
}
```

```csharp
if (db.TryFind(email, out var u))
    Console.WriteLine(u.Name);          // no warning INSIDE the true-branch — the attribute taught the compiler
```

## Challenge: null-audit a mini contact book

Design a contact book where every nullability decision is deliberate, then prove the design prevents crashes.

### Requirements

1. Model: `Contact` — required `Name`, required `Email`, optional `Phone`, optional `Company`; `Company` is a type with required `Name`, optional `Website`. Collections (e.g. `List<string> Tags`) are never null — empty instead.
2. `ContactBook`:
   - `Contact? Find(string? query)` (null/blank query → null; search name OR email, case-insensitive)
   - `Contact GetRequired(string query)` — throws `KeyNotFoundException` when absent (document why this exists alongside Find: caller chooses their failure mode)
   - `bool TryFind(string? query, [NotNullWhen(true)] out Contact? contact)`
   - `IEnumerable<string> Websites()` — all non-null company websites, no nulls in the output (`OfType<string>()` or `Where(w => w is not null)` + `!` with justification, or pattern-based `Select`)
3. Demo flow that: looks up an existing and a missing contact via all three APIs; prints `contact.Company?.Website ?? "-"` chains; and formats a display line where Phone shows as "n/a" when absent.
4. Constraints: zero build warnings; at most one `!` in the whole file, with a comment defending it (or zero).

:::solution Show solution
```csharp
using System.Diagnostics.CodeAnalysis;

public class Company
{
    public required string Name { get; init; }
    public string? Website { get; init; }
}

public class Contact
{
    public required string Name { get; init; }
    public required string Email { get; init; }
    public string? Phone { get; init; }
    public Company? Company { get; init; }
    public List<string> Tags { get; init; } = [];

    public string Display()
        => $"{Name,-10} {Email,-18} ☎ {Phone ?? "n/a",-12} 🏢 {Company?.Name ?? "-"}";
}

public class ContactBook
{
    private readonly List<Contact> _contacts = [];

    public void Add(Contact c) => _contacts.Add(c);

    public Contact? Find(string? query)
    {
        if (string.IsNullOrWhiteSpace(query)) return null;
        return _contacts.FirstOrDefault(c =>
            c.Name.Contains(query, StringComparison.OrdinalIgnoreCase) ||
            c.Email.Contains(query, StringComparison.OrdinalIgnoreCase));
    }

    // Exists so callers who consider absence a BUG fail fast with a clear error,
    // instead of null-checking at every call site.
    public Contact GetRequired(string query)
        => Find(query) ?? throw new KeyNotFoundException($"No contact matches '{query}'");

    public bool TryFind(string? query, [NotNullWhen(true)] out Contact? contact)
    {
        contact = Find(query);
        return contact is not null;
    }

    public IEnumerable<string> Websites()
        => _contacts.Select(c => c.Company?.Website).OfType<string>();
}
```

```csharp
var book = new ContactBook();
book.Add(new Contact
{
    Name = "Ada", Email = "ada@ex.com", Phone = "+44 1815",
    Company = new Company { Name = "Analytical Engines", Website = "https://ae.example" }
});
book.Add(new Contact { Name = "Grace", Email = "grace@ex.com" });

foreach (var c in new[] { "ada", "nobody" })
{
    if (book.TryFind(c, out var hit))
        Console.WriteLine(hit.Display());                       // no warning: NotNullWhen(true)
    else
        Console.WriteLine($"'{c}' not found");
}

Console.WriteLine(book.Find("grace")?.Company?.Website ?? "-"); // chained absence: prints -

try { book.GetRequired("nobody"); }
catch (KeyNotFoundException ex) { Console.WriteLine($"expected: {ex.Message}"); }

Console.WriteLine($"websites: {string.Join(", ", book.Websites())}");
```

Notable: `Find(...) ?? throw ...` — throw is an expression, composing with ??. `Select(...).OfType<string>()` filters nulls *and* converts `string?` → `string` in one step, keeping the signature honest with zero `!`. Three lookup APIs = three failure modes, chosen by the caller: null, exception, or bool+out.
:::

@CHECKS
- Zero nullable warnings and ≤ 1 justified `!`
- Find/GetRequired/TryFind offer null, throw, and bool failure modes respectively
- Websites() returns IEnumerable&lt;string&gt; (not string?) with no null elements
- Tags demonstrates empty-not-null collection design

@QUIZ

- A runtime check
* A compile-time warning from flow analysis — nothing changes at runtime
- An automatic null substitution
- An exception at assignment

- Inserts a runtime null check that throws early

## The real tier: streams

A **Stream** is an abstract sequence of bytes — file, network socket, memory, zip entry, HTTP body: one API for all. Layered:

```
FileStream / MemoryStream / NetworkStream        ← raw bytes
   └─ StreamReader / StreamWriter                ← text (encoding-aware)
   └─ GZipStream, CryptoStream, BufferedStream   ← wrap/transform other streams
```

```csharp
using var reader = new StreamReader("huge.log");         // note 'using' — see below
string? line;
while ((line = reader.ReadLine()) is not null)
    if (line.Contains("ERROR")) Console.WriteLine(line);
```

This processes a 10 GB file with tiny memory — `ReadAllText` on the same file would allocate 10 GB. **Rule: known-small → File helpers; unbounded/large → streams.** `File.ReadLines(path)` (lazy) vs `ReadAllLines` (eager) is the same rule in one letter.

## IDisposable and `using` — deterministic cleanup

Files hold OS handles; connections hold sockets. The GC will *eventually* finalize them, but "eventually" means locked files and exhausted connection pools. `IDisposable` is the contract for *release now*:

```csharp
using var stream = new FileStream("data.bin", FileMode.Create);   // using DECLARATION: disposes at scope end
// … write …
// ← stream.Dispose() runs HERE, even if an exception flew through

using (var r = new StreamReader(path))                            // using STATEMENT: explicit block form
{
    …
}                                                                  // disposed here
```

`using` compiles to `try/finally { Dispose(); }` — last lesson's finally, packaged. **Anything IDisposable gets a `using`** unless ownership is genuinely transferred elsewhere. Writers buffer: forgetting to dispose a `StreamWriter` can *lose your final bytes* (Dispose flushes), a bug that hides until production.

Implementing it yourself (for a type owning a disposable):

```csharp
public sealed class LogSession(string path) : IDisposable
{
    private readonly StreamWriter _writer = new(path, append: true);
    public void Log(string msg) => _writer.WriteLine($"{DateTime.UtcNow:o} {msg}");
    public void Dispose() => _writer.Dispose();          // pass the duty along
}
```

```csharp
{
    public decimal Total => Qty * UnitPrice;
}

string[] products = ["Keyboard", "Mouse", "Monitor", "Dock", "Webcam"];
using (var w = new StreamWriter("sales.csv"))
{
    w.WriteLine("date,region,product,qty,unit_price");
    var rng = new Random(42);
    for (int i = 0; i < 100_000; i++)
    {
        if (i % 10_000 == 9_999) { w.WriteLine("corrupted,row"); continue; }   // plant bad rows
        var date = new DateOnly(2026, 1, 1).AddDays(rng.Next(200));
        w.WriteLine($"{date:yyyy-MM-dd},{regions[rng.Next(3)]},{products[rng.Next(5)]}," +

    }
}

// 2 — lazy reader
static IEnumerable<Sale> ReadSales(string path, Action<string> onBadRow)
{
    foreach (var line in File.ReadLines(path).Skip(1))
    {
        var p = line.Split(',');
        if (p.Length == 5
            && DateOnly.TryParse(p[0], out var date)
            && int.TryParse(p[3], out int qty)
            && decimal.TryParse(p[4], out decimal price))
        {
            yield return new Sale(date, p[1], p[2], qty, price);
        }
        else onBadRow(line);
    }
}

// 3 — single-pass aggregation
long memBefore = GC.GetTotalMemory(forceFullCollection: true);

int rows = 0, bad = 0;
var byRegion = new Dictionary<string, decimal>();
var byProduct = new Dictionary<string, decimal>();

foreach (var s in ReadSales("sales.csv", _ => bad++))
{
    rows++;
    byRegion[s.Region] = byRegion.GetValueOrDefault(s.Region) + s.Total;
    byProduct[s.Product] = byProduct.GetValueOrDefault(s.Product) + s.Total;
}

long memAfter = GC.GetTotalMemory(true);
var topProduct = byProduct.MaxBy(kv => kv.Value);

// 4 — write report + gzip
using (var report = new StreamWriter("report.txt"))
{
    report.WriteLine($"rows: {rows:N0}   malformed: {bad}");
    foreach (var (region, revenue) in byRegion.OrderByDescending(kv => kv.Value))
        report.WriteLine($"{region,-5} {revenue,15:C}");
    report.WriteLine($"top product: {topProduct.Key} ({topProduct.Value:C})");
}

using (var output = File.Create("sales.csv.gz"))
using (var gzip = new System.IO.Compression.GZipStream(output, System.IO.Compression.CompressionLevel.Optimal))
    input.CopyTo(gzip);

long zipped = new FileInfo("sales.csv.gz").Length;
Console.WriteLine(File.ReadAllText("report.txt"));
Console.WriteLine($"csv {raw:N0} B → gz {zipped:N0} B ({(double)zipped / raw:P0})");
Console.WriteLine($"managed memory delta ≈ {(memAfter - memBefore) / 1024:N0} KB (streaming!)");
```

## Reading JSON you don't own: JsonDocument / JsonNode

When you need a few fields from a big payload — or the shape is dynamic — skip classes:

```csharp
// Read-only, allocation-light:

decimal price = doc.RootElement.GetProperty("items")[0].GetProperty("price").GetDecimal();
if (doc.RootElement.TryGetProperty("optional", out var opt)) { … }

// Mutable DOM:

```

## .NET 10 niceties (recognition level)

`JsonSerializerOptions.Strict` preset (rejects duplicate properties, unmapped members); `AllowDuplicateProperties = false` for security-sensitive parsing; `PipeReader` support. :::warn Round-trip gotchas
DateTime serializes as ISO 8601 — always parse/store round-trip formats. decimal is safe, but JavaScript consumers may mangle large numbers (> 2⁵³) — send big IDs as strings. And `Deserialize<T>` returns `T?` — null when input is the literal `null`; handle it (the `!` in examples above is the documented idiom when input is known non-null).

```csharp
using System.Text.Json;
using System.Text.Json.Serialization;
using System.Text.RegularExpressions;

public enum Mood { Great, Ok, Rough }

public record Entry(Guid Id, DateTimeOffset At, string Text, List<string> Tags, Mood Mood);

public static class Journal
{
    public static readonly JsonSerializerOptions Options = new()
    {
        WriteIndented = true,
        PropertyNamingPolicy = JsonNamingPolicy.CamelCase,
        Converters = { new JsonStringEnumConverter() },
    };

    public static string PathFor() => Path.Combine(
        Environment.GetFolderPath(Environment.SpecialFolder.ApplicationData),
        "BootcampJournal", "journal.json");

    public static List<Entry> Load()
    {
        string path = PathFor();
        if (!File.Exists(path)) return [];
        try
        {
            return JsonSerializer.Deserialize<List<Entry>>(File.ReadAllText(path), Options) ?? [];
        }
        catch (JsonException)
        {
            File.Copy(path, Path.ChangeExtension(path, ".bad.json"), overwrite: true);
            Console.WriteLine("⚠ journal was corrupted; backed up and starting fresh");
            return [];
        }
    }

    public static void Save(List<Entry> entries)
    {
        Directory.CreateDirectory(Path.GetDirectoryName(PathFor())!);
        File.WriteAllText(PathFor(), JsonSerializer.Serialize(entries, Options));
    }

    public static Entry NewEntry(Mood mood, string text)
    {
        var tags = Regex.Matches(text, @"#(\w+)").Select(m => m.Groups[1].Value.ToLowerInvariant())
                        .Distinct().ToList();
        return new Entry(Guid.CreateVersion7(), DateTimeOffset.UtcNow, text, tags, mood);
    }

    public static int Import(List<Entry> entries, string file)
    {
        using var doc = JsonDocument.Parse(File.ReadAllText(file));
        int added = 0;
        foreach (var item in doc.RootElement.GetProperty("items").EnumerateArray())
        {
            var at = DateTimeOffset.FromUnixTimeSeconds(item.GetProperty("ts").GetInt64());
            string note = item.GetProperty("note").GetString() ?? "";
            Mood mood = item.GetProperty("mood").GetInt32() switch
            {
                >= 4 => Mood.Great,
                3 => Mood.Ok,
                _ => Mood.Rough
            };
            var tags = item.TryGetProperty("tags", out var t)
                ? t.EnumerateArray().Select(x => x.GetString()!).ToList()
                : [];
            entries.Add(new Entry(Guid.CreateVersion7(), at, note, tags, mood));
            added++;
        }
        return added;
    }
}
```

? Why reuse a single JsonSerializerOptions instance?
- Options are IDisposable
* Each instance caches reflection/serialization metadata; new-per-call rebuilds that cache and wrecks performance
- Options are mutable after first use
- The serializer requires a singleton
> Options hold compiled metadata per type. The documented pattern: static readonly options, shared. (Source generation moves this cost to compile time entirely.)

? Your C# property is `UserName` but the API sends `user_name`. Cleanest fix?
- Rename the property to user_name
* [JsonPropertyName("user_name")] on the property (or a global naming policy if the WHOLE api uses snake_case)
- Parse manually with JsonDocument
- String-replace the JSON before deserializing
> Per-property mapping for exceptions; naming policies for systematic conventions. Both keep C# names idiomatic.

? When is JsonDocument the right tool over typed Deserialize&lt;T&gt;?
- Always; it's newer
* Probing a few fields from a payload whose full shape you don't own or model
- When you need to modify the JSON
- When the JSON is invalid
> The ladder: typed classes for shapes you own; JsonDocument for read-only probing; JsonNode when you must edit unknown shapes.

? `JsonSerializer.Deserialize<Product>(json)` returns Product? because…
- Deserialization often fails
* The JSON literal `null` legally deserializes to null — the signature tells the truth
- Products are optional
- It's a bug in the API
> Valid JSON can be the token null. The nullable return forces you to decide: `?? throw`, `!` when input is known, or handle the null.

? Serializing enums as strings ([JsonStringEnumConverter]) is preferred because…
- Numbers are larger on the wire
* "active" survives enum reordering and is self-documenting; the number 1 silently changes meaning if members are inserted
- Strings parse faster
- JavaScript can't read numbers
> Numeric enum JSON couples the wire format to declaration order — an invisible breaking change waiting to happen. Names are stable and readable.
