## Why tests, honestly

Tests are not bureaucracy; they're **executable specifications** plus a **regression alarm**. The payoff compounds: refactoring without fear, upgrading dependencies with confidence, onboarding by reading tests as examples. Untested code isn't "done" — it's "worked once."

.NET's main frameworks: **xUnit** (the modern default, used by the .NET team itself — we use it), NUnit (fine, older style), MSTest (fine, Microsoft's). Skills transfer ~95% between them.

## Setup: the two-project shape

```bash
dotnet new classlib -n MathKit
dotnet new xunit -n MathKit.Tests
dotnet add MathKit.Tests reference MathKit
dotnet new sln -n MathKit && dotnet sln add MathKit MathKit.Tests
dotnet test
```

Production code and test code live in separate projects; the test project references the production one (never the reverse). `dotnet test` discovers and runs everything.

## Anatomy of a test

```csharp
public class TemperatureTests
{
    [Fact]                                            // marks a test method
    public void CelsiusToFahrenheit_Converts_BoilingPoint()
    {
        // Arrange — set the stage
        double celsius = 100;

        // Act — ONE action under test
        double result = Temperature.CelsiusToFahrenheit(celsius);

        // Assert — verify the outcome
        Assert.Equal(212, result);
    }
}
```

**Arrange-Act-Assert** — the universal test skeleton. Naming convention (pick one, stay consistent): `Method_Scenario_ExpectedOutcome` or `Method_ExpectedOutcome_WhenScenario`. The name is the failure message's headline — write it for the person debugging at 2 AM.

## The assertion vocabulary

```csharp
Assert.Equal(expected, actual);            // order matters — expected FIRST (failure messages depend on it)
Assert.Equal(3.14159, actual, precision: 3);   // floating point: ALWAYS use precision/tolerance
Assert.NotEqual(a, b);
Assert.True(condition);  Assert.False(condition);   // last resort — Equal gives better messages
Assert.Null(value);      Assert.NotNull(value);
Assert.Same(a, b);                         // reference identity (rarely what you want)

// Collections
Assert.Contains(item, collection);
Assert.DoesNotContain(item, collection);
Assert.Empty(collection);  Assert.Single(collection);
Assert.Equal([1, 2, 3], actualList);       // sequence equality — works on collections directly
Assert.All(items, item => Assert.True(item.Price > 0));

// Strings
Assert.StartsWith("Error:", message);
Assert.Contains("timeout", message, StringComparison.OrdinalIgnoreCase);
Assert.Matches(@"^\d{4}-\d{2}$", period);

// Exceptions — assert failures precisely
var ex = Assert.Throws<ArgumentOutOfRangeException>(() => account.Withdraw(-5));
Assert.Equal("amount", ex.ParamName);

var ex2 = await Assert.ThrowsAsync<TimeoutException>(() => client.FetchAsync(url));
```

`Assert.Throws` is the *right* way to test error paths: it fails if no exception is thrown, if the *wrong type* is thrown, and hands you the exception for detail asserts.

## What makes a GOOD test

- **Fast** — milliseconds. Slow suites don't get run.
- **Isolated** — no shared state between tests; xUnit creates a **new class instance per test** precisely to enforce this. No dependence on execution order (xUnit randomizes within a class!).
- **Deterministic** — no `DateTime.Now`, no `Random` without a seed, no real network. (This is why Module 4's library took `DateOnly today` as a parameter — today it pays off.)
- **One logical assertion** — one reason to fail. Multiple `Assert.Equal` lines verifying facets of one outcome: fine. Testing two behaviors in one method: split it.
- **Tests behavior, not implementation** — assert on outputs and observable state, not private fields. Tests coupled to internals break on every refactor and protect nothing.

```csharp
namespace MathKit;

public class PriceCalculator
{
    public decimal Subtotal(IEnumerable<(decimal Price, int Qty)> lines)
        => lines.Sum(l => l.Price * l.Qty);

    public decimal ApplyDiscount(decimal subtotal, string? code) => code?.ToUpperInvariant() switch
    {
        null or "" => subtotal,
        "SAVE10" => subtotal * 0.90m,
        "SAVE25" => subtotal >= 100m
            ? subtotal * 0.75m
            : throw new InvalidOperationException("SAVE25 requires a subtotal of at least 100"),
        _ => throw new ArgumentException($"Unknown code '{code}'", nameof(code))
    };

    public decimal Total(decimal discounted, decimal taxRate = 0.11m)
    {
        ArgumentOutOfRangeException.ThrowIfNegative(discounted);
        ArgumentOutOfRangeException.ThrowIfNegative(taxRate);
        return Math.Round(discounted * (1 + taxRate), 2);
    }
}
```

* Arrange (set up), Act (the one operation under test), Assert (verify the outcome)
- Async, Await, Assert
- Add, Apply, Approve
> AAA gives every test the same skeleton: readers instantly find what's being tested and what's expected. One Act per test.

- Save memory
* Guarantee isolation — instance fields can't leak state between tests
- Run tests faster
- Support async tests
> Per-test instantiation makes shared-instance-state bugs structurally impossible. Shared setup that's expensive goes into fixtures (next lesson).

- try/catch with a bool flag
* Assert.Throws&lt;ArgumentOutOfRangeException&gt;(() => account.Withdraw(-5)) and optionally inspect the returned exception
- Mark the test [ExpectedException]
- Check the balance afterward
> Assert.Throws verifies the exact exception type, fails when nothing throws, and returns the exception for detail assertions — precise and readable.

? `Assert.Equal(0.3, 0.1 + 0.2)` fails. The correct fix is…
- Use Assert.True(0.1 + 0.2 == 0.3)
* Assert.Equal(0.3, 0.1 + 0.2, precision: 15) or a tolerance — floating point needs approximate equality
- Cast to float

- Private fields can't be read

## Theories: one test, many cases

A `[Fact]` is a single case. A `[Theory]` runs once **per data row** — each row is an independent test in the runner:

```csharp
[Theory]
[InlineData(100, "SAVE10", 90)]
[InlineData(100, "save10", 90)]        // case-insensitivity as a row, not a copy-pasted test
[InlineData(200, "SAVE25", 150)]
[InlineData(50, null, 50)]
[InlineData(50, "", 50)]
public void ApplyDiscount_ComputesExpected(decimal subtotal, string? code, decimal expected)
    => Assert.Equal(expected, _calc.ApplyDiscount(subtotal, code));
```

Five scenarios, four lines of logic. Theories shine for: boundary tables, parser cases, validation matrices — anywhere you'd otherwise clone a test and tweak two numbers.

### Beyond InlineData

`InlineData` takes only compile-time constants. For richer objects:

```csharp
public static TheoryData<string, string[]> SplitCases => new()
{
    { "a,b", ["a", "b"] },
    { "a,,b", ["a", "b"] },
    { "", [] },
};

[Theory]
[MemberData(nameof(SplitCases))]
public void Split_HandlesEdgeCases(string input, string[] expected) { … }
```

`TheoryData<>` is type-checked — wrong types fail at compile time, not mysteriously at run time. (`[ClassData]` exists for reusable cross-class datasets.)

## Shared context: the fixture ladder

xUnit's isolation model gives you explicit tools when setup must be shared:

| Scope | Mechanism | Use for |
|-------|-----------|---------|
| Per test | Constructor + `IDisposable` | Default: fresh state, cheap setup |
| Per class (all tests share ONE instance of the fixture) | `IClassFixture<T>` | Expensive setup: seeded database, parsed file |
| Across classes | `ICollectionFixture<T>` + `[Collection]` | One resource for a whole suite area |

```csharp
public class DatabaseFixture : IDisposable
{
    public string ConnectionString { get; }
    public DatabaseFixture()  { /* create + seed a test DB — runs ONCE */ }
    public void Dispose()     { /* drop it — after the class's last test */ }
}

public class OrderQueryTests(DatabaseFixture db) : IClassFixture<DatabaseFixture>
{
    [Fact]
    public void FindsSeededOrder() { /* use db.ConnectionString */ }
}
```

Constructor/Dispose still run per test around the shared fixture — combine both: fixture for the expensive immutable part, constructor for the per-test clean slate.

## Organizing a real suite

- **Mirror the source tree**: `src/Shop.Core/Pricing/Discount.cs` → `tests/Shop.Core.Tests/Pricing/DiscountTests.cs`. Finding tests must be zero-thought.
- **Group by class then behavior**: one test class per production class is the default; split big ones by scenario (`DiscountTests.Validation`, `DiscountTests.Calculation`) using nested classes if helpful.
- **Builders for messy Arranges**: when object setup dominates tests, write a fluent test-data builder (`new OrderBuilder().WithLines(3).Paid().Build()`). Your Module 11 fluent skills, applied to tests.
- **Skip and traits**: `[Fact(Skip = "flaky on CI — issue #42")]` documents WHY; `[Trait("Category", "Integration")]` enables `dotnet test --filter Category=Unit`.

```csharp
namespace Validation;

public record PolicyResult(bool Valid, List<string> Problems);

public static class PasswordPolicy
{
    public static PolicyResult Check(string? password)
    {
        List<string> problems = [];
        string p = password ?? "";

        if (p.Length < 10) problems.Add("too short (min 10)");
        if (p.Length > 64) problems.Add("too long (max 64)");
        if (!p.Any(char.IsUpper)) problems.Add("needs an uppercase letter");
        if (!p.Any(char.IsLower)) problems.Add("needs a lowercase letter");
        if (!p.Any(char.IsDigit)) problems.Add("needs a digit");
        if (p.Contains(' ')) problems.Add("no spaces allowed");

        return new PolicyResult(problems.Count == 0, problems);
    }
}
```

## Challenge: theory-test the Module 3 CSV parser

Your `ParseCsvLine` from Module 3 (quoted fields, doubled quotes) is *made* of edge cases — the perfect theory subject.

### Requirements

1. A `TheoryData<string, string[]>`-driven suite covering at least: simple fields; empty line (one empty field? decide and encode!); trailing comma; quoted comma; doubled quotes; quoted empty `""`; whitespace preservation; a field that is ONLY a quoted comma; unterminated quote (decide: last field as-is? exception? — encode your decision).
2. At least 12 data rows total. Each row's expectation array is the complete parse — use `Assert.Equal(expected, actual)` sequence equality.
3. One `[Fact]` documenting the unterminated-quote decision with a comment explaining the choice (specs live in tests).
4. Round-trip property test (manual style): a theory of `string[]` inputs → build a CSV line by joining with quoting logic you write in the test → parse it back → `Assert.Equal(original, parsed)`. Three tricky rows minimum (fields containing commas, quotes, both).
5. If ANY test disagrees with your parser: fix the parser, not the test — unless the test's expectation was genuinely wrong, in which case say so in a commit-style comment.

:::solution Show solution (core)
```csharp
public class CsvParserTests
{
    public static TheoryData<string, string[]> Cases => new()
    {
        { "a,b,c", ["a", "b", "c"] },
        { "", [""] },                                    // decision: empty line = one empty field
        { "a,", ["a", ""] },                             // trailing comma = trailing empty field
        { ",a", ["", "a"] },
        { "\"a,b\",c", ["a,b", "c"] },
        { "\"say \"\"hi\"\"\"", ["say \"hi\""] },
        { "\"\"", [""] },                                // quoted empty
        { " a , b ", [" a ", " b "] },                   // whitespace preserved (RFC-ish)
        { "\",\"", [","] },                              // field that IS a comma
        { "a,\"b\nc\",d", ["a", "b\nc", "d"] },          // if your parser takes multi-line fields; else remove
        { "x", ["x"] },
        { "\"unterminated", ["unterminated"] },          // decision documented below
    };

    [Theory]
    [MemberData(nameof(Cases))]
    public void ParseCsvLine_ParsesCorrectly(string input, string[] expected)
        => Assert.Equal(expected, CsvParser.ParseCsvLine(input));

    [Fact]
    public void ParseCsvLine_UnterminatedQuote_YieldsFieldAsIs()
    {
        // DECISION: we tolerate unterminated quotes, returning accumulated content.
        // Rationale: import tooling favors salvaging rows over hard failure;
        // the malformed-row COUNT (Module 6 reporter) is the right place to flag it.
        var result = CsvParser.ParseCsvLine("\"oops,");
        Assert.Equal(["oops,"], result);
    }

    public static TheoryData<string[]> RoundTripCases => new()
    {
        (string[])["plain", "with,comma", "with\"quote"],
        ["", ",", "\"\""],
        ["a b", " leading", "trailing "],
    };

    [Theory]
    [MemberData(nameof(RoundTripCases))]
    public void BuildThenParse_RoundTrips(string[] original)
    {
        string line = string.Join(",", original.Select(Quote));

        var parsed = CsvParser.ParseCsvLine(line);

        Assert.Equal(original, parsed);

        static string Quote(string f)
            => f.Contains(',') || f.Contains('"')
                ? $"\"{f.Replace("\"", "\"\"")}\""
                : f;
    }
}
```

The round-trip test is the quiet star: it verifies parser and quoting are true inverses across the whole edge-case space, and catches bugs neither direction's example tests would. (Property-based testing frameworks like FsCheck industrialize this idea with generated inputs — worth exploring later.)
:::

## The problem: hidden dependencies

```csharp
public class OrderService
{
    public string PlaceOrder(Cart cart)
    {
        var total = cart.Total();
        var receipt = new PaymentGateway().Charge(total);        // REAL network call!
        File.AppendAllText("orders.log", $"{DateTime.Now}: {receipt}");  // REAL file! REAL clock!
        return receipt;
    }
}
```

This is untestable *by construction*: running the test charges a card. The disease is `new`-ing dependencies and touching ambient statics (`File`, `DateTime.Now`) inside business logic.

## The cure: depend on abstractions, inject implementations

```csharp
public interface IPaymentGateway { string Charge(decimal amount); }
public interface IOrderLog { void Append(string entry); }

public class OrderService(IPaymentGateway gateway, IOrderLog log, TimeProvider clock)
{
    public string PlaceOrder(Cart cart)
    {
        ArgumentNullException.ThrowIfNull(cart);
        if (cart.IsEmpty) throw new InvalidOperationException("Cart is empty");

        string receipt = gateway.Charge(cart.Total());
        log.Append($"{clock.GetUtcNow():o}: {receipt}");
        return receipt;
    }
}
```

**Constructor injection**: dependencies arrive as interfaces; the class *declares* its needs and hides nothing. Production wires real implementations (Module 10's DI container automates this); tests wire **test doubles**. `TimeProvider` is .NET's built-in abstract clock (with `FakeTimeProvider` in the `Microsoft.Extensions.TimeProvider.Testing` package) — the standard cure for `DateTime.Now` disease.

## The test double taxonomy

| Double | Purpose | Example |
|--------|---------|---------|
| **Stub** | Returns canned answers; no verification | Gateway that always returns "receipt-1" |
| **Fake** | Working lightweight implementation | In-memory repository backed by a Dictionary |
| **Mock** | Records calls so you can verify **interactions** | "Charge was called once with 99.95" |
| **Spy** | Real thing + recording | Rarely needed |

### Hand-rolled doubles — always available, often clearest

```csharp

    {
        ChargedAmounts.Add(amount);
        return ReceiptToReturn;
```

## State vs interaction testing — the judgment call

**Prefer asserting state/results** ("the returned receipt is X"; "the repository now contains Y") — it survives refactors. **Verify interactions** only when the interaction *is* the requirement ("exactly one charge attempt", "email sent once"). Over-mocked suites that verify every internal call are change-detectors, not tests — the most common testing anti-pattern in industry.

:::tip The design feedback loop
"This class is hard to test" is never a testing problem — it's the class confessing: too many dependencies (split it), hidden ones (inject them), static/ambient state (abstract it). Testability and good design are the same property observed from two angles.
:::

@QUIZ
? The root cause of "untestable" code is usually…
- Missing test framework features
* Hidden dependencies: new-ed collaborators and ambient statics (clock, file system, network) buried inside logic
- Too many public methods
- Lack of comments
> If a class's collaborators arrive via constructor as abstractions, tests substitute them freely. If it news/statics them internally, the real world comes attached.

? A stub differs from a mock in that…
* A stub only supplies canned data; a mock additionally records calls for interaction verification
- Stubs are faster
- Mocks are hand-written only
- Stubs work only for HTTP
> Stub = input provider. Mock = interaction recorder. NSubstitute objects serve as both — the distinction is in how your test USES them.

? When should you verify interactions (Received) rather than assert state?
- Always; it's more thorough
* When the interaction IS the requirement — "charged exactly once", "email sent" — i.e., observable side effects on the outside world
- When state is hard to reach
- Never
> Side effects on external systems are only visible as interactions. For everything else, state assertions survive refactoring better. Over-mocking creates brittle change-detector suites.

? TimeProvider solves which testing problem?
- Slow tests
* DateTime.Now-dependent logic being irreproducible — inject the clock, fake it, pin any moment
- Time zone conversions
- Async timing
> The abstract clock (with FakeTimeProvider) makes "what happens on a Saturday?" a one-line arrangement instead of a wait-until-Saturday joke.

? "This class needs 7 mocked dependencies to test" most likely means…
- You need a better mocking library
* The class has too many responsibilities — the test pain is design feedback urging a split
- Tests should use the real dependencies
- The class is fine; tests are overkill
> Test friction mirrors coupling. Wide constructors flag classes doing too much — listen to the tests and refactor.

## Test-Driven Development: the loop

**Red → Green → Refactor**:

1. **Red** — write a *small failing test* for the next bit of behavior. Watch it fail (proves the test can fail!).
2. **Green** — write the *minimum* production code to pass. Resist elegance.
3. **Refactor** — with green as your net, clean up both production and test code. Repeat.

```
Red:      Assert.Equal("I", ToRoman(1));      → ToRoman doesn't exist: fails
Green:    static string ToRoman(int n) => "I";              // yes, really — minimum!
Red:      Assert.Equal("II", ToRoman(2));                   → fails
Green:    => string.Concat(Enumerable.Repeat("I", n));      // generalize when forced
Red:      Assert.Equal("IV", ToRoman(4));                   → fails … and so the design GROWS
```

Why the ritual works: the test-first constraint forces **small steps**, **testable design by default** (you're the first consumer of your own API), and a **spec that accumulates**. You don't need TDD for everything — but for algorithmic/logic-heavy code it is astonishingly effective, and *knowing how* is a hiring bar at many shops.

## The testing pyramid — where to spend

```
        ▲  E2E/UI (few):        full system through the UI — slow, brittle, priceless when green
       ▲▲  Integration (some):  real DB / real HTTP boundaries — Module 9/10 test these
     ▲▲▲▲  Unit (many):         logic in isolation — fast, precise, cheap
```

Healthy ratios are pyramid-shaped. Inverted pyramids (all E2E) are slow and flaky; all-unit suites miss wiring bugs. In .NET practice: xUnit for the base, `WebApplicationFactory` for API integration tests (Module 10), Testcontainers for real-database tests (Module 9), Playwright for E2E.

## Coverage: a flashlight, not a target

```bash
dotnet test --collect:"XPlat Code Coverage"     # Coverlet → coverage.cobertura.xml
```

Coverage tells you what you *forgot to touch* — uncovered branches are unreviewed risk. But **100% coverage proves nothing about assertion quality** (a test with no asserts covers plenty). Sane practice: watch the trend, investigate holes in *important* code, never gamify the number. Mutation testing (e.g. Stryker.NET) is the honest metric — it breaks your code and checks tests notice — file under "explore later."

## Naming the strategy: what to test how

| Code kind | Strategy |
|-----------|----------|
| Pure logic (pricing, parsing, rules) | Unit test exhaustively; theories for matrices; TDD shines here |
| Orchestrators (services calling collaborators) | Unit with doubles; verify critical interactions only |
| Adapters (EF repositories, HTTP clients) | Integration tests against real-ish infrastructure |
| Configuration/wiring | One smoke test that the app boots and answers |
| UI | Few E2E happy paths + component tests where the framework supports them |

:::tip The pragmatic rules
Write the test you wish existed when this breaks at 2 AM. Test behavior at public seams. If arranging a test is agony, fix the design, not the test. Delete tests that no longer earn their run time. A failing test must say WHAT broke without opening a debugger.
:::

```csharp
public static string From(int n)

    [
        (10, "X"), (9, "IX"), (5, "V"), (4, "IV"), (1, "I"),
    ];
```

## Challenge: TDD the `BowlingScore` kata (the classic)

Score a 10-pin bowling game from a list of rolls — the most famous TDD exercise in existence. Rules: 10 frames; open frame = sum of two rolls; **spare** (10 in two rolls) = 10 + next one roll bonus; **strike** (10 in one roll) = 10 + next two rolls bonus; 10th frame allows bonus rolls (max 3 rolls).

### Requirements

1. **Strict TDD**: each behavior enters via a failing test first. Keep a war-log comment at the top of the test file: one line per red-green cycle (`// 1. all gutters → 0  2. all ones → 20  3. one spare …`).
2. Suggested test ladder (don't skip ahead!):
   - all gutter balls → 0
   - twenty 1s → 20
   - one spare then a 3 → 16 + rest
   - one strike then 3,4 → 24 + rest
   - perfect game (twelve 10s) → 300
   - all spares with final 5 → 150
3. API: `BowlingScore.Score(IReadOnlyList<int> rolls)` returning int. No frame classes unless a test forces them (spoiler: an index-walking loop suffices — let the tests prove it).
4. Edge contract (your choice, encoded in tests): invalid roll values (11, -1) throw.
5. After green: refactor to your taste with tests as the net, then run coverage and confirm every branch is exercised.

:::solution Show solution (algorithm + key tests)
```csharp
public static class BowlingScore
{
    public static int Score(IReadOnlyList<int> rolls)
    {
        if (rolls.Any(r => r is < 0 or > 10))
            throw new ArgumentOutOfRangeException(nameof(rolls), "rolls must be 0–10");

        int score = 0, i = 0;
        for (int frame = 0; frame < 10; frame++)
        {
            if (rolls[i] == 10)                            // strike
            {
                score += 10 + rolls[i + 1] + rolls[i + 2];
                i += 1;
            }
            else if (rolls[i] + rolls[i + 1] == 10)        // spare
            {
                score += 10 + rolls[i + 2];
                i += 2;
            }
            else                                           // open
            {
                score += rolls[i] + rolls[i + 1];
                i += 2;
            }
        }
        return score;
    }
}
```

```csharp
    [Fact] public void PerfectGame_Scores300() => Assert.Equal(300, BowlingScore.Score(Repeat(10, 12)));
    [Fact] public void AllSpares_Scores150() => Assert.Equal(150, BowlingScore.Score(Repeat(5, 21)));

    [Theory]
    [InlineData(11)] [InlineData(-1)]
    public void InvalidRoll_Throws(int bad)
        => Assert.Throws<ArgumentOutOfRangeException>(() => BowlingScore.Score(Rolls(bad)));
}
```

@QUIZ
? In TDD, why must you SEE the new test fail before making it pass?
- Ritual tradition
* A test that never failed might be incapable of failing — red proves it actually tests something
- To practice reading stack traces
- To measure how long fixes take
> Green-on-arrival tests (wrong assert, testing existing behavior) are silent liabilities. Red first validates the test itself.

? "Write the minimum code to pass" exists to…
- Save typing
* Keep design driven by actual requirements (tests) instead of speculative generality
- Make tests run faster
- Avoid compiler warnings
> Hardcoding "I" feels absurd but enforces the discipline: every line of production code exists because a test demanded it. Generality arrives when tests force it.

? The testing pyramid recommends…
- Mostly E2E tests for realism
* Many fast unit tests, fewer integration tests, few E2E tests
- Equal amounts of each
- Only unit tests
> Cost and flakiness grow toward the top; precision grows toward the bottom. Wiring bugs need SOME integration/E2E — but the bulk belongs at the base.

? 100% code coverage guarantees…
- Bug-free code
- Every behavior is asserted
* Only that every line executed during tests — assertions may still be missing or weak
- Good design
> Coverage measures execution, not verification. Use it to find forgotten areas; use mutation testing to audit assertion strength.

? Which code MOST deserves TDD?
- Auto-generated DTOs
- Framework configuration
* Algorithmic logic with rich cases — parsers, calculators, scoring rules
- One-line property wrappers
> TDD's incremental case-by-case pressure matches algorithmic complexity perfectly (Roman, Bowling). Wiring and DTOs get thinner strategies — smoke and integration tests.
