## The problem: waiting without blocking

I/O (network, disk, databases) is thousands of times slower than CPU work. A thread that *blocks* on I/O is a wasted worker — in a server, blocked threads mean collapsed throughput; in a UI app, a frozen window. **Asynchrony releases the thread while the I/O is in flight.**

```csharp
// Synchronous: the thread SITS THERE for ~300ms doing nothing
string html = client.GetStringAsync(url).Result;      // (also a deadlock trap — see below)

// Asynchronous: the thread is FREED during the wait
string html = await client.GetStringAsync(url);
```

## The rules of the road

```csharp
public async Task<string> FetchTitleAsync(string url)      // 1. 'async' enables 'await' inside
{
    using var client = new HttpClient();
    string html = await client.GetStringAsync(url);        // 2. awaiting a Task<string> yields a string
    return ExtractTitle(html);                              // 3. return T from Task<T> — wrapping is automatic
}
```

- Return **`Task<T>`** (has a result), **`Task`** (no result), or `ValueTask<T>` (perf niche). **`async void` is only for event handlers** — its exceptions crash the process because no Task carries them.
- Name with the `Async` suffix by convention.
- `await` unwraps: result out, or the task's **exception rethrown** with a sane stack trace.
- Async is contagious *upward* — callers of async methods generally become async too, all the way to `Main` (`static async Task Main()` — top-level statements handle this automatically).

## What `await` actually does (the honest version)

`await` does **not** create a thread. The compiler rewrites your method into a **state machine**:

1. Code runs synchronously until the first await of an incomplete task.
2. The method **returns to its caller** right there, registering the rest of itself (the *continuation*) to run when the awaited task completes.
3. The waiting itself is done by the OS/network stack — **no thread is consumed** during the wait.
4. On completion, the continuation resumes (on the thread pool in console/server apps; on the UI thread in desktop apps, courtesy of the SynchronizationContext).

```csharp
Console.WriteLine($"before: thread {Environment.CurrentManagedThreadId}");
await Task.Delay(1000);                          // async sleep — zero threads consumed while waiting
Console.WriteLine($"after:  thread {Environment.CurrentManagedThreadId}");   // often a DIFFERENT thread!
```

:::warn The blocking sins
`.Result`, `.Wait()`, and `.GetAwaiter().GetResult()` on incomplete tasks **block the thread** — the very thing async exists to avoid — and in UI/legacy-ASP.NET contexts they *deadlock* (the continuation needs the thread you're blocking). The fix is always the same: await it. "Async all the way down."
:::

## Composition: the real superpower

```csharp
// Sequential — when B needs A's result:
var user = await GetUserAsync(id);
var orders = await GetOrdersAsync(user.Id);

// Concurrent — independent operations OVERLAP their waits:
Task<User> userTask = GetUserAsync(id);          // starts immediately (hot task!)
Task<Weather> weatherTask = GetWeatherAsync();   // also in flight
var results = await Task.WhenAll(userTask, weatherTask);   // both done: total ≈ max, not sum

// or with different types:
await Task.WhenAll(userTask, weatherTask);
User u = userTask.Result;                        // safe AFTER completion — .Result on a done task doesn't block
```

Three 300 ms calls: sequential = 900 ms, concurrent = ~300 ms. This — not threads — is where most real-world async performance comes from.

```csharp
Task<T> first = await Task.WhenAny(taskA, taskB);   // races: first finisher wins
```

## Async in loops and streams

```csharp
foreach (var url in urls)
    results.Add(await FetchAsync(url));            // sequential — fine, sometimes intended

// IAsyncEnumerable<T>: a stream of values arriving over time
await foreach (var line in ReadLinesAsync(path))
    Process(line);

static async IAsyncEnumerable<string> ReadLinesAsync(string path)
{
    using var reader = new StreamReader(path);
    while (await reader.ReadLineAsync() is { } line)
        yield return line;                          // yield + await compose!
}
```

### Requirements

1. Simulated services with distinct latencies and failure behavior:
   - `GetProfileAsync(userId)` — 300 ms, always works

2. `BuildDashboardAsync(userId)` returns a `Dashboard` record and must:
   - run all three **concurrently** (prove with total time ≈ 500 ms, not 1200)
   - treat recommendations as *optional*: on failure, dashboard still builds with an empty list and a `Degraded = true` flag (wrap ONLY that task's await in try/catch)
   - propagate failures of the two required services normally
3. Run it 4 times in a loop printing per-run timing, contents summary, and degraded status — you should see both healthy and degraded runs.
4. Stretch: add a `Task.WhenAny`-based *soft timeout* — if recommendations take longer than 250 ms, proceed without them (they might still land later; ignore the result).

:::solution Show solution
```csharp
public record Profile(string Name, string Tier);
public record Order(string Id, decimal Total);
public record Dashboard(Profile Profile, List<Order> Orders, List<string> Recommendations, bool Degraded);

static async Task<Profile> GetProfileAsync(int userId)
{
    await Task.Delay(300);
    return new Profile($"user-{userId}", "Premium");
}

static async Task<List<Order>> GetOrdersAsync(int userId)
{
    await Task.Delay(500);
    return [new("ord-1", 49.99m), new("ord-2", 129.00m)];
}

static async Task<List<string>> GetRecommendationsAsync(int userId)
{
    await Task.Delay(400);
    if (Random.Shared.Next(2) == 0) throw new TimeoutException("rec engine overloaded");
    return ["Dock", "Headset", "Monitor arm"];
}

static async Task<Dashboard> BuildDashboardAsync(int userId)
{
    // start EVERYTHING first — hot tasks run concurrently
    Task<Profile> profileTask = GetProfileAsync(userId);
    Task<List<Order>> ordersTask = GetOrdersAsync(userId);
    Task<List<string>> recsTask = GetRecommendationsAsync(userId);

    // required services: let failures fly
    Profile profile = await profileTask;
    List<Order> orders = await ordersTask;

    // optional service: contain its failure
    List<string> recs = [];
    bool degraded = false;
    try
    {
        recs = await recsTask;
    }
    catch (TimeoutException)
    {
        degraded = true;
    }

    return new Dashboard(profile, orders, recs, degraded);
}

for (int run = 1; run <= 4; run++)
{
    var sw = System.Diagnostics.Stopwatch.StartNew();
    var dash = await BuildDashboardAsync(42);
    Console.WriteLine($"run {run}: {sw.ElapsedMilliseconds,4} ms  " +
        $"{dash.Profile.Name} ({dash.Profile.Tier}), {dash.Orders.Count} orders, " +
        $"{dash.Recommendations.Count} recs{(dash.Degraded ? "  ⚠ degraded" : "")}");
}

// Stretch: soft timeout on recommendations
static async Task<List<string>> RecsWithSoftTimeout(Task<List<string>> recsTask, int ms)
{
    var completed = await Task.WhenAny(recsTask, Task.Delay(ms));
    if (completed == recsTask)
    {
        try { return await recsTask; } catch { return []; }
    }
    return [];                                   // timer won; abandon (not cancel) the recs
}
```

The critical detail: all three tasks are **created before any await** — that's what makes them concurrent. Awaiting inline (`await GetProfileAsync(...)` then `await GetOrdersAsync(...)`) would serialize them. Timing proves it: ~500 ms (the max), not 1200 (the sum). The per-dependency failure policy (required vs optional) is real production design — most dashboards you use work exactly this way.
:::

## CancellationToken: cooperative cancellation

.NET cancellation is **cooperative** — nothing is killed; work is *asked* to stop and agrees to check:

```csharp
using var cts = new CancellationTokenSource();
CancellationToken token = cts.Token;

Task work = DoWorkAsync(token);      // pass the token DOWN through every layer
cts.Cancel();                        // request cancellation (or CancelAfter(ms))
```

Inside cancellable work:

```csharp
static async Task DoWorkAsync(CancellationToken ct)
{
    foreach (var item in bigList)
    {
        ct.ThrowIfCancellationRequested();       // check at loop boundaries
        await ProcessAsync(item, ct);            // FORWARD the token to everything async
    }
}
```

Cancellation surfaces as **`OperationCanceledException`** — by convention it means "stopped as requested", not "failed":

```csharp
try
{
    await work;
}
catch (OperationCanceledException)
{
    Console.WriteLine("cancelled cleanly");      // expected path, not an error
}
```

Every serious async API takes an optional `CancellationToken` — and **yours should too**. It's the last parameter by convention.

### Timeouts

```csharp
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));   // auto-cancels
var data = await FetchAsync(url, cts.Token);

// or per-call without a CTS (.NET 6+):
var result = await SomeTaskAsync().WaitAsync(TimeSpan.FromSeconds(5));  // TimeoutException on expiry

// linking: cancel when EITHER the user cancels OR the timeout hits
using var linked = CancellationTokenSource.CreateLinkedTokenSource(userToken);
linked.CancelAfter(TimeSpan.FromSeconds(30));
```

## Progress reporting

```csharp
public async Task ImportAsync(IProgress<int>? progress, CancellationToken ct)
{
    for (int i = 0; i < files.Count; i++)
    {
        ct.ThrowIfCancellationRequested();
        await ImportOneAsync(files[i], ct);
        progress?.Report((i + 1) * 100 / files.Count);
    }
}

// caller:
var progress = new Progress<int>(pct => Console.Write($"\r{pct}%"));
await ImportAsync(progress, cts.Token);
```

`Progress<T>` captures the current context — in UI apps the callback lands on the UI thread automatically. This trio — `Task` + `CancellationToken` + `IProgress<T>` — is the standard signature for long-running operations.

## Task.Run: CPU work off the current thread

`async` handles *waiting*; `Task.Run` handles *computing*:

```csharp
// CPU-heavy work would block; push it to the thread pool:
int[] primes = await Task.Run(() => ComputePrimes(10_000_000), ct);
```

Rules: use it in *applications* to keep UIs responsive or parallelize CPU work; **don't** wrap naturally-async I/O in Task.Run (adds a thread for nothing); don't sprinkle it inside libraries (let callers decide their threading).

## Throttled concurrency: the pattern you'll use forever

Firing 10,000 concurrent requests is a self-inflicted denial of service. Bound the concurrency:

```csharp
using var gate = new SemaphoreSlim(8);          // at most 8 in flight

var tasks = urls.Select(async url =>
{
    await gate.WaitAsync(ct);
    try { return await FetchAsync(url, ct); }
    finally { gate.Release(); }
});
var results = await Task.WhenAll(tasks);
```

Or the built-in loop with parallelism control:

```csharp
await Parallel.ForEachAsync(urls,
    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (url, token) => { results.Add(await FetchAsync(url, token)); });   // careful: thread-safe collection needed!
```

:::warn Shared state under concurrency
The moment two tasks touch one variable, you need a plan: thread-safe collections (`ConcurrentDictionary`, `ConcurrentBag`), `Interlocked.Increment` for counters, or confinement (each task returns results; combine after WhenAll — often the cleanest). `List<T>.Add` from parallel code corrupts the list.
:::

## Tutorial: a cancellable, progress-reporting downloader

Project `Downloader`. Simulated downloads with every production pattern.

### Step 1 — the unit of work

```csharp
public record DownloadResult(string File, long Bytes, bool FromCache);

static async Task<DownloadResult> DownloadAsync(string file, CancellationToken ct)
{
    long total = Random.Shared.Next(200, 900);
    for (long done = 0; done < total; done += 50)
    {
        ct.ThrowIfCancellationRequested();               // cooperative checkpoints
        await Task.Delay(25, ct);                        // Delay itself honors the token
    }
    return new DownloadResult(file, total * 1024, false);
}
```

### Step 3 — throttled batch with progress

```csharp
string[] files = Enumerable.Range(1, 20).Select(i => $"file{i:D2}.bin").ToArray();
using var gate = new SemaphoreSlim(4);                   // max 4 concurrent
int completed = 0;

var tasks = files.Select(async file =>
{
    await gate.WaitAsync(cts.Token);
    try
    {
        var result = await DownloadAsync(file, cts.Token);
        int done = Interlocked.Increment(ref completed); // thread-safe counter
        Console.WriteLine($"[{done,2}/{files.Length}] {file} ({result.Bytes / 1024} KB)");
        return result;
    }
    finally { gate.Release(); }
}).ToArray();

try
{
    var results = await Task.WhenAll(tasks);
    Console.WriteLine($"✔ all done: {results.Sum(r => r.Bytes) / 1024:N0} KB total");
}
catch (OperationCanceledException)
{
    Console.WriteLine($"cancelled with {completed}/{files.Length} finished");
}
```

Run it and press Ctrl+C mid-flight: in-flight items stop at their next checkpoint, queued items never start, finished work stays finished. That's cooperative cancellation working as designed. Note `Interlocked.Increment` — `completed++` from 4 concurrent tasks would lose updates.

### Step 4 — add a global timeout

```csharp
using var linked = CancellationTokenSource.CreateLinkedTokenSource(cts.Token);
linked.CancelAfter(TimeSpan.FromSeconds(3));             // whichever fires first wins
// pass linked.Token everywhere instead of cts.Token
```

Set 3 seconds, watch the batch die at the deadline; set 60, watch it finish. One token, two cancellation sources.

### Step 5 — per-item retry with backoff

```csharp
static async Task<T> WithRetry<T>(Func<CancellationToken, Task<T>> op, int attempts, CancellationToken ct)
{
    for (int attempt = 1; ; attempt++)
    {
        try
        {
            return await op(ct);
        }
        catch (Exception ex) when (attempt < attempts && ex is not OperationCanceledException)
        {
            int delay = 100 * (1 << attempt);            // exponential backoff: 200, 400, 800…
            Console.WriteLine($"  retry {attempt} in {delay} ms ({ex.GetType().Name})");
            await Task.Delay(delay, ct);
        }
    }
}
```

The `when` filter is doing precision work: retry real failures, but *never* swallow cancellation. Wire it around a flaky version of DownloadAsync (throw 30% of the time) and watch backoff in action.

## Challenge: `BatchProcessor` — a production-shaped job runner

Build a generic batch processor exercising every pattern from this lesson.

### Requirements

1. `public static async Task<BatchReport> RunAsync<T, TResult>(IEnumerable<T> items, Func<T, CancellationToken, Task<TResult>> worker, int maxConcurrency, IProgress<(int Done, int Total)>? progress, CancellationToken ct)`.
2. Behavior: throttle with SemaphoreSlim; per-item failures are *captured*, not batch-fatal; report progress after each completion; honor cancellation promptly (queued items don't start).
3. `BatchReport` record: `Succeeded`, `Failed`, `Cancelled` counts + `List<(string Item, string Error)>` failures + `Elapsed`.
4. Demo: 30 simulated jobs (150–400 ms each; 20% throw `IOException`), concurrency 5, console progress bar (`\r` + percentage), a 4-second linked timeout, and a final report table. Run once to completion (raise the timeout) and once hitting the timeout — the report must be honest in both cases.
5. Thread-safety audit in comments: name every piece of shared state and why it's safe (Interlocked / ConcurrentBag / confinement).

:::solution Show solution
```csharp
public record BatchReport(int Succeeded, int Failed, int Cancelled,
                          List<(string Item, string Error)> Failures, TimeSpan Elapsed);

public static class BatchProcessor
{
    public static async Task<BatchReport> RunAsync<T, TResult>(
        IEnumerable<T> items,
        Func<T, CancellationToken, Task<TResult>> worker,
        int maxConcurrency,
        IProgress<(int Done, int Total)>? progress,
        CancellationToken ct)
    {
        var list = items.ToList();
        var sw = System.Diagnostics.Stopwatch.StartNew();
        using var gate = new SemaphoreSlim(maxConcurrency);

        int succeeded = 0, failed = 0, cancelled = 0, done = 0;
        // Shared state safety:
        //  - counters: Interlocked only
        //  - failures: ConcurrentBag (multi-writer)
        //  - list/sw: written before tasks start, read after — confinement by phase
        var failures = new System.Collections.Concurrent.ConcurrentBag<(string, string)>();

        var tasks = list.Select(async item =>
        {
            try
            {
                await gate.WaitAsync(ct);                 // throws if already cancelled → queued items skip
            }
            catch (OperationCanceledException)
            {
                Interlocked.Increment(ref cancelled);
                return;
            }

            try
            {
                await worker(item, ct);
                Interlocked.Increment(ref succeeded);
            }
            catch (OperationCanceledException)
            {
                Interlocked.Increment(ref cancelled);
            }
            catch (Exception ex)
            {
                Interlocked.Increment(ref failed);
                failures.Add((item!.ToString()!, ex.Message));
            }
            finally
            {
                gate.Release();
                progress?.Report((Interlocked.Increment(ref done), list.Count));
            }
        }).ToArray();

        await Task.WhenAll(tasks);                        // individual failures already captured → won't throw
        return new BatchReport(succeeded, failed, cancelled, [.. failures], sw.Elapsed);
    }
}
```

```csharp
static async Task<string> SimulatedJob(int id, CancellationToken ct)
{

    if (Random.Shared.Next(5) == 0) throw new IOException($"disk hiccup on job {id}");
    return $"job-{id}";

using var linked = CancellationTokenSource.CreateLinkedTokenSource(cts.Token);
linked.CancelAfter(TimeSpan.FromSeconds(4));              // set 60 for the full run

    Console.Write($"\r[{new string('█', p.Done * 20 / p.Total),-20}] {p.Done}/{p.Total}"));

var report = await BatchProcessor.RunAsync(
    Enumerable.Range(1, 30), SimulatedJob, maxConcurrency: 5, progress, linked.Token);

Console.WriteLine($"\n✔ {report.Succeeded}  ✘ {report.Failed}  ⏹ {report.Cancelled}  in {report.Elapsed.TotalSeconds:F1}s");
foreach (var (item, error) in report.Failures)
    Console.WriteLine($"   {item}: {error}");
```

This is, at small scale, how real job systems (Hangfire workers, queue consumers) are shaped.
:::

- Inside library code to make sync methods "async"
- To make HttpClient faster
> I/O is already threadless-async; wrapping it in Task.Run burns a pool thread for nothing. Task.Run is for computation, in application code.

? SemaphoreSlim(8) around requests achieves…
- Sequential execution
- Faster individual requests
* At most 8 operations in flight — protecting yourself and the remote service from unbounded concurrency
- Automatic retries
> Unbounded WhenAll over thousands of items is an accidental DoS. Gate + WaitAsync/Release (or Parallel.ForEachAsync's MaxDegreeOfParallelism) bounds it.

? Why `Interlocked.Increment(ref counter)` instead of counter++ in parallel code?
- It's shorter
* counter++ is read-modify-write; concurrent tasks interleave and LOSE updates. Interlocked makes it atomic
- counter++ throws under concurrency
- No reason; they're equivalent
> Lost updates are the classic race: two tasks read 5, both write 6. Interlocked (or confinement, or locks) is mandatory for shared mutable state.

## HttpClient fundamentals


`GetFromJsonAsync` = GET + status check + System.Text.Json deserialize (web defaults: camelCase, case-insensitive) in one call.

### Lifetime: the famous rule

**Do not create an HttpClient per request** — sockets linger (TIME_WAIT) and you exhaust ports under load. For apps without DI: one static client for the app's life. In ASP.NET Core (Module 10): `IHttpClientFactory` manages pooled handlers properly. A `using` around HttpClient in a loop is the #1 HttpClient bug in the wild.

### Status codes & errors

```csharp
var response = await client.GetAsync($"users/{id}", ct);

if (response.StatusCode == System.Net.HttpStatusCode.NotFound)
    return null;                                   // 404 often isn't exceptional — decide!

response.EnsureSuccessStatusCode();                // else: throw HttpRequestException on 4xx/5xx
var user = await response.Content.ReadFromJsonAsync<User>(cancellationToken: ct);
```

`GetFromJsonAsync` throws on non-success; drop to `GetAsync` when you need per-status decisions. Catch `HttpRequestException` (network/DNS/status failures) and `TaskCanceledException` (timeout — awkwardly, .NET surfaces HttpClient timeouts as cancellation; check `ex.InnerException is TimeoutException` on .NET 6+).

### Full request control

```csharp
using var request = new HttpRequestMessage(HttpMethod.Get, "search?q=dotnet");
request.Headers.Authorization = new("Bearer", token);
request.Headers.Accept.ParseAdd("application/json");

using var resp = await client.SendAsync(request, HttpCompletionOption.ResponseHeadersRead, ct);
await using var stream = await resp.Content.ReadAsStreamAsync(ct);   // stream big bodies, don't buffer
```

`ResponseHeadersRead` starts processing before the whole body downloads — pair with streaming deserialization for large payloads.

## Resilience: the real world is flaky

Transient failures (503s, timeouts, connection resets) are *normal*. Production HTTP needs retry + backoff + circuit-breaking. Modern .NET standardizes this via `Microsoft.Extensions.Http.Resilience` (built on **Polly**) with DI (Module 10):

```csharp
services.AddHttpClient<CatalogClient>()
        .AddStandardResilienceHandler();     // retries w/ exponential backoff + jitter, timeout, circuit breaker
```

Until DI, your Module 7 `WithRetry` helper is the same idea hand-rolled. Retry only *idempotent* operations (GET, PUT) automatically; retried POSTs can double-charge cards.

## Calling APIs well — etiquette that keeps you unblocked

- Send a real `User-Agent`; respect `Retry-After` headers on 429 (rate-limited) responses.
- Timeouts always (the default 100 s is not a strategy); cancellation tokens through every call.
- Log request URL + status + elapsed — you will need it the first time something breaks.

? Why is `using var client = new HttpClient()` per request harmful?
- HttpClient isn't disposable
* Each instance's sockets linger after disposal; under load you exhaust ephemeral ports — share one client (or use IHttpClientFactory)
- It leaks memory only
- It disables HTTPS

? GetFromJsonAsync&lt;T&gt; on a 404 response…
- Returns default(T)
* Throws HttpRequestException — use GetAsync + status inspection when 404 is a normal outcome
- Retries automatically
- Returns an empty T

? An HttpClient timeout surfaces as…
- TimeoutException directly

- HttpRequestException with status 408
- A null response

- None

- HttpClient filters the response
- It doesn't; you must model everything

## Async ≠ parallel — pick the right tool

| Workload | Tool | Why |
|----------|------|-----|
| Many I/O waits (network, disk) | `async`/`await` + WhenAll | Overlap waits; ~zero threads |
| CPU-heavy computation | `Parallel.For/ForEach`, PLINQ | Use all cores |
| Mixed async I/O over a collection | `Parallel.ForEachAsync` | Concurrency-capped async loop |
| Producer/consumer pipelines | `Channel<T>` | Decoupled stages, backpressure |

## Data parallelism: Parallel & PLINQ

```csharp
// CPU-bound loop across all cores:
Parallel.For(0, images.Count, i => ApplyFilter(images[i]));

Parallel.ForEach(files,
    new ParallelOptions { MaxDegreeOfParallelism = Environment.ProcessorCount },
    file => Transcode(file));

// PLINQ — parallel LINQ for CPU-heavy queries:
var primes = Enumerable.Range(2, 5_000_000)
    .AsParallel()
    .Where(IsPrime)
    .Count();
```

Rules of engagement: the work per item must be *meaningful* (parallelizing `x + 1` costs more in coordination than it saves); results order is not guaranteed (`.AsOrdered()` restores it at a cost); and shared mutable state is forbidden without synchronization — prefer per-item results combined afterward.

```csharp
// The safe aggregation shape:
long total = files.AsParallel().Sum(f => new FileInfo(f).Length);   // framework combines per-thread partials
```

### `lock` — when you truly must share

```csharp
private readonly Lock _lock = new();          // .NET 9+ dedicated Lock type
private int _hits;

public void RecordHit()
{
    lock (_lock) { _hits++; }                  // one thread at a time in this block
}
```

Keep locked regions tiny; never `await` inside a `lock` (compile error, and for good reason). If you're locking a lot, restructure toward confinement or channels.

## Channels: async producer/consumer done right

`System.Threading.Channels` is the modern way to pump work between async producers and consumers — a thread-safe async queue with **backpressure**:

```csharp
using System.Threading.Channels;

var channel = Channel.CreateBounded<string>(capacity: 100);   // bounded = backpressure!

// Producer(s):
async Task ProduceAsync(ChannelWriter<string> writer, CancellationToken ct)
{
    foreach (var url in urls)
        await writer.WriteAsync(url, ct);      // WAITS when the channel is full — producer slows to consumer pace
    writer.Complete();                          // signal: no more items
}

// Consumer(s):
async Task ConsumeAsync(ChannelReader<string> reader, CancellationToken ct)
{
    await foreach (var url in reader.ReadAllAsync(ct))       // IAsyncEnumerable!
        await ProcessAsync(url, ct);
}

// Wire N producers to M consumers freely:
var producers = ProduceAsync(channel.Writer, ct);
var consumers = Enumerable.Range(0, 4).Select(_ => ConsumeAsync(channel.Reader, ct)).ToArray();
await producers;
await Task.WhenAll(consumers);
```

Why bounded matters: an unbounded queue with a fast producer and slow consumer grows until memory dies. A bounded channel makes the producer *wait* — the system self-regulates. This concept (backpressure) is the heart of every serious data pipeline, from TPL Dataflow to Kafka.

### Choosing shapes

- One HTTP fetch feeding one parser feeding one DB writer, all at different speeds → **pipeline of channels**.
- 10,000 independent API calls, max 8 at once → **SemaphoreSlim/Parallel.ForEachAsync** (last lesson).
- Crunch 10M numbers → **PLINQ/Parallel.For**.
- Background service consuming a queue forever → **channel + worker loop** (Module 11's BackgroundService).

```csharp
int unsafeCount = 0;
```

### Step 3 — a three-stage channel pipeline

Simulate: crawl (I/O) → parse (CPU) → save (I/O), each at its own pace:

```csharp
using System.Threading.Channels;

var pages = Channel.CreateBounded<string>(5);
var parsed = Channel.CreateBounded<(string Url, int WordCount)>(5);

// Stage 1: two crawlers
async Task Crawl(int id)
{
    for (int i = id; i < 20; i += 2)
    {
        await Task.Delay(80);                                    // "network"
        await pages.Writer.WriteAsync($"https://site/{i}");
        Console.WriteLine($"  crawler{id} fetched page {i}");
    }
}

// Stage 2: one parser (CPU-ish)
async Task Parse()
{
    await foreach (var url in pages.Reader.ReadAllAsync())
    {
        await Task.Delay(150);                                   // deliberately SLOWER than crawlers
        await parsed.Writer.WriteAsync((url, Random.Shared.Next(200, 900)));
    }
    parsed.Writer.Complete();
}

// Stage 3: one saver
async Task Save()
{
    await foreach (var (url, words) in parsed.Reader.ReadAllAsync())
        Console.WriteLine($"      saved {url} ({words} words)");
}

var crawlers = Task.WhenAll(Crawl(0), Crawl(1));
var parser = Parse();
var saver = Save();

await crawlers;
pages.Writer.Complete();          // upstream done → signal
await parser;                     // parser drains, then completes parsed
await saver;
Console.WriteLine("pipeline drained cleanly");
```

Watch the output rhythm: crawlers burst ahead, then *stall* — the bounded channel (capacity 5) is backpressure making fast stages wait for slow ones. Kill the bound (`CreateUnbounded`) and the stall disappears — along with your memory safety at scale.

### Step 4 — graceful completion semantics

Trace the shutdown chain in step 3: producers finish → `Complete()` on pages → `ReadAllAsync` loops end → parser completes parsed → saver's loop ends. No sentinel values, no polling, no flags — completion *propagates through the pipeline*. This choreography is what makes channels superior to hand-rolled queues.

```csharp
            }

            int msIdx = parts[3].IndexOf("in ");
            if (msIdx >= 0 && double.TryParse(parts[3][(msIdx + 3)..].TrimEnd('m', 's'), out double ms))
                localTimes.Add(ms);
        }
        lock (mergeLock) responseTimes.AddRange(localTimes);
    });

alerts.Writer.Complete();
await alertWriter;

responseTimes.Sort();
double P(double q) => responseTimes[(int)(q * (responseTimes.Count - 1))];
Console.WriteLine($"""
    lines: {totalLines:N0} in {sw.ElapsedMilliseconds:N0} ms
    levels: {string.Join("  ", levelCounts.Select(kv => $"{kv.Key}:{kv.Value:N0}"))}
    latency p50 {P(0.50):F0} ms   p95 {P(0.95):F0} ms
    alerts written: {alertsWritten}
    """);
```

Honest note on the sync bridge: `Parallel.ForEach` bodies are synchronous, so the channel write uses GetAwaiter().GetResult() — acceptable here because the wait is the *intended* backpressure. The fully-async alternative is `Parallel.ForEachAsync` with an async body — refactor to it as a bonus and the bridge disappears. Both designs are defensible; knowing *why* is the lesson.

@QUIZ
? Parallel.For is the right tool when…
- Making many HTTP calls
* The work is CPU-bound and each iteration is substantial and independent
- Iterations must run in order
- You need backpressure
> Data parallelism spreads computation across cores. I/O belongs to async; ordering needs sequential; flow control needs channels.

? A bounded channel's key property vs an unbounded one?
- It's faster
* WriteAsync waits when full — backpressure keeps a fast producer from drowning a slow consumer (and your memory)
- It preserves ordering
- It allows multiple readers
> Both preserve FIFO and support multiple readers/writers. Boundedness is about flow control: the queue can't grow without limit.

? `channel.Writer.Complete()` causes…
- Pending items to be dropped
* ReadAllAsync loops to finish after draining remaining items — completion propagates gracefully downstream
- An exception in readers
- The channel to reset
> Complete says "no more items ever". Readers drain what's buffered, then their await foreach ends — the clean-shutdown mechanism for pipelines.

? `Parallel.For(0, 1_000_000, _ => count++)` produces a wrong count because…
- Parallel.For skips iterations
* ++ is read-modify-write; concurrent threads interleave and overwrite each other's updates (a data race)
- int can't hold a million
- The lambda captures incorrectly
> Classic lost-update race. Fixes in preference order: confinement (per-thread partials), Interlocked, lock.

? Why is `await` inside a `lock` block forbidden?
- Locks are value types
* The method could resume on a different thread, and holding a lock across a suspension invites deadlocks — the compiler bans it outright
- await releases all locks
- It's allowed with async locks
> lock ownership is thread-affine and suspension breaks that. For async mutual exclusion use SemaphoreSlim(1,1) with WaitAsync/Release in try/finally.
