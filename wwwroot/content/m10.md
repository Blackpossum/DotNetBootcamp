## The shape of a web service

ASP.NET Core is .NET's web framework — consistently at the top of the TechEmpower benchmarks and the runtime behind Bing, Stack Overflow, and a substantial slice of the internet's APIs. **Minimal APIs** are its modern, terse entry point:

```csharp
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/", () => "Hello, web!");
app.MapGet("/time", () => new { Utc = DateTimeOffset.UtcNow });   // objects auto-serialize to JSON

app.Run();                                                        // blocks, serving requests
```

```bash
dotnet new web -n MyApi && cd MyApi && dotnet run
# → Now listening on: http://localhost:5xxx
```

Two phases to internalize: **builder phase** (register services, read config) → `Build()` → **app phase** (map endpoints, add middleware) → `Run()`.

## Routing: verbs, templates, binding

```csharp
app.MapGet("/products", () => Results.Ok(products));
app.MapGet("/products/{id:int}", (int id) => …);                  // route constraint
app.MapPost("/products", (ProductDto dto) => …);                  // body binds from JSON
app.MapPut("/products/{id}", (int id, ProductDto dto) => …);
app.MapDelete("/products/{id}", (int id) => …);

// Binding sources — inferred by convention:
app.MapGet("/search", (string q, int page = 1) => …);             // simple types ← query string (?q=x&page=2)
app.MapPost("/orders", (OrderDto dto, HttpContext ctx) => …);     // complex type ← JSON body; framework types injected
```

REST conventions worth absorbing now: nouns for resources (`/products`, not `/getProducts`); GET reads (safe, cacheable), POST creates, PUT replaces, DELETE removes; plural resource names; ids in the path, filters in the query string.

### Returning results honestly

```csharp
app.MapGet("/products/{id:int}", (int id) =>
    store.Find(id) is { } product
        ? Results.Ok(product)                            // 200 + JSON
        : Results.NotFound());                           // 404

app.MapPost("/products", (ProductDto dto) =>
{
    var created = store.Add(dto);
    return Results.Created($"/products/{created.Id}", created);   // 201 + Location header
});
```

`Results.*` (or the typed `TypedResults.*`) map directly to HTTP semantics: `Ok` 200, `Created` 201, `NoContent` 204, `BadRequest` 400, `NotFound` 404, `ValidationProblem` 400+details. Status codes are your API's body language — get them right and every client tool understands you.

## Route groups — structure as endpoints multiply

```csharp
var products = app.MapGroup("/products").WithTags("Products");
products.MapGet("/", ListProducts);
products.MapGet("/{id:int}", GetProduct);
products.MapPost("/", CreateProduct);

static IResult ListProducts(ProductStore store) => Results.Ok(store.All);   // named methods > fat lambdas
```

## OpenAPI: your API's contract

.NET 10 templates wire **OpenAPI document generation** in natively:

```csharp
builder.Services.AddOpenApi();
…
app.MapOpenApi();                    // serves /openapi/v1.json
```

That JSON document describes every endpoint, parameter, and schema — machine-readable. Point any Swagger UI/Scalar at it for interactive docs, generate typed clients from it, diff it in CI to catch breaking changes. Metadata enriches it:

```csharp
products.MapGet("/{id:int}", GetProduct)
    .WithSummary("Get a product by id")
    .Produces<Product>(200)
    .Produces(404);
```

:::note Controllers exist too
The `[ApiController]` class-based style dominates older codebases and remains fully supported — read it fluently (attributes `[HttpGet("{id}")]`, base class `ControllerBase`, `ActionResult<T>`). New services default to minimal APIs; the concepts (routing, binding, DI, middleware) are identical.
:::

### Step 2 — an in-memory store + endpoints

```csharp
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddOpenApi();
var app = builder.Build();
app.MapOpenApi();

var quotes = new List<Quote>
{
    new(1, "Talk is cheap. Show me the code.", "Linus Torvalds"),
    new(2, "Simplicity is the soul of efficiency.", "Austin Freeman"),
    new(3, "Programs must be written for people to read.", "Harold Abelson"),
};
int nextId = 4;

var api = app.MapGroup("/quotes").WithTags("Quotes");

api.MapGet("/", (string? author) =>
    author is null
        ? Results.Ok(quotes)
        : Results.Ok(quotes.Where(q => q.Author.Contains(author, StringComparison.OrdinalIgnoreCase))));

api.MapGet("/random", () => Results.Ok(quotes[Random.Shared.Next(quotes.Count)]));

api.MapGet("/{id:int}", (int id) =>
    quotes.FirstOrDefault(q => q.Id == id) is { } quote
        ? Results.Ok(quote)
        : Results.NotFound(new { Error = $"no quote {id}" }));

api.MapPost("/", (QuoteDto dto) =>
{
    if (string.IsNullOrWhiteSpace(dto.Text) || string.IsNullOrWhiteSpace(dto.Author))
        return Results.BadRequest(new { Error = "text and author are required" });

    var quote = new Quote(nextId++, dto.Text.Trim(), dto.Author.Trim());
    quotes.Add(quote);
    return Results.Created($"/quotes/{quote.Id}", quote);
});

api.MapDelete("/{id:int}", (int id) =>
    quotes.RemoveAll(q => q.Id == id) > 0 ? Results.NoContent() : Results.NotFound());

app.Run();

public record Quote(int Id, string Text, string Author);
public record QuoteDto(string Text, string Author);
```

## Challenge: `HabitTracker` API (in-memory)

Design and build a habit-tracking API — resource modeling is the exercise.

### Requirements

1. Resources & routes (route groups, correct verbs/status codes):
   - `GET /habits` — list, filterable by `?tag=`
   - `POST /habits` — create (name required 3–50 chars, optional tags list) → 201 + Location
   - `GET /habits/{id}` — 200/404
   - `DELETE /habits/{id}` — 204/404
   - `POST /habits/{id}/checkins` — record a check-in for today; **reject duplicates for the same day** with 409 Conflict
   - `GET /habits/{id}/streak` — current streak: consecutive days ending today (or yesterday if today unchecked)
2. Records for models; a plain `List<Habit>`/`Dictionary` store is fine (persistence next lessons).
3. Streak logic must be correct across gaps — write it as a pure static method and reason about it (this is Module 2 loops + Module 3 dates wearing a web hat).
4. Exercise every endpoint with curl/REST client including: duplicate check-in → 409, streak with a gap, filter by tag.
5. `.WithSummary` + `.Produces` metadata on at least the streak endpoint; confirm it appears in `/openapi/v1.json`.

:::solution Show solution (core)
```csharp
public record Habit(int Id, string Name, List<string> Tags, SortedSet<DateOnly> CheckIns);
public record HabitDto(string Name, List<string>? Tags);

var habits = new Dictionary<int, Habit>();
int nextId = 1;

var api = app.MapGroup("/habits").WithTags("Habits");

api.MapGet("/", (string? tag) => Results.Ok(
    habits.Values
        .Where(h => tag is null || h.Tags.Contains(tag, StringComparer.OrdinalIgnoreCase))
        .Select(h => new { h.Id, h.Name, h.Tags, CheckInCount = h.CheckIns.Count })));

api.MapPost("/", (HabitDto dto) =>
{
    if (dto.Name is not { Length: >= 3 and <= 50 })
        return Results.BadRequest(new { Error = "name must be 3–50 chars" });

    var habit = new Habit(nextId++, dto.Name.Trim(), dto.Tags ?? [], []);
    habits[habit.Id] = habit;
    return Results.Created($"/habits/{habit.Id}", habit);
});

api.MapGet("/{id:int}", (int id) =>
    habits.TryGetValue(id, out var h) ? Results.Ok(h) : Results.NotFound());

api.MapDelete("/{id:int}", (int id) =>
    habits.Remove(id) ? Results.NoContent() : Results.NotFound());

api.MapPost("/{id:int}/checkins", (int id) =>
{
    if (!habits.TryGetValue(id, out var h)) return Results.NotFound();

    var today = DateOnly.FromDateTime(DateTime.Today);
    return h.CheckIns.Add(today)                              // SortedSet.Add returns false on duplicate
        ? Results.Created($"/habits/{id}/checkins", new { Date = today })
        : Results.Conflict(new { Error = "already checked in today" });
});

api.MapGet("/{id:int}/streak", (int id) =>
        habits.TryGetValue(id, out var h)
            ? Results.Ok(new { Streak = CurrentStreak(h.CheckIns, DateOnly.FromDateTime(DateTime.Today)) })
            : Results.NotFound())
    .WithSummary("Current consecutive-day streak")
    .Produces<object>(200)
    .Produces(404);

static int CurrentStreak(SortedSet<DateOnly> checkIns, DateOnly today)
{
    // streak may end today OR yesterday (today not yet checked)
    var cursor = checkIns.Contains(today) ? today
               : checkIns.Contains(today.AddDays(-1)) ? today.AddDays(-1)
               : default;
    if (cursor == default) return 0;

    int streak = 0;
    while (checkIns.Contains(cursor))
    {
        streak++;
        cursor = cursor.AddDays(-1);
    }
    return streak;
}
```

Design notes: `SortedSet<DateOnly>` makes duplicate rejection a return value (no pre-check race) and keeps dates ordered for free; 409 Conflict is the precise code for "valid request, conflicting state" — distinct from 400 (malformed) and 404 (absent). CurrentStreak is a pure function taking `today` as a parameter — Module 8's testability reflex, applied without being asked.
:::

@QUIZ
? In `app.MapGet("/items/{id:int}", (int id, string? sort) => …)`, where do id and sort bind from?
* id from the route path; sort from the query string (?sort=…)
- Both from the query string
- Both from the body
- id from headers, sort from route
> Simple types bind route-first, then query. Complex types bind from the JSON body. The :int constraint 404s non-numeric paths before your code runs.

? POST creating a resource should return…
- 200 with the resource
* 201 Created with a Location header pointing at the new resource
- 204 No Content
- 302 Redirect
> 201 + Location is the REST contract for creation — Results.Created($"/items/{id}", item) produces exactly that shape.

? 409 Conflict vs 400 Bad Request — the distinction?
- They're interchangeable
* 400 = the request itself is malformed/invalid; 409 = the request is fine but conflicts with current server state (duplicate, version clash)
- 409 is for authentication
- 400 is server-side errors
> Duplicate check-in, unique-constraint hit, optimistic concurrency clash → 409. Missing required field, bad format → 400. Clients branch on this.

? The OpenAPI document (/openapi/v1.json) exists so that…
- Browsers render the API
* Machines can read your API's full contract: interactive docs, generated clients, CI breaking-change diffs
- The API runs faster
- Endpoints are secured
> OpenAPI is the lingua franca of HTTP APIs. .NET 10 generates it natively from your endpoint metadata.

? WebApplication's two phases are…
- Compile and run
* Builder phase (register services/config) before Build(), then app phase (middleware + endpoints) before Run()
- Debug and release
- Startup and shutdown
> Services registered after Build() throw; middleware added before it doesn't exist. The phase boundary is the framework's spine — internalize it now, everything in the next lesson hangs off it.

## The DI container: Module 8's pattern, industrialized

ASP.NET Core has a built-in **IoC container**. You register services in the builder phase; the framework constructs and injects them everywhere:

```csharp
builder.Services.AddSingleton<IClock, SystemClock>();
builder.Services.AddScoped<IOrderService, OrderService>();
builder.Services.AddTransient<IEmailRenderer, EmailRenderer>();

// Endpoints receive registered services as parameters — just declare them:
app.MapPost("/orders", (OrderDto dto, IOrderService orders) => orders.Place(dto));
```

### The three lifetimes — the exam question that matters daily

| Lifetime | One instance per… | Use for |
|----------|-------------------|---------|
| **Singleton** | application | Stateless services, caches, config holders, HttpClient handlers |
| **Scoped** | HTTP request | **DbContext**, anything carrying per-request state |
| **Transient** | injection | Lightweight stateless helpers |

The classic bug: **a scoped service injected into a singleton** — the "captive dependency". The singleton outlives the request; its captured DbContext is disposed or shared across requests. The container detects the direct case and throws; the indirect cases corrupt data. Rule: a service may only depend on lifetimes *equal or longer* than its own.

```csharp
// EF integration — registers a SCOPED context, pooled for performance:
builder.Services.AddDbContextPool<ShopContext>(o => o.UseSqlite(connectionString));

// HttpClient done right (Module 7's factory promise, delivered):
builder.Services.AddHttpClient<CatalogClient>(c => c.BaseAddress = new Uri("https://api…"))
                .AddStandardResilienceHandler();      // Polly retries/timeout/circuit-breaker
```

## The middleware pipeline

Every request flows through an ordered chain of **middleware**; every response flows back through it in reverse:

```
request →  ExceptionHandler → HTTPS → Auth → RateLimit → [endpoint] 
response ←────────────────────────────────────────────────────┘
```

```csharp
app.UseExceptionHandler();               // catches everything downstream → 500 ProblemDetails
app.UseHttpsRedirection();
app.UseAuthentication();                 // WHO are you (fills User)
app.UseAuthorization();                  // MAY you (checks policies)
app.UseRateLimiter();

// custom middleware — the standard shape:
app.Use(async (context, next) =>
{
    var sw = Stopwatch.StartNew();
    await next(context);                                 // ↓ everything downstream runs here
    app.Logger.LogInformation("{Method} {Path} → {Status} in {Ms}ms",
        context.Request.Method, context.Request.Path,
        context.Response.StatusCode, sw.ElapsedMilliseconds);
});
```

**Order is behavior**: exception handling first (to catch everything), auth before endpoints (to protect them), CORS before responses are shaped. A middleware that doesn't call `next` *short-circuits* — that's how auth rejects and rate limiters throttle.

### Errors as ProblemDetails

```csharp
builder.Services.AddProblemDetails();
app.UseExceptionHandler();
app.UseStatusCodePages();
```

Failures become RFC 9457 `application/problem+json` — a standard shape (`type`, `title`, `status`, `detail`) every client can parse. `Results.ValidationProblem(errors)` emits the same family for 400s. Never leak stack traces in production responses; log them instead.

## Configuration & Options

Configuration merges layers, later overriding earlier: `appsettings.json` → `appsettings.{Environment}.json` → user-secrets (dev) → environment variables → command line.

```json
// appsettings.json
{ "Smtp": { "Host": "mail.example.com", "Port": 587 } }
```

```csharp
public class SmtpOptions { public required string Host { get; set; } public int Port { get; set; } = 25; }

builder.Services.Configure<SmtpOptions>(builder.Configuration.GetSection("Smtp"));

// consume via IOptions<T>:
app.MapGet("/mail-config", (IOptions<SmtpOptions> opt) => opt.Value.Host);
```

Secrets never go in appsettings.json (it's in git!): `dotnet user-secrets` for development, environment variables / key vaults in production. `ASPNETCORE_ENVIRONMENT` (Development/Production) selects the environment; `app.Environment.IsDevelopment()` branches on it.

## Logging

```csharp
app.MapGet("/work", (ILogger<Program> log) =>
```

### Step 1 — three counters, three lifetimes

```csharp
public interface ICounter { Guid Id { get; } int Next(); }
public class Counter : ICounter
{
    public Guid Id { get; } = Guid.NewGuid();
    private int _n;
    public int Next() => ++_n;
}

public interface ISingletonCounter : ICounter;   public class SingletonCounter : Counter, ISingletonCounter;
public interface IScopedCounter : ICounter;      public class ScopedCounter : Counter, IScopedCounter;
public interface ITransientCounter : ICounter;   public class TransientCounter : Counter, ITransientCounter;
```

```csharp
builder.Services.AddSingleton<ISingletonCounter, SingletonCounter>();
builder.Services.AddScoped<IScopedCounter, ScopedCounter>();
builder.Services.AddTransient<ITransientCounter, TransientCounter>();

app.MapGet("/lifetimes", (
    ISingletonCounter s,
    IScopedCounter sc1, IScopedCounter sc2,          // injected TWICE in one request
    ITransientCounter t1, ITransientCounter t2) => new
{
    Singleton = new { s.Id, Count = s.Next() },
    ScopedSameRequest = new { First = sc1.Id, Second = sc2.Id, Same = sc1.Id == sc2.Id },   // true!
    TransientSameRequest = new { First = t1.Id, Second = t2.Id, Same = t1.Id == t2.Id },    // false!
});
```

Hit `/lifetimes` repeatedly: the singleton's Id never changes and its count climbs across requests; scoped Ids change per request but are identical within one; transient Ids differ even within a single request. Three refreshes teach more than three articles.

### Step 3 — timing + correlation middleware

```csharp
app.Use(async (ctx, next) =>
{
    string correlationId = ctx.Request.Headers.TryGetValue("X-Correlation-Id", out var cid)
        ? cid.ToString() : Guid.NewGuid().ToString("N")[..8];

```

Every response now carries a correlation id and every request logs one structured line — the twin pillars of debuggable services. Curl with `-i` to see the header.

```csharp
app.Use(async (ctx, next) =>
```

## Challenge: production-grade plumbing for a tiny API

Take a 3-endpoint API (`GET /items`, `POST /items`, `GET /items/{id}` over an in-memory store — write it fresh in 10 minutes) and give it production plumbing. The API is trivial *on purpose*; the plumbing is the deliverable.

### Requirements

1. **Services & lifetimes**: `IItemStore` (singleton — it IS the shared state), `IRequestAudit` (scoped: collects notes during one request, flushed by middleware at the end), `IIdGenerator` (transient). Wire each; justify each lifetime in a one-line comment.
2. **Middleware stack, correctly ordered**: exception handler (+ProblemDetails) → correlation id → timing/structured log (including the audit flush) → a maintenance-mode gate (returns 503 + Retry-After when `Features:Maintenance` is true in config) → endpoints.
3. **Options**: `FeaturesOptions { Maintenance, MaxItemsPerRequest }` bound from config; POST rejects batches over the limit with `Results.ValidationProblem`.
4. **Structured logging** throughout — zero string interpolation in log calls (grep yourself honest).
5. **Prove it works**: a curl session showing — a normal request with correlation id header; a thrown exception (`GET /items/boom` endpoint that throws) returning clean ProblemDetails with NO stack trace; maintenance mode flipped on via environment variable returning 503 everywhere.

:::solution Show solution (core wiring)
```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddProblemDetails();
builder.Services.Configure<FeaturesOptions>(builder.Configuration.GetSection("Features"));
builder.Services.AddSingleton<IItemStore, ItemStore>();        // app-wide shared state (thread-safe inside!)
builder.Services.AddScoped<IRequestAudit, RequestAudit>();     // per-request note collector
builder.Services.AddTransient<IIdGenerator, IdGenerator>();    // stateless helper, cheap to make

var app = builder.Build();

app.UseExceptionHandler();                                     // FIRST: catch everything below

app.Use(async (ctx, next) =>                                   // correlation
{
    ctx.Items["cid"] = Guid.NewGuid().ToString("N")[..8];
    ctx.Response.Headers["X-Correlation-Id"] = (string)ctx.Items["cid"]!;
    await next(ctx);
});

app.Use(async (ctx, next) =>                                   // timing + audit flush
{
    var sw = Stopwatch.StartNew();
    await next(ctx);
    var audit = ctx.RequestServices.GetRequiredService<IRequestAudit>();   // resolve scoped INSIDE the request
    app.Logger.LogInformation("[{Cid}] {Method} {Path} → {Status} ({Ms} ms) notes: {Notes}",
        ctx.Items["cid"], ctx.Request.Method, ctx.Request.Path,
        ctx.Response.StatusCode, sw.ElapsedMilliseconds, audit.Notes);
});

app.Use(async (ctx, next) =>                                   // maintenance gate
{
    var features = ctx.RequestServices.GetRequiredService<IOptions<FeaturesOptions>>().Value;
    if (features.Maintenance)
    {
        ctx.Response.StatusCode = StatusCodes.Status503ServiceUnavailable;
        ctx.Response.Headers.RetryAfter = "3600";
        await ctx.Response.WriteAsJsonAsync(new { Error = "down for maintenance" });
        return;
    }
    await next(ctx);
});

app.MapGet("/items", (IItemStore store, IRequestAudit audit) =>
{
    audit.Note("listed items");
    return Results.Ok(store.All);
});

app.MapPost("/items", (List<ItemDto> dtos, IItemStore store, IIdGenerator ids,
                       IOptions<FeaturesOptions> opt, IRequestAudit audit) =>
{
    if (dtos.Count > opt.Value.MaxItemsPerRequest)
        return Results.ValidationProblem(new Dictionary<string, string[]>
        {
            ["items"] = [$"max {opt.Value.MaxItemsPerRequest} items per request"]
        });

    var created = dtos.Select(d => store.Add(ids.Next(), d.Name)).ToList();
    audit.Note($"created {created.Count}");
    return Results.Created("/items", created);
});

app.MapGet("/items/boom", () => (IResult)(throw new InvalidOperationException("kaboom")));
// (or: app.MapGet("/items/boom", IResult () => throw new InvalidOperationException("kaboom"));)

app.Run();
```

The subtle piece: the timing middleware resolves `IRequestAudit` from `ctx.RequestServices` — the request's *scope* — rather than constructor injection (middleware constructed once = singleton context, would capture!). @QUIZ
? Why must DbContext be Scoped, not Singleton?
- Performance
* A context is a unit of work with per-request tracked state, and it isn't thread-safe — one per request is the correct shape
- SQLite requires it
- Singletons can't be disposed
> One shared tracker across all concurrent requests = corruption + unbounded memory + stale identity-map reads. Request-scoped is the law (and AddDbContext registers it so).

? A "captive dependency" is…
- A circular reference
* A shorter-lived service held by a longer-lived one — e.g. scoped DbContext captured by a singleton — outliving its intended lifetime
- A service without an interface
- A disposed service
> The singleton keeps its first request's scoped instance forever: disposed contexts, cross-request data bleed. Depend only on equal-or-longer lifetimes.

? Middleware order matters because…
- Alphabetical order is enforced
* Requests traverse the pipeline in registration order (and responses in reverse) — auth must precede endpoints, exception handling must wrap everything
- It affects DI resolution
- It doesn't
> UseExceptionHandler first catches all downstream throws; a gate placed after MapXxx protects nothing. Pipeline order IS the security and error model.

? `log.LogInformation("order {OrderId}", id)` beats `log.LogInformation($"order {id}")` because…
- It's faster to type
* The template keeps OrderId as structured, queryable data in log systems — interpolation flattens it into an opaque string
- Interpolation throws in logging
- Templates are localized
> Structured logging turns logs into a database. `{OrderId}` is indexed; "order 42" is grep-only. Also avoids formatting cost when the level is filtered out.

? Config value present in appsettings.json AND as an environment variable — which wins?
- appsettings.json
* The environment variable — later providers override earlier ones
- Whichever was set most recently
- It throws for ambiguity

### DTOs vs entities — never expose your database

```csharp
// ENTITY — internal, has FKs, navigations, EF concerns:
public class Product { public int Id; public string Name; public decimal Price; public Category Category; … }

// DTOs — the API's public contract, shaped for clients:
public record ProductResponse(int Id, string Name, decimal Price, string Category);
public record CreateProductRequest(string Name, decimal Price, int CategoryId);
public record UpdateProductRequest(string Name, decimal Price);
```

Why the ceremony: entities leak schema (rename a column, break clients), create serialization cycles (Product→Category→Products→…), and over-post (a client PUTs `"id": 999` into your entity). DTO mapping is cheap insurance — write it manually with expression-bodied methods or projections (Mapster/AutoMapper exist; manual is clearer while learning).

## The service layer + typed results

```csharp
public class ProductService(ShopContext db)
{
    public async Task<ProductResponse?> GetAsync(int id, CancellationToken ct)
        => await db.Products.AsNoTracking()
            .Where(p => p.Id == id)
            .Select(p => new ProductResponse(p.Id, p.Name, p.Price, p.Category.Name))
            .FirstOrDefaultAsync(ct);

    public async Task<Result<ProductResponse>> CreateAsync(CreateProductRequest req, CancellationToken ct)
    {
        if (!await db.Categories.AnyAsync(c => c.Id == req.CategoryId, ct))
            return Result<ProductResponse>.Fail("CategoryId", "no such category");

        if (await db.Products.AnyAsync(p => p.Name == req.Name, ct))
            return Result<ProductResponse>.Fail("Name", "name already exists");

        var product = new Product { Name = req.Name, Price = req.Price, CategoryId = req.CategoryId };
        db.Add(product);
        await db.SaveChangesAsync(ct);

        return Result<ProductResponse>.Ok(new(product.Id, product.Name, product.Price,
            (await db.Categories.FindAsync([req.CategoryId], ct))!.Name));
    }
}
```

## Patterns per verb — the professional defaults

```csharp
// GET list: paginate ALWAYS, filter server-side, project, no tracking
products.MapGet("/", async (string? search, int page, int pageSize, ShopContext db, CancellationToken ct) =>
{
    pageSize = Math.Clamp(pageSize == 0 ? 20 : pageSize, 1, 100);       // never trust client sizes

    var items = await query.OrderBy(p => p.Name)
```

## AuthN vs AuthZ — two different questions

- **Authentication**: *who are you?* → produces an identity (claims).
- **Authorization**: *may you do this?* → checks the identity against requirements.

Web APIs use **bearer tokens**: login once → receive a token → send `Authorization: Bearer <token>` on every request. The dominant format is **JWT** (JSON Web Token): three base64url parts — header.payload.signature:

```
{ "alg": "HS256" } . { "sub": "42", "name": "ada", "role": "admin", "exp": 1784972400 } . <signature>
```

The **signature** (HMAC or RSA over the first two parts with a server secret/key) makes tokens tamper-proof: change a claim, the signature fails validation. Crucial mental model: JWTs are **signed, not encrypted** — anyone can *read* the payload (paste one into jwt.io) — so never put secrets in claims. Statelessness is the win (no session store, any instance validates) and the cost (revocation is hard — hence short expiries + refresh tokens).

1. `POST /auth/register` + `/auth/login` with an in-memory user store BUT real password hashing: `PasswordHasher<T>` from Microsoft.AspNetCore.Identity (never plaintext, even in demos — the habit is the point). Tokens carry NameIdentifier + Name + role claim (`user` by default; seed one `admin`).
2. Notes CRUD (`/notes`), EF-or-in-memory storage where each Note has an `OwnerId`:
   - Users see ONLY their notes in lists, get 404 (not 403 — don't leak existence!) for others' note ids
   - Update/delete: owner only
   - `GET /admin/notes` — admins see everything, policy-protected
3. A `Adult`-style assertion policy of your invention (e.g. `PowerUser`: role user AND claim `notes-quota` > 10) applied to one endpoint; login issues the claim.
4. Ownership enforcement lives in ONE place (service method or a helper like `Task<Note?> FindOwnedAsync(int id, ClaimsPrincipal user)`), not copy-pasted per endpoint.
5. Curl transcript proving: register→login→create→list (own only)→cross-user 404→admin sees all→403 for non-admin on /admin→the assertion policy in both directions.

:::solution Show solution (core)
```csharp
// registration with real hashing
var users = new Dictionary<string, (string Hash, string Role, int Quota)>();   // username → data
var hasher = new PasswordHasher<string>();

app.MapPost("/auth/register", (RegisterRequest req) =>
{
    if (users.ContainsKey(req.Username))
        return Results.Conflict(new { Error = "username taken" });
    users[req.Username] = (hasher.HashPassword(req.Username, req.Password), "user", 5);
    return Results.Created("/auth/register", new { req.Username });
});

app.MapPost("/auth/login", (LoginRequest req, IConfiguration config) =>
{
    if (!users.TryGetValue(req.Username, out var u) ||
        hasher.VerifyHashedPassword(req.Username, u.Hash, req.Password) == PasswordVerificationResult.Failed)
        return Results.Unauthorized();

    var claims = new List<Claim>
    {
        new(ClaimTypes.NameIdentifier, req.Username),
        new(ClaimTypes.Name, req.Username),
        new(ClaimTypes.Role, u.Role),
        new("notes-quota", u.Quota.ToString()),
    };
    return Results.Ok(new { Token = IssueToken(claims, config) });
});

// policies
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("AdminOnly", p => p.RequireRole("admin"))
    .AddPolicy("PowerUser", p => p.RequireAssertion(ctx =>
        ctx.User.IsInRole("user") &&
        int.TryParse(ctx.User.FindFirstValue("notes-quota"), out int q) && q > 10));

// ownership helper — THE single enforcement point
static string UserId(ClaimsPrincipal user) => user.FindFirstValue(ClaimTypes.NameIdentifier)!;

async Task<Note?> FindOwnedAsync(NotesDb db, int id, ClaimsPrincipal user)
    => await db.Notes.FirstOrDefaultAsync(n => n.Id == id && n.OwnerId == UserId(user));

// endpoints
notes.MapGet("/", async (NotesDb db, ClaimsPrincipal user) =>
    Results.Ok(await db.Notes.Where(n => n.OwnerId == UserId(user))
        .Select(n => new NoteDto(n.Id, n.Title, n.Body)).ToListAsync()))
    .RequireAuthorization();

notes.MapGet("/{id:int}", async (int id, NotesDb db, ClaimsPrincipal user) =>
    await FindOwnedAsync(db, id, user) is { } note
        ? Results.Ok(new NoteDto(note.Id, note.Title, note.Body))
        : Results.NotFound())                          // 404 for "not yours" — existence not leaked
    .RequireAuthorization();

notes.MapDelete("/{id:int}", async (int id, NotesDb db, ClaimsPrincipal user) =>
{
    var note = await FindOwnedAsync(db, id, user);
    if (note is null) return Results.NotFound();
    db.Notes.Remove(note);
    await db.SaveChangesAsync();
    return Results.NoContent();
}).RequireAuthorization();

app.MapGet("/admin/notes", async (NotesDb db) =>
        Results.Ok(await db.Notes.Select(n => new { n.Id, n.OwnerId, n.Title }).ToListAsync()))
    .RequireAuthorization("AdminOnly");
```

The two decisions that make this professional: **404 over 403 for foreign resources** (a 403 confirms "note 17 exists but isn't yours" — an information leak; 404 reveals nothing), and **single-point ownership enforcement** (FindOwnedAsync bakes the OwnerId predicate into the query itself — there is no code path that fetches a foreign note then forgets to check). Both patterns transfer directly to production multi-tenant systems, where the predicate typically becomes an EF global query filter keyed on the current tenant.

@QUIZ
? A JWT's signature guarantees…
- The payload is encrypted
* The token wasn't modified since issuance — any claim tampering invalidates it
- The user's password was correct
- The token can't be stolen
> Signatures give integrity, not confidentiality (payload is readable!) and not possession-security (a stolen token works until expiry — hence HTTPS + short lifetimes).

? 401 vs 403?
* 401 = authentication missing/invalid; 403 = authenticated but not permitted
- 401 = server error; 403 = client error
- They're interchangeable
- 403 = token expired
> "Who are you?" failed → 401 (+ WWW-Authenticate). "You may not" → 403. APIs that conflate them break client retry/login logic.

? Why must the JWT signing key live in user-secrets/vaults, never appsettings.json?
- JSON can't hold long strings
* Anyone with the key can FORGE valid tokens for any user — committed keys are a total auth bypass
- Keys rotate daily
- appsettings is size-limited
> The signing key IS your auth system. Git history is forever; leaked keys mean attacker-issued admin tokens that validate perfectly.

? Requesting another user's note should return 404 rather than 403 because…
- 404 is easier to implement
* 403 confirms the resource exists — an information leak; 404 reveals nothing about other tenants' data
- Browsers cache 403
- REST requires it
> Enumeration attacks harvest existence from status codes. Scope queries by owner so foreign resources are simply "not found".

? ASP.NET Core Identity's password storage uses…
- AES encryption
- SHA256 of the password
* Salted, iterated adaptive hashing (PBKDF2) — deliberately slow, unique per user
- Plaintext with restricted DB access
> Fast hashes are brute-forceable at billions/sec. Adaptive KDFs with salt make each guess expensive and rainbow tables useless. Never roll your own; PasswordHasher exists.
