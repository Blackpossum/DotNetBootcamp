## Rule zero: measure, then optimize

Optimizing without measurement is guessing with confidence. The .NET toolchain:

- **BenchmarkDotNet** — THE micro-benchmark harness: handles warmup (JIT tiers!), statistical rigor, memory diagnostics. Results you can trust.
- **`dotnet-counters`** — live metrics (GC rates, exceptions, threadpool) against any running app.
- **`dotnet-trace` / Visual Studio profiler** — where is time actually going?
- **Stopwatch** — fine for coarse "is it seconds or milliseconds" questions (as this course has done throughout).

```csharp
[MemoryDiagnoser]                                  // allocation columns — usually the story
public class ParseBenchmarks
{
    private readonly string _line = "2026-07-22,EU,Keyboard,12,49.99";

    [Benchmark(Baseline = true)]
    public string[] Split() => _line.Split(',');

    [Benchmark]
    public int SpanParse()                          // preview of what's below
    {
        ReadOnlySpan<char> span = _line;
        int comma = span.LastIndexOf(',');
        return int.Parse(span[(span.LastIndexOf(',', comma - 1) + 1)..comma]);
    }
}
// dotnet run -c Release  → a report with Mean, StdDev, Gen0 collections, Allocated bytes
```

Benchmark **Release builds only** — Debug disables the optimizations you're measuring.

## Why allocation is the usual villain

Module 1's GC truths, cashed in: allocation is cheap, but *collection* costs scale with allocation *rate*. Hot paths that allocate force frequent Gen 0 collections; objects surviving into Gen 1/2 cost more; the Large Object Heap fragments. Most "make it faster" work in real services is "make it allocate less":

| Allocation source | Cure |
|-------------------|------|
| Substring/Split in parsers | `Span<char>` slicing (below) |
| String concat in loops | `StringBuilder` (Module 3) / `string.Create` |
| Boxing (value type → object) | Generics; avoid non-generic APIs (Module 5) |
| Closures in hot lambdas | `static` lambdas (Module 5) |
| Growing collections | Pre-size capacity (Module 3) |
| Repeated buffers | `ArrayPool<T>.Shared.Rent/Return` |
| Async state machines in sync-completing paths | `ValueTask<T>` (library-author concern) |

## Span&lt;T&gt;: slicing without copying

`Span<T>`/`ReadOnlySpan<T>` are **views over existing memory** — array, string, stackalloc, native — with zero allocation:

```csharp
ReadOnlySpan<char> line = "2026-07-22,EU,Keyboard,12,49.99";

// Substring ALLOCATES a new string; slicing a span allocates NOTHING:
ReadOnlySpan<char> date = line[..10];                  // view, not copy
int firstComma = line.IndexOf(',');

// int.Parse / decimal.Parse accept spans directly — parse without materializing strings:
decimal price = decimal.Parse(line[(line.LastIndexOf(',') + 1)..]);

// Slicing arrays:
int[] numbers = [1, 2, 3, 4, 5, 6];
Span<int> middle = numbers.AsSpan(1..4);               // writable window
middle[0] = 99;                                        // writes through to the array!

// stackalloc — small scratch buffers with zero heap involvement:
Span<byte> buffer = stackalloc byte[64];
```

The catch: `Span<T>` is a `ref struct` — stack-only. It cannot live in class fields, be boxed, or cross `await` boundaries (the state machine would need to heap it). For async scenarios use **`Memory<T>`/`ReadOnlyMemory<T>`** (heap-safe views; `.Span` to slice inside sync sections). C# 14's first-class span conversions make APIs increasingly just take spans — your code often gets faster by *recompiling*.

### The modern parsing idiom

```csharp
// zero-allocation CSV field walk:
static int CountFields(ReadOnlySpan<char> line)
{
    int count = 1;
    foreach (var range in line.Split(','))             // span Split enumerates ranges — no arrays!
        count++;
    return count - 1;
}
```

`MemoryExtensions.Split` (spans), `ISpanParsable<T>`, `Utf8Parser`, `SearchValues<char>` (vectorized multi-char search) — the BCL's whole modern text layer is span-first. Reading it is now in your power.

:::warn Optimize the 3%, ship the 97%
Knuth's line cut both ways: premature optimization is evil AND the critical 3% matters. The workflow: write clear code → measure under real load → optimize the proven hot spots with these tools → re-measure. Span-ifying a config parser that runs once at startup is hobbyism; span-ifying a log parser chewing 100 GB/day is engineering.
:::

### Step 3 — span version, step by step

```csharp
public static LogLine ParseSpan(ReadOnlySpan<char> line)
{
    int p1 = line.IndexOf('|');
    int p2 = line[(p1 + 1)..].IndexOf('|') + p1 + 1;

    ReadOnlySpan<char> levelSpan = line[(p1 + 1)..p2];
    string level = levelSpan switch                             // intern the 4 known levels: zero new strings
    {
        "INFO" => "INFO", "WARN" => "WARN", "ERROR" => "ERROR", "DEBUG" => "DEBUG",
        _ => levelSpan.ToString()
    };

    return new LogLine(
        DateTime.Parse(line[..p1]),
        level,
        int.Parse(line[(line.LastIndexOf('=') + 1)..]));        // parse straight from the slice
}
```

Add `[Benchmark] public int Spans()` looping with `ParseSpan(line)`. Rerun: typically **3–5× faster, ~85% less allocation**. Every technique is legible: IndexOf walks, range slices, span-parsing, and the level-interning switch (pattern matching on spans!).

### Step 4 — where does the REST of the allocation come from?

The record itself! If the consumer only needs the duration sum, parse *just that*:

```csharp
[Benchmark]
public int SpansNoRecord()
{
    int total = 0;
    foreach (var line in _lines)
    {
        ReadOnlySpan<char> span = line;
        total += int.Parse(span[(span.LastIndexOf('=') + 1)..]);
    }
    return total;                                               // ~zero allocation per line
}
```

The deepest perf lesson: the fastest code is the code that doesn't run. Parsing three fields when you need one was the real waste — no Span cleverness beats *doing less*.

### Step 5 — ArrayPool for buffer churn

```csharp
[Benchmark]
public int PooledBuffer()
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(4096);
    try
    {
        // … simulate filling/processing the buffer …
        return buffer.Length;
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer);
    }
}
```

Compare against `new byte[4096]` per iteration in the memory column: pooling turns steady-state buffer churn into ~zero. This is how Kestrel, streams, and every serious IO library manage buffers.

```csharp
public static Dictionary<string, int> IndexSpan(string document)
{
    var counts = new Dictionary<string, int>(StringComparer.Ordinal);
    ReadOnlySpan<char> text = document;
    int i = 0;

    Span<char> lowered = stackalloc char[64];                   // scratch for lowering, no heap

    while (i < text.Length)
    {
        while (i < text.Length && !char.IsLetter(text[i])) i++;         // skip separators
        int start = i;
        while (i < text.Length && char.IsLetter(text[i])) i++;          // consume word
        int len = i - start;
        if (len < 3 || len > 64) continue;

        ReadOnlySpan<char> word = text.Slice(start, len);
        int written = word.ToLowerInvariant(lowered);                    // lower into the scratch span
        ReadOnlySpan<char> key = lowered[..written];

        // Stage 3 — span lookup, allocate only for NEW words:
        var alternate = counts.GetAlternateLookup<ReadOnlySpan<char>>();
        ref int count = ref System.Runtime.InteropServices.CollectionsMarshal
            .GetValueRefOrAddDefault(counts, key.ToString(), out _);     // stage 2 version
        count++;
        // (true stage 3: alternate.TryGetValue(key, out…) first; key.ToString() only on miss —
        //  see the full listing in your benchmark project)
    }
    return counts;
}
```

## Reflection: reading (and invoking) types at runtime

Every assembly carries full metadata (Module 1); **reflection** reads it at runtime:

```csharp
Type type = typeof(Order);                          // or instance.GetType()

foreach (PropertyInfo prop in type.GetProperties())
    Console.WriteLine($"{prop.PropertyType.Name} {prop.Name}");

// read/write dynamically:
object? value = prop.GetValue(order);
prop.SetValue(order, newValue);

// find by attribute — the plugin/discovery pattern:
var handlers = assembly.GetTypes()
    .Where(t => t.GetCustomAttribute<JobHandlerAttribute>() is not null);

// instantiate + invoke dynamically:
object instance = Activator.CreateInstance(type)!;
MethodInfo method = type.GetMethod("Handle")!;
method.Invoke(instance, [payload]);
```

This is how xUnit finds `[Fact]`s, DI containers construct services, EF maps entities, serializers roam objects. **Costs**: ~100-1000× slower than direct calls, no compile-time safety (typos fail at runtime), and — increasingly relevant — **trimming/AOT hostility**: if code is only reachable via reflection, the trimmer can't see it and cuts it.

### Custom attributes — metadata you define

```csharp
[AttributeUsage(AttributeTargets.Property)]
public class RedactAttribute : Attribute;

public class User
{
    public required string Name { get; set; }
    [Redact] public required string Ssn { get; set; }
}

// a reflection-driven redactor:
static string Dump(object obj) => string.Join(", ",
    obj.GetType().GetProperties().Select(p =>
        $"{p.Name}={(p.GetCustomAttribute<RedactAttribute>() is null ? p.GetValue(obj) : "███")}"));
```

Attributes + reflection = declarative frameworks. You've consumed this pattern all course (`[Fact]`, `[Required]`, `[JsonIgnore]`); now you can build it.

## Source generators: reflection's compile-time successor

A **source generator** is a compiler plugin that *writes C# during compilation* based on your code. Same metaprogramming power, zero runtime cost, full AOT compatibility:

```
your code + [attributes] ──► Roslyn ──► generator runs ──► generated .g.cs ──► compiled together
```

You've been *using* them: `System.Text.Json` source generation (Module 6), regex generators, ASP.NET's request delegate generator, WPF/dependency-property generators. The consumption pattern is always: **partial** type + attribute + the generator fills the other half:

```csharp
// JSON, AOT-ready serializer code at compile time:
[JsonSerializable(typeof(Product))]
public partial class AppJsonContext : JsonSerializerContext { }
// usage: JsonSerializer.Serialize(product, AppJsonContext.Default.Product)

// Regex compiled at build time — inspect the generated code in your IDE!
public static partial class Patterns
{
    [GeneratedRegex(@"#(\w+)")]
    public static partial Regex Hashtags();
}

// High-performance logging without allocation or boxing:
public static partial class Log
{
    [LoggerMessage(Level = LogLevel.Warning, Message = "retry {Attempt} for {OrderId}")]
    public static partial void RetryScheduled(ILogger logger, int attempt, string orderId);
}
```

C# 14's **partial constructors and events** exist precisely to widen what generators can fill in. In your IDE, generated files are browsable (Solution Explorer → Analyzers → generator name) — *read them*; it demystifies the whole mechanism.

### When to choose which

| Need | Tool |
|------|------|
| Framework-style discovery in app code (occasional, warm paths) | Reflection — simple, flexible |
| Hot-path serialization/mapping/logging | Source generation — zero runtime cost |
| AOT/trimmed deployment | Source generation (reflection breaks) |
| One-off dev tooling/scripts | Reflection — speed of writing wins |

Writing your *own* generator (an `IIncrementalGenerator` in a netstandard2.0 analyzer project) is a specialized library-author skill — know the shape exists, consume them fluently, and reach for authorship when you find yourself generating boilerplate by hand across many types.

## Tutorial: build a mini object mapper — then watch generators beat it

### Step 1 — a reflection-based auto-mapper (build the classic)

```csharp
public static class Mapper
{
    public static TDest Map<TDest>(object source) where TDest : new()
    {
        var dest = new TDest();
        var destProps = typeof(TDest).GetProperties().ToDictionary(p => p.Name);

        foreach (var srcProp in source.GetType().GetProperties())
        {
            if (destProps.TryGetValue(srcProp.Name, out var destProp)
                && destProp.CanWrite
                && destProp.PropertyType.IsAssignableFrom(srcProp.PropertyType))
            {
                destProp.SetValue(dest, srcProp.GetValue(source));
            }
        }
        return dest;
    }
}
```

### Step 3 — attribute-driven validation walker

```csharp
[AttributeUsage(AttributeTargets.Property)]
public class NotEmptyAttribute : Attribute;

[AttributeUsage(AttributeTargets.Property)]
public class MaxAttribute(int value) : Attribute { public int Value { get; } = value; }

public static List<string> Validate(object obj) =>
    obj.GetType().GetProperties().SelectMany(p => Check(p, p.GetValue(obj))).ToList();

static IEnumerable<string> Check(PropertyInfo p, object? value)
{
    if (p.GetCustomAttribute<NotEmptyAttribute>() is not null
        && value is string s && string.IsNullOrWhiteSpace(s))
        yield return $"{p.Name} must not be empty";

    if (p.GetCustomAttribute<MaxAttribute>() is { } max
        && value is int n && n > max.Value)
        yield return $"{p.Name} exceeds {max.Value}";
}
```

## Challenge: `ConfigDump` — a reflection tool, hardened

Build a diagnostic utility every real service wants: dump effective configuration at startup — safely.

### Requirements

1. `ConfigDumper.Dump(object optionsObject)` returns a formatted multi-line string of all public properties: name, type, value — recursing into nested option objects (max depth 3, cycle-safe via a visited set), formatting collections as `[a, b, c]` (first 5 + count).
2. Redaction: properties named like secrets (`*Password*`, `*Key*`, `*Secret*`, `*Token*`, `*ConnectionString*` — case-insensitive) OR marked `[Redact]` print `███` plus a `(length: N)` hint for strings. The name-based net catches what devs forget to annotate.
3. Formatting rules via pattern matching on the value: null → `(null)`; bool/numbers/strings/DateTimeOffset → direct; enums → name; IEnumerable → the bracket form; other objects → recurse.
4. Wire it into a Generic Host app (Module 11): on startup, resolve two options classes (invent realistic ones — SmtpOptions with a Password, MonitorOptions with nested RetryOptions) and log the dump.
5. Tests: redaction by name AND by attribute; depth limiting (self-referencing object doesn't hang); collection truncation at 5.
6. Reflection-cost note in comments: why is startup-time reflection fine here (once, cold path) where a hot mapper wasn't — and what would break under AOT (the `Type.GetProperties` walk needs the types preserved; note `[DynamicallyAccessedMembers]` as the mitigation breadcrumb).

:::solution Show solution (core)
```csharp
[AttributeUsage(AttributeTargets.Property)]
public class RedactAttribute : Attribute;

public static class ConfigDumper
{
    private static readonly string[] SecretHints =
        ["password", "key", "secret", "token", "connectionstring"];

    public static string Dump(object options)
    {
        var sb = new StringBuilder();
        DumpInto(sb, options, indent: 0, depth: 0, visited: []);
        return sb.ToString();
    }

    private static void DumpInto(StringBuilder sb, object obj, int indent, int depth, HashSet<object> visited)
    {
        if (depth > 3 || !visited.Add(obj)) return;             // depth + cycle guard

        foreach (var prop in obj.GetType().GetProperties())
        {
            object? value = prop.GetValue(obj);
            string pad = new(' ', indent * 2);

            if (IsSecret(prop))
            {
                string hint = value is string s ? $" (length: {s.Length})" : "";
                sb.AppendLine($"{pad}{prop.Name}: ███{hint}");
                continue;
            }

            string formatted = value switch
            {
                null => "(null)",
                bool or int or long or double or decimal or DateTimeOffset or DateOnly => value.ToString()!,
                string str => $"\"{str}\"",
                Enum e => e.ToString(),
                System.Collections.IEnumerable seq => FormatCollection(seq),
                _ => ""                                          // complex → recurse below
            };

            if (formatted is not "")
            {
                sb.AppendLine($"{pad}{prop.Name}: {formatted}");
            }
            else
            {
                sb.AppendLine($"{pad}{prop.Name}:");
                DumpInto(sb, value!, indent + 1, depth + 1, visited);
            }
        }
    }

    private static bool IsSecret(PropertyInfo prop)
```

## The publishing spectrum

One codebase, four ways to ship — a deliberate ladder of tradeoffs:

| Mode | Flags | Output | Startup | Best for |
|------|-------|--------|---------|----------|
| Framework-dependent | (default) | ~1 MB | normal | Machines with .NET installed |
| Self-contained | `--self-contained` | ~70 MB | normal | Zero-prerequisite installs |
| + Trimmed | `-p:PublishTrimmed=true` | ~25 MB | normal | Smaller self-contained |
| **Native AOT** | `-p:PublishAot=true` | ~5–15 MB native | **~10× faster** | CLI tools, lambdas, microservices |

## Native AOT: no JIT, no IL — just machine code

```bash
dotnet publish -c Release -r win-x64 -p:PublishAot=true
```

The compiler (ILC) compiles *everything ahead of time* into one native binary: no JIT warmup, instant start (~10–30 ms vs 100–300 ms), lower memory floor, and nothing to decompile. .NET 10 extends AOT reach; ASP.NET Core minimal APIs have an AOT-ready subset (`dotnet new webapiaot`).

**The contract**: no runtime codegen. Which outlaws:

- Unbounded reflection (`Type.GetType(string)`, `Activator` over unknown types, `MakeGenericType`)
- `Reflection.Emit`, runtime proxies (classic mocking libraries!), `dynamic`
- Serializers/mappers that roam objects reflectively at runtime

The cures are last lesson's: **source-generated** JSON/logging/regex, DI without open-ended scanning, and libraries marked AOT-compatible. The compiler + analyzers warn (`IL2xxx`/`IL3xxx` warnings) — treat them as errors in AOT projects; a warning-free publish generally means a working binary.

The .NET SDK builds OCI images **without a Dockerfile**:


The SDK picks a matching base image (runtime-deps for AOT/self-contained, aspnet for framework-dependent), layers your app, sets the entrypoint. Classic Dockerfiles remain fully supported (multi-stage: sdk image builds → aspnet image runs) — read them fluently; CI systems are full of them:


Container facts that bite: ASP.NET Core in containers listens on **8080** by default (non-root user); configuration arrives via environment variables (`ConnectionStrings__Default=…` — Module 10's provider chain shining); logs go to stdout for the orchestrator to collect.

## When one service becomes many

A **monolith** (one deployable) is the *right* starting point — simpler ops, refactoring across features, one transaction boundary. **Microservices** split by business capability when forces demand: teams stepping on each other, divergent scaling needs, independent deploy cadence. The price is steep: network calls replace method calls, transactions fragment, observability becomes survival gear. Your Module 11 architecture skills decide *where the seams go* (a well-modularized monolith splits gracefully; a tangled one shatters).

## Synchronous: HTTP and gRPC

Service-to-service HTTP you already own (Modules 7/10). **gRPC** is the higher-performance alternative: HTTP/2, binary **Protobuf** payloads, contract-first, streaming built in:

```protobuf
// catalog.proto — the contract IS the artifact both sides generate from
syntax = "proto3";
service Catalog {
  rpc GetProduct (ProductRequest) returns (ProductReply);
  rpc WatchPrices (PriceWatchRequest) returns (stream PriceUpdate);   // server streaming!
}
message ProductRequest { int32 id = 1; }
message ProductReply { int32 id = 1; string name = 2; double price = 3; }
```

```csharp
// server: inherit the generated base
public class CatalogService : Catalog.CatalogBase
{
    public override Task<ProductReply> GetProduct(ProductRequest req, ServerCallContext ctx)
        => Task.FromResult(new ProductReply { Id = req.Id, Name = $"product-{req.Id}", Price = 9.99 });
}
app.MapGrpcService<CatalogService>();

// client: generated, strongly typed
var client = new Catalog.CatalogClient(GrpcChannel.ForAddress("https://localhost:5001"));
var reply = await client.GetProductAsync(new ProductRequest { Id = 42 });
```

Choose gRPC for internal service-to-service (typed contracts, ~5-10× smaller payloads, streaming); JSON/HTTP for public APIs (browser/tooling reach). Both coexist in one ASP.NET Core app.

## Asynchronous: messaging

The deeper decoupling: services communicate through a **broker** (RabbitMQ, Azure Service Bus, Kafka) instead of calling each other:

```
OrderService ──publish──► [order-placed] ──► InventoryService (subscriber)
                                        ──► EmailService     (subscriber)
                                        ──► AnalyticsService (subscriber)
```

- **Queues** (one consumer per message): work distribution — your Module 11 JobRunner, distributed.
- **Pub/Sub topics** (every subscriber gets a copy): event notification — publishers don't know or care who listens (Module 5's events, at system scale).

Benefits: temporal decoupling (consumer down? messages wait), load leveling (spikes queue instead of toppling), independent evolution. Costs — and these are laws, not bugs:

- **At-least-once delivery** → consumers must be **idempotent** (processing a message twice must be harmless: check an idempotency key/processed-message table before acting).
- **Ordering** is per-partition/queue at best.
- **Eventual consistency** — downstream views lag the source of truth by design; UX and business logic must tolerate it.

### Patterns you'll meet (recognition level, with your foundations)

- **Outbox** — write the DB change AND the outgoing event in one transaction (an `Outbox` table); a background service (Module 11!) publishes from it. Solves "saved but never published".
- **Saga / compensation** — distributed "transactions" as a sequence of local ones, with compensating actions on failure (your Module 6 bank transfer compensation, stretched across services).
- **Circuit breaker / retry with jitter** — Module 7/10 resilience, now mandatory: one slow dependency can cascade through synchronous call chains.
- **In .NET**: `MassTransit` and `NServiceBus` (broker abstractions with sagas/outbox built in), `Aspire` for local orchestration, OpenTelemetry tracing across every hop (the correlation id from Module 10, standardized).

:::tip The distributed-systems litmus test
Before splitting a service, answer in writing: What happens when the network call fails halfway? Where does the retry come from, and is the target idempotent? Which data is allowed to be stale, and for how long? If the answers are shrugs, stay a monolith longer — a correct monolith beats a subtly-wrong constellation every day of the week.
:::

```csharp
        await PersistProcessedIds(processed);
        File.Delete(file);                                        // the "ack"
    }
    await Task.Delay(500);
}
```

Run publisher + consumer in two terminals; restart the consumer each time it dies. **Watch the laws operate**: the file (message) survives the crash → gets redelivered → the ledger catches the duplicate → exactly-once *effect* from at-least-once *delivery*. You have now personally implemented the idempotent-consumer pattern; every real broker interaction is this with better plumbing.

The idempotency ledger solves the consumer's redelivery problem — at-least-once delivery (which the outbox's own retry behavior creates!) means duplicates WILL arrive, and the ledger-plus-effect-in-one-transaction makes reprocessing harmless. The producer's guarantee manufactures the very duplicates the consumer's guarantee absorbs: that pairing — not either half alone — is what "exactly-once processing" actually means in practice.*

@QUIZ
? The outbox pattern exists because…
- Queues are slow
* Writing the database AND publishing an event are two systems — a crash between them loses events; the outbox makes them one local transaction plus a relay
- Events need schemas
- It reduces message size
> The dual-write problem is fundamental: no distributed transaction spans your DB and a broker (affordably). Outbox = event as data, committed atomically, published asynchronously.

? At-least-once delivery obliges every consumer to be…
- Fast
* Idempotent — processing the same message twice must produce the same effect as once
- Stateless
- Ordered
> Redelivery is a feature (crash recovery), so duplicates are a certainty. Idempotency keys/ledgers checked transactionally with the effect are the standard cure.

? gRPC beats JSON/HTTP for internal service calls mainly via…
- Easier debugging in browsers
* Binary Protobuf payloads, HTTP/2 multiplexing, generated typed clients, and first-class streaming
- No need for contracts
- Automatic retries
> Contract-first .proto files generate both ends; payloads shrink; streams replace polling. Public APIs stay JSON for reach — the two coexist per audience.

? "Eventual consistency" between Orders and Shipping means…
- Data is eventually lost
* Shipping's view lags Orders by design; queries may briefly show an order without its shipment — the system converges
- Transactions retry until consistent
- Clocks must be synchronized
> Async integration trades instant global consistency for resilience and decoupling. UX and downstream logic must tolerate (and often surface) the lag.

? The strongest argument for starting with a monolith is…
- Microservices are always slower
* Every network seam adds failure modes, latency, and consistency puzzles — pay those costs only when team/scale forces demand, from a codebase whose modules already have clean seams
- Monoliths need no architecture
- Containers don't support multiple services
> Module 11's modular monolith IS microservices-ready. Distribution is an operational decision, not a design virtue — the litmus-test questions must have answers first.

```csharp
// DevBoard.Core/Cards/MovePolicy.cs
public record MoveFacts(int CardBoardId, int TargetColumnBoardId,
                        int TargetColumnCardCount, int? TargetColumnWipLimit);

public abstract record MoveDecision
{
    public sealed record Allowed : MoveDecision;
    public sealed record CrossBoard : MoveDecision;
    public sealed record WipLimitReached(int Limit) : MoveDecision;
}

public static class MovePolicy
{
    public static MoveDecision Decide(MoveFacts f) => f switch
    {
        { CardBoardId: var c, TargetColumnBoardId: var t } when c != t => new MoveDecision.CrossBoard(),
        { TargetColumnWipLimit: int limit, TargetColumnCardCount: var n } when n >= limit
            => new MoveDecision.WipLimitReached(limit),
        _ => new MoveDecision.Allowed()
    };
}
```
